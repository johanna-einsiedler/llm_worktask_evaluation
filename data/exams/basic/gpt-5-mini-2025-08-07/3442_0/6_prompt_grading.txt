### Exam Purpose
Confirm that a candidate can independently perform the core end-to-end work needed to store, retrieve, and manipulate data for analysis of a system’s capabilities and requirements. Specifically, the exam verifies practical ability to:
- ingest a small dataset (CSV/JSON text),
- design a simple storage model (file-based or SQLite),
- write correct queries / code to retrieve and transform data,
- produce aggregated metrics and a reproducible output (JSON) that an evaluator can verify.

This mimics real tasks such as logging ingestion, basic telemetry analysis, feature usage reporting, or requirements-capability mapping in a small application.

---

### Core Competencies
The basic exam will test that a candidate can:
- Perform data ingestion from plain text (CSV/JSON) into a persistent store (SQLite or local structured files).
- Design a minimal, sensible schema or structured storage for the dataset.
- Write correct, parameterized queries or programmatic filters to retrieve required information.
- Implement common data manipulations: filtering, joins (if multiple tables), derived fields, grouping/aggregation, and simple transformations (normalization, type casting, handling missing data).
- Produce a reproducible artifact (test_submission.json) containing required results and short justifications.
- Write clear, runnable code (single script) that creates the outputs without external network access or non-standard libraries.

---

### Recommended Structure
Total allowed time: 90 minutes.

Overall organization: 4 small, ordered tasks that form a pipeline (ingest → store → retrieve/transform → report). Each task has explicit deliverables and expected JSON fields in test_submission.json. Candidate should provide:
- One runnable script (name recommended: run_exam.py or run_exam.<ext>) that, when run, produces test_submission.json.
- The produced file test_submission.json (primary artifact for grading).
- (Optional but recommended) small README.txt with the single run command and language/runtime used.

Tasks and recommended time allotment:
1. Task 1 — Ingest & Store (20 minutes)
   - Deliverable: a database file (or local data files) created by the script and an entry in test_submission.json with the schema definition and row counts.
   - Action: parse the provided dataset (simple CSV or JSON provided inline in the exam prompt), create tables/files, insert data, and report the number of rows per table.

2. Task 2 — Retrieve & Query (25 minutes)
   - Deliverable: SQL queries or code snippets used and the numeric answers to 3–4 factual questions (e.g., total records, top N users by events, count by category).
   - Action: Write and run queries/filters that answer the given questions. Include results in test_submission.json in specified keys.

3. Task 3 — Manipulate & Transform (25 minutes)
   - Deliverable: a set of transformations producing derived columns and at least one joined/aggregated result (e.g., hourly counts, rate calculations). Output the transformed sample (first N rows) and the aggregate numbers in test_submission.json.
   - Action: Implement required transformations (handle missing values, cast types, compute derived fields like duration, normalized names) and produce aggregated metrics.

4. Task 4 — Report & Justify (20 minutes)
   - Deliverable: produce a small JSON report (key metrics) and 1–3 short textual justifications (1–2 sentences each) about schema choice and one data-handling decision (e.g., how missing values were treated).
   - Action: Export a final summary JSON object with specified keys and provide brief reasoning entries.

Note: The tasks are cumulative — output of Task 1 is used in Tasks 2–4.

- Parameterized queries or prepared statements if using SQL (demonstrates safe query practice).
- A small decision point: require the candidate to pick one simple schema normalization (e.g., extract a “user” table from events) or keep a denormalized table and justify the choice in 1–2 sentences.

### Strategic Elements (decision points that separate conceptual from practical capability)
Use multi-step processes and dependencies so candidates must execute a pipeline:
- Data dependencies: Task 2 and Task 3 must use the persistent store created in Task 1. Mistakes in ingestion will cascade and be visible — a practical test of end-to-end handling.
- Validation step: require explicit detection and handling of at least one data anomaly (e.g., missing timestamp rows must be dropped or imputed — candidate chooses and notes why).
- Schema decision: require a short choice between (A) normalizing user info into separate table or (B) keeping a single denormalized events table. Candidate must pick one and provide a 1–2 sentence justification. This reveals practical trade-off understanding.
- Reproducibility / run script: requiring a single command to generate the JSON output forces candidates to write runnable code rather than only theoretical answers.
- Minimal performance awareness: ask candidate to create an index on a column used by frequent queries (e.g., timestamp, user_id) and report whether the index exists (simple, but shows awareness).

These elements reveal who can actually do the work (connect the steps, debug, and produce repeatable outputs).

How the materials were constructed and why
- Two small CSV files are provided: events.csv (15 data rows including one exact duplicate row) and users.csv (6 users). This size keeps the whole exam doable within 90 minutes while still requiring schema design, cleaning, joins, and aggregation.
- The events.csv intentionally includes several "dirty" elements to force real ingestion decisions:
  - One exact duplicate row: the row with event_id E3 appears twice (identical row). Candidate must deduplicate.
  - One missing timestamp: event_id E5 has an empty timestamp field.
  - One malformed timestamp: event_id E8 has timestamp value "not_a_timestamp".
  - Inconsistent event_type casing and extra whitespace: values like "Click", " click ", "CLICK ", "PURCHASE", and "View".
  - Numeric values are represented as strings in quotes for some rows (e.g., "10", "100") and as plain numbers in others; candidate must cast to numeric type.
- users.csv includes one user (U6) with no events (to test handling of zero-count users) and one user (U5) missing signup_date. Plans are "free", "pro", "enterprise". All user_ids used by events (U1..U5) exist in users.csv; U6 is present only in users.csv.

Key patterns / relationships for the evaluator to expect
- After basic cleaning steps a typical deterministic pipeline would:
  1. Remove exact duplicate rows (dedupe full-row equality) — removes the duplicate E3 row.
  2. Handle missing/malformed timestamps by either dropping those rows or imputing timestamps (the candidate must choose and state which). The problematic rows are:
     - E5 (missing timestamp)
     - E8 (malformed timestamp "not_a_timestamp")
  3. Normalize event_type by trimming whitespace and lowercasing (e.g., " Click" -> "click", "PURCHASE" -> "purchase").
  4. Cast value column to numeric (integer).
  5. Parse timestamps into a consistent ISO-8601 form; if timezone absent (e.g., "2021-07-01 09:15:00"), the candidate may treat it as UTC and convert to "2021-07-01T09:15:00Z".
  6. Create an index on a frequently queried column such as user_id or timestamp (if using SQLite). The candidate should report whether the index was created.

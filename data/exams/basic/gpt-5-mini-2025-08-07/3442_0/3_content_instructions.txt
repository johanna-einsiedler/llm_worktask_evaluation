### Exam Title
Practical Data Ingestion, Querying, Transformation, and Analysis (Basic level)

### Instructions for Candidate

You have 90 minutes to complete this practical exam. Work locally using only the tools available on your machine (a code execution environment and a text editor). Common acceptable tools: sqlite3 and/or Python 3. You may choose the method you prefer (direct CSV -> SQLite import, or a short Python ingestion script), but you must justify that choice in your submission.

Follow these sequential tasks and deliverables exactly. Package everything into a single JSON file named test_submission.json (submission details below).

Overall time budget (suggested; you must report actual minutes spent for each step in your submission):
- Step 1 — Setup & Data Import: 25 minutes
- Step 2 — Core Retrieval Queries: 30 minutes
- Step 3 — Data Transformation & Export: 20 minutes
- Step 4 — Summary & Interpretation: 15 minutes
Total allowed time: 90 minutes

Step 1 — Setup & Data Import (deliverable #1)
- Create a minimal data model appropriate for the provided CSV and implement ingestion into a local store (SQLite database or in-memory via script).
- Deliverables for this step (include in the JSON):
  - The SQL CREATE TABLE statement(s), or the short ingestion script you ran (paste the code).
  - Exact commands you ran to create/import (so an evaluator can re-run them).
  - A concise report of row counts: total rows in the CSV, rows successfully loaded, and rows dropped/modified due to malformed data.
  - One-line justification of your ingestion method choice (script vs direct SQLite import).
  - One short sentence describing any data-cleaning decisions you made for malformed or missing values (drop, impute, or treat as zero).

Step 2 — Core Retrieval Queries (deliverable #2)
- Answer the analytical questions (below) by writing and running SQL queries (or equivalent code that operates on the loaded store).
- Provide 4–6 queries that demonstrate SELECT, WHERE, GROUP BY, ORDER BY, aggregate functions (COUNT, SUM, AVG), and at least one join or derived column.
- For each query include (in the JSON):
  - The exact SQL (or script) text run.
  - The exact command line used to run it.
  - The result set produced (as a JSON array of row objects). If a query returns >200 rows, include only the top 200 rows plus the full row count.
  - A one-sentence explanation of what the result shows.
- The required analytical questions to answer:
  1. Count events per day and report the days with more than N events. (Use N = 50.)
  2. Find the top 5 components by average metric_value (descending), excluding rows with invalid or missing metric_value.
  3. Compute error rate per component: fraction of events with status_code >= 500 divided by total events for that component. Sort descending and show components with at least 5 events.
  4. For each component, compute average metric_value for successful events (status_code in 200..299) vs error events (status_code >= 500). Present component_id, avg_success, avg_error (use NULL where no events in a category).
  5. (One join) If a components lookup table is provided with component_id and human-readable name, join it to produce the top-5 components (by avg metric_value) with human-readable names. If no lookup is provided, you may create one inline with at least three minimal mappings and note this in assumptions.
- Note: later steps may rely on transformations you perform here (for example, normalized timestamps). Ensure any such transformations are recorded in Step 1 and used consistently.

Step 3 — Data Transformation & Export (deliverable #3)
- Create one derived, analysis-ready dataset and export it (CSV or JSON). Examples: normalize timestamps to UTC date, bucket metric_value into categories, compute rates per-minute, or compute per-component daily aggregates.
- Deliverables (include in JSON):
  - The script/SQL used to create the transformed dataset.
  - The exact command(s) used to produce an export file (you may paste the exported contents into JSON; include full export if ≤200 rows, otherwise include a sample plus the total row count).
  - A 1–2 sentence explanation of why the transformation is useful for downstream analysis.
- The transformation must explicitly handle malformed or missing values (describe how you handled them).

Step 4 — Summary & Interpretation (deliverable #4)
- Provide concise key findings and 2–3 actionable recommendations based on the data and queries.
- Include short assumptions you made (timestamps timezone, meaning of status codes, rows dropped, synthetic lookup mappings, etc.)
- Report actual time spent (minutes) on each step and total time.

Mandatory reproducibility elements (every step)
- Include the exact commands to reproduce DB creation, ingestion, query execution, and export. These must be re-runnable given the original CSV file.
- Paste the code/scripts used as text (not as attachments).
- If you chose a scripting approach, paste the entire script (keep it concise).

Edge-case requirements
- The provided CSV contains some malformed rows (e.g., empty metric_value or malformed timestamp). You must explicitly state how many rows were affected and how you handled them.
- You must include a one-line justification for the ingestion approach chosen (SQLite import vs Python script).

Time management and constraints
- You may trim query output in the JSON if the full result exceeds 200 rows—include top rows and the full row count.
- Keep any single code or SQL string in the JSON reasonably short. If a script is long, include only the script file content (still paste complete script).

### Expected Outcome

By the end of the test you must produce one file named test_submission.json that contains:
- Candidate contact and environment info.
- Total time spent and per-step time reports.
- For each step (Setup & Import, Core Queries, Transformation & Export, Summary), the code, commands, outputs, brief explanations, and any export contents (or samples).
- Query outputs for the five analytical questions above (as JSON arrays).
- The exported transformed dataset (full if ≤200 rows; otherwise a sample plus count).
- A concise summary of findings, recommendations, and any assumptions.
- A one-line ingestion-method justification.

Your submission must be self-contained: an evaluator should be able to run the listed commands (given the same CSV provided with the exam) and reproduce your reported outputs.

### Provided Materials

You will be given one CSV file named system_events.csv (50–300 rows) with the following columns:
- id (string/integer)
- timestamp (ISO-8601 string; a few rows have malformed timestamps)
- component_id (string)
- metric_value (numeric; a few rows empty or non-numeric)
- status_code (integer)
- message (optional text)

Notes:
- The CSV includes a small number (1–5) of malformed or missing metric_value rows and 1–3 malformed timestamp rows to force cleaning decisions.
- A lookup CSV components_lookup.csv may or may not be provided. If it is provided, it contains component_id and name. If it is not, follow the Step 2 instruction to create a minimal mapping if needed.

Allowed tools
- Any language or tool available locally on your machine. Typical choices: sqlite3 command-line, Python 3 (standard library), bash. Internet access is disabled — do not attempt to download packages.

### Submission Format

You must submit a single file named test_submission.json (UTF-8 plain text). This will be the only file evaluated. Follow this required JSON schema exactly (fields must be present; empty optional fields are allowed but will be noted by evaluators):

Top-level keys:
- candidate: { name: string, email: string, language_used: string, environment: string }
- time_spent_minutes: integer (total)
- steps: array of step objects (order: Setup & Import, Core Queries, Transformation & Export, Summary)
- summary: { key_findings: [string...], recommendations: [string...], assumptions: [string...] }
- reproducibility: { commands: [string...], files_created: [string...] }
- justification: { ingestion_choice: string }  // One-line reason for ingestion method

Each step object must contain:
- name: string (one of the four step names above)
- time_spent_minutes: integer
- artifacts: {
    code: string,               // SQL or script text used (paste actual code)
    commands: [string...],      // exact commands run
    outputs: object,            // JSON-serializable: e.g., {"rows_inserted":120} or {"query_1":[{...},...] }
    short_explanation: string   // 1–3 sentences
  }

Specific expectations for Core Queries step:
- artifacts.outputs must include keys: query_1, query_2, query_3, query_4, query_5 corresponding to the five analytical questions; each should be an array of row objects (or a sample + count as described above).

Constraints and evaluator convenience:
- If an output >200 rows, include only top 200 rows and add a field rows_total with the full count.
- Keep code strings reasonably short. If a script exceeds 2,000 characters, it is acceptable but include a brief note in the step.artifacts.short_explanation pointing to where the evaluator should copy/paste it.
- All SQL or code must be plain text in the JSON (no attachments).
- You must include the exact commands necessary to (re)create the DB and run queries (for example: sqlite3 data.db < create.sql; sqlite3 data.db "SELECT ..." ; python3 ingest.py; etc.).

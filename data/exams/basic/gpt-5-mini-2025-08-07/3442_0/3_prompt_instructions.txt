Here is the exam overview written by another exam designer:
<examoverview>
### Exam Purpose
Confirm that a candidate can practically store, retrieve, and manipulate data to support simple analysis of system capabilities and requirements in a realistic engineering context. The exam validates that the candidate can:

- Design a minimal data model for a small dataset.
- Ingest raw data into a local store.
- Write correct queries to retrieve and aggregate data to answer practical questions.
- Transform and export results for downstream analysis.
- Produce reproducible, runnable artifacts (scripts/SQL) and a brief interpretation of results.

This demonstrates the real-world capability to turn raw telemetry or simple system logs into structured information useful for requirements analysis, capacity planning, or feature validation.

---

### Core Competencies to be Tested
- Data modelling: choosing tables/fields and types appropriate for the task.
- Data ingestion: importing CSV/text into a local datastore (SQLite or plain CSV processing).
- Querying: writing selection, filtering, grouping/aggregation, and simple joins.
- Data transformation: derived columns, handling of missing/invalid values, simple normalization.
- Exporting and reproducibility: producing exportable results (CSV/JSON) and supplying runnable scripts.
- Communication: concise explanation of steps, assumptions, and actionable conclusions.
- Basic code hygiene: runnable scripts, modular SQL, and clear comments.

---

### Recommended Structure
Time budget: maximum 90 minutes total.

Overall organization — 4 sequential tasks (deliverables packaged into one JSON file named test_submission.json):

1. Setup & Data Import (25 minutes)
   - Deliverable:
     - SQL CREATE TABLE statement(s) or a short ingestion script.
     - Confirmation that data was loaded (row counts) and any data-cleaning actions.
   - Goal: Candidate creates an appropriate schema and loads the provided CSV dataset into a local SQLite database (or ingests into memory via a script).

2. Core Retrieval Queries (30 minutes)
   - Deliverable:
     - 4–6 SQL queries (or equivalent code) that answer specific analytical questions supplied in the prompt (examples below).
     - Each query should include the SQL code, the resulting output (as JSON array of rows), and a one-sentence explanation of what the result shows.
   - Goal: Test basic SELECT, WHERE, GROUP BY, ORDER BY, aggregates (COUNT, SUM, AVG), and one join or derived column.

3. Data Transformation & Export (20 minutes)
   - Deliverable:
     - A short script or SQL statement that performs a simple transformation (e.g., normalize a field, bucket a metric, compute rates), exports the derived dataset (CSV or JSON contents included in the JSON submission), and explains why the transform is useful for analysis.
   - Goal: Verify the candidate can create analysis-ready data and output it in a standard format.

4. Summary & Interpretation (15 minutes)
   - Deliverable:
     - A short conclusions section (3–6 bullet points) describing the key findings from the queries and any recommendations or assumptions.
     - Self-report of time spent per step.
   - Goal: Validate the candidate’s ability to interpret the data and communicate conclusions succinctly.

Total recommended tasks: 4. The exam creator should provide a single input data file (CSV) with ~50–300 rows and 6–10 columns (include timestamps, categorical fields, numeric metrics), and 3–4 analytical questions to be answered by queries.

---

### Practicality — Ensuring Hands-on Assessment
- Provide a single CSV file (attached to the exam) that must be imported. Do not allow internet access; candidate must do all work locally.
- Allow use of any language/tool available locally (common expectation: sqlite3 command-line + Python or a language of choice).
- Require runnable artifacts (SQL scripts or a small script) and their outputs included verbatim in test_submission.json so evaluators can reproduce results without additional files.
- Make the tasks data-driven: answers must be produced by running queries against the provided dataset (not describing how they would do it).

Example analytical questions (basic-level):
- "Count events per day and report days with more than N events."
- "Find top 5 components by average response time."
- "Compute error rate (errors / total) per component and sort descending."
- "Join the events data with a provided 'components' lookup to report human-readable names."

These are simple, realistic operations that require actual execution.

---

### Strategic Elements (to distinguish practical ability)
Include elements that force candidates to implement steps rather than only explain them:
- Data dependency: later queries rely on an earlier transformation (e.g., must normalize timestamps to UTC in Step 1 so Step 2 grouping by day is correct).
- Edge-case handling: dataset contains a few rows with missing/invalid values in a metric column. Candidate must explicitly clean/handle those rows and explain choices (drop, impute, or treat as zero).
- Decision point: allow candidate to pick between two ingestion methods (direct CSV into SQLite or processing via a script) but require a one-sentence justification in the submission for the chosen method. This separates conceptual knowledge (knowing options) from ability to execute and justify a practical choice.
- Reproducibility requirement: candidate must include exact commands to recreate the DB (or to run the script). This demonstrates they can produce runnable deliverables.

These elements ensure candidates who only conceptually understand workflows will fail to provide runnable, correct outputs.

---

### Evaluation Insights (what to look for and scoring)
Scoring total: 100 points. Passing threshold: 80 points (basic exam target).

Suggested rubric (weights & observable artifacts):

1. Setup & Data Import — 20 points
   - Schema is appropriate and justified (8 pts).
   - Data successfully ingested; row counts match expectations; handling of obvious malformed rows (7 pts).
   - Submission includes runnable commands/scripts to reproduce import (5 pts).

2. Core Retrieval Queries — 40 points
   - Correctness of query results relative to dataset and question (each query scored) (25 pts).
   - SQL style/readability and comments (5 pts).
   - Result outputs included in JSON and match what the SQL would return (10 pts).

3. Data Transformation & Export — 20 points
   - Transformation is correct and useful (10 pts).
   - Exported results included and are in proper format (CSV/JSON) (5 pts).
   - Explanation of why transformation was necessary/useful (5 pts).

4. Summary & Interpretation — 10 points
   - Clear, accurate, concise conclusions and recommendations (7 pts).
   - Time log + explanation of choices and edge-case handling (3 pts).

5. Reproducibility & Packaging — 10 points
   - test_submission.json present, properly structured and complete; code snippets included verbatim (5 pts).
   - Commands/steps are sufficient for an evaluator to rerun everything in <= 10 minutes (5 pts).

Observables that indicate competence:
- Submissions include SQL and/or script text that runs without modification on the provided dataset.
- Query outputs in the JSON match executing the submitted SQL or script.
- Candidate handled dirty data explicitly and justified the approach concisely.
- Clear, actionable interpretation of results (not just restating numbers).

Automated evaluation suggestions:
- Evaluator can write a small harness to:
  - Load candidate SQL/script from JSON.
  - Run ingestion script and compare resulting table counts.
  - Execute listed queries and compare actual output to the candidate's reported output in JSON.
  - Check that exported data (embedded in JSON) matches what the script/queries would produce.

### Deliverable format: test_submission.json (required)
To simplify evaluation, candidates must submit a single JSON file named test_submission.json. This file should be UTF-8 plain text and follow this required schema (fields described below must be present; empty optional fields allowed but flagged):

Required top-level keys:
- candidate: { name: string, email: string, language_used: string, environment: string (e.g., "sqlite3 + python3.9") }
- time_spent_minutes: integer (total)
- steps: array of step objects in sequence (see below)
- summary: { key_findings: [string...], recommendations: [string...], assumptions: [string...] }
- reproducibility: { commands: [string...], files_created: [string...] }
- justification: { ingestion_choice: string }  // One-line reason for method chosen

Each step object (in steps array) must include:
- name: string (e.g., "Setup & Import")
- time_spent_minutes: integer
- artifacts: object containing:
  - code: string (SQL or script text used; include comments)
  - commands: [string...] (commands used to run code)
  - outputs: JSON-serializable object (e.g., { "rows_inserted": 250 } or { "query_results": [ {col1: val, ...}, ... ] })
  - short_explanation: string (1–3 sentences)

Example minimal skeleton (content should be filled by candidate):

{
  "candidate": { "name":"", "email":"", "language_used":"python3", "environment":"sqlite3, python3.9" },
  "time_spent_minutes": 85,
  "steps": [
    {
      "name":"Setup & Import",
      "time_spent_minutes": 20,
      "artifacts": {
        "code": "CREATE TABLE events (...); -- SQL",
        "commands": ["sqlite3 data.db < create.sql", "sqlite3 data.db .tables"],
        "outputs": { "rows_inserted": 120 },
        "short_explanation":"Created events table and imported CSV; dropped 2 malformed rows."
      }
    },
    {
      "name":"Core Queries",
      "time_spent_minutes": 35,
      "artifacts": {
        "code": "SELECT day, COUNT(*) as cnt FROM events GROUP BY day HAVING cnt > 50;",
        "commands": ["sqlite3 data.db \"SELECT ...\""],
        "outputs": { "query_1":[ {"day":"2025-01-01","cnt":72}, ... ], "query_2":[ ... ] },
        "short_explanation":"Query 1 shows days with heavy load; Query 2 shows error rates per component."
      }
    },
    {
      "name":"Transformation & Export",
      "time_spent_minutes": 20,
      "artifacts": {
        "code": "python3 transform.py  # included below",
        "commands": ["python3 transform.py > transformed.json"],
        "outputs": { "export_rows": 120, "export_sample": [ {"component":"A","error_rate":0.04}, ... ] },
        "short_explanation":"Computed error rates and exported JSON for downstream analysis."
      }
    }
  ],
  "summary": {
    "key_findings": ["Component X has the highest average response time (450ms)","Error rate spikes on 2025-01-10"],
    "recommendations": ["Investigate component X", "Add monitoring on endpoint Y"],
    "assumptions": ["Timestamps in dataset are in UTC", "Rows with missing response_time were dropped"]
  },
  "reproducibility": {
    "commands": ["sqlite3 data.db < create.sql", "python3 queries.py"],
    "files_created": ["data.db","transformed.json"]
  },
  "justification": { "ingestion_choice":"Used sqlite import for quick SQL querying and reproducibility" }
}

Notes for evaluators:
- Require that the code strings be short (<= 2,000 characters each) and queries return at most 200 rows for inclusion (candidate can trim output or include only the top results). For larger exports, allow embedding a small sample and row count.
- If candidate used a scripting language, they must paste the script as text in the appropriate step artifact.

---

### Practical Elements to Include (quick checklist for exam creator)
- Attach a CSV dataset (50–300 rows) with:
  - at least: id, timestamp, component_id, metric_value, status_code, optional message.
  - a small number of malformed rows (e.g., empty metric_value, malformed timestamp) to force cleaning.
- Provide 3–4 analytical questions to be answered by queries (listed in the exam prompt).
- State allowed tools (sqlite3, python3, bash) and that internet access is disabled.
- Provide an example test_submission.json skeleton in the prompt.
- Timebox to 90 minutes and ask candidate to report minutes used per step.

---

This structure ensures the exam is hands-on (candidate must run code and produce outputs), practical (uses realistic dataset and questions), reproducible, and assessable by automated or manual graders. It keeps complexity appropriate for an entry-level Software Developers, Applications role while allowing clear separation between candidates who understand the workflow conceptually and those who can actually perform it.

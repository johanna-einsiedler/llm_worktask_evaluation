Here is the exam overview written by another exam designer:
<examoverview>
### Exam Purpose
Confirm that the candidate can practically modify an existing application to (1) diagnose and correct defects, (2) adapt the code/configuration to a changed runtime environment (a simple "new hardware" or platform constraint), and (3) make a small, measurable performance improvement — all within a real codebase and using normal developer tools (editor + execution environment). This verifies the candidate’s hands-on ability to maintain and evolve software rather than only their conceptual knowledge.

### Core Competencies to be Tested
- Debugging / root-cause analysis: reproduce a failing behavior, find the source, and apply a minimal, correct fix.
- Code modification and testing: make edits, run provided tests, produce reproducible test output.
- Environment adaptation: update code/configuration so the application runs under a changed runtime constraint (for example: different I/O semantics, reduced buffer size, simple API change).
- Basic performance reasoning and measurement: run a simple benchmark, propose and implement one safe optimization, and demonstrate measurable improvement.
- Communication and traceability: produce clear, concise explanation of changes, include a patch/diff, and provide run instructions.
- Minimal code hygiene: readable changes, appropriate variable names, brief inline comments if needed, and a small unit test or a test update when applicable.

### Recommended Structure (Basic exam — single 90-minute session, target completion <= 90 minutes)
Total time budget: 90 minutes (exam materials should explicitly recommend this split to candidates).

Number of practical tasks: 3 small, sequential hands-on tasks in one repository:
1. Task A — Bug Fix (40 minutes)
2. Task B — Environment Adaptation (20 minutes)
3. Task C — Small Performance Improvement + short explanation (25 minutes)

Reserve 5 minutes buffer for packaging submission.

Expected deliverables (candidate uploads in test_submission.json and as files in the repo if the platform permits):
- test_submission.json (required): structured answers and metadata (see template below).
- Patches/diffs or modified source files (either included as a unified diff string field inside test_submission.json or saved in the repo). If diffs are not possible, include full updated source file(s) contents.
- Test run outputs and/or benchmark outputs captured as plain text strings inside test_submission.json.
- A brief explanation (1–3 short paragraphs) per task describing approach, root cause, and trade-offs.

High-level flow:
- Candidate clones repo (provided by exam admin) containing a small Python application (or language chosen by the exam designer), a failing test or reproducible bug, an adaptation requirement, and a benchmark script.
- Candidate runs provided test runner and benchmark harness, makes code edits, re-runs tests/benchmarks, and records results.
- Candidate packages results into test_submission.json.

Why these tasks and sequence?
- Sequential dependency: Task A ensures the candidate can reproduce and fix failures — necessary baseline. Task B tests ability to reason about runtime differences and make configuration/code changes. Task C tests the candidate’s capability to measure and safely optimize code.
- The sequence mirrors common real-world maintenance tasks.

### Practical Elements to Include (how to make it hands-on)
- Self-contained repo with:
  - Small but realistic code base (approx. 150–400 LOC across a few files) implementing a simple utility or microservice functionality (e.g., data processing, simple cache, file-transformer).
  - A test runner script (e.g., run_tests.py) that prints PASS/FAIL and shows failing traces for Task A. Must run without external packages.
  - A small benchmarking script (e.g., bench.py) that performs repeated work and prints timings. Provide deterministic input to make improvements measurable.
  - Clear README with commands for running tests and bench.
- No internet access for candidates; ensure code has no external dependencies.
- Provide a failing test case and a reproducible failing run; candidate must correct the code to pass it.
- For environment adaptation, simulate a hardware/platform change that requires code change (examples below).
- Make performance improvement modest but measurable (e.g., reduce median runtime by 20–40% on the supplied benchmark through algorithmic or micro-optimization like avoiding repeated computation, caching, or using more efficient data structures).
- Require submission of:
  - the modified file(s) or unified diff,
  - outputs (console logs) of test runner before and after fixes (they can paste the before/after logs),
  - benchmark numbers before and after the optimization,
  - a short explanation of the thought process and verification steps,
  - one-line summary of potential side-effects or risk areas from the change.

Examples of environment-adaptation scenarios (choose one for the exam):
- New hardware has less available memory: require processing to be streaming-based instead of in-memory for one operation (the basic exam should use a tiny, trivial streaming adaptation like switching from list-based accumulation to incremental write).
- I/O change: previously the code read from local files; now it must accept data from stdin (or a given file descriptor). Candidate must add an alternate code path.
- Constrained API: a helper function's parameter signature changes (e.g., callback signature) and candidate must adapt the wrapper code to the new signature.

Practical scoring safeguards
- Include an automated acceptance test runner that prints explicit results. Evaluators can reproduce candidate’s claims by applying the candidate patch and running the same runner.

### Strategic Elements (steps/decision points that distinguish real ability)
- Reproducibility step: candidate must run tests and paste failing logs — distinguishes someone who actually ran code vs. someone who only conceptualized fixes.
- Minimal, targeted changes: evaluate whether candidate modifies only necessary lines vs. sweeping unrelated edits. Good candidates produce minimal diffs.
- Root-cause explanation: require candidate to describe the bug's cause in one or two sentences. This checks diagnosis ability, not guesswork.
- Trade-off decision for performance: the candidate must pick a safe optimization and explain trade-offs (memory vs. speed, complexity, maintainability). This shows practical judgment.
- Evidence-based optimization: candidate must capture before/after benchmark numbers. Candidates who "optimize" without measurement cannot score well.
- Add/adjust a small unit test if appropriate: if the bug was not covered, writing a short test demonstrates competence.
- Edge-case handling: ask the candidate to note one edge case that remains untested or a risk that would require further work.

These elements force a candidate to actually run/debug/measure, not just describe.

### Test Submission JSON Schema (test_submission.json)
Require test_submission.json with these fields. All fields must be plain strings or numbers and small arrays, so it is easy to validate automatically.

{
  "candidate_name": "<Full name>",
  "time_taken_minutes": <number>,
  "task_results": [
    {
      "task_id": "A-bugfix",
      "status": "fixed" | "not_fixed" | "partial",
      "files_modified": ["src/file1.py", "src/file2.py"],
      "patch_unified_diff": "<string containing unified diff or 'N/A' if whole file provided>",
      "pre_fix_test_output": "<exact console output from running run_tests.py before edits>",
      "post_fix_test_output": "<exact console output from running run_tests.py after edits>",
      "explanation": "<1–3 short paragraphs: root cause, why fix works, why minimal>",
      "unit_tests_added_or_modified": ["tests/test_bugcase.py"] or [],
      "self_assessed_confidence": "<1-5>"
    },
    {
      "task_id": "B-adapt_env",
      "status": "adapted" | "not_adapted" | "partial",
      "files_modified": ["src/io_adapter.py"],
      "patch_unified_diff": "<string>",
      "run_output_after_adaptation": "<console output showing app running in new mode>",
      "explanation": "<what changed in environment, what you changed in code, why safe>",
      "risks_or_limitations": "<short note about residual issues>"
    },
    {
      "task_id": "C-performance",
      "status": "improved" | "no_change" | "regressed",
      "files_modified": ["src/processor.py"],
      "patch_unified_diff": "<string>",
      "benchmark_before_ms": <number>,
      "benchmark_after_ms": <number>,
      "bench_command_run": "<command used to run bench>",
      "explanation": "<brief explanation of what was optimized and trade-offs>"
    }
  ],
  "other_notes": "<optional: anything else the candidate wants to state>"
}

Notes for candidate instructions:
- Paste exact console outputs including any stack traces or timing lines.
- If multiple files are changed, include all in the files_modified list and include a single unified diff string (git format) or the new file contents labeled with file path headers.
- Provide exact commands used to run tests and benchmarks.

### Evaluation Insights (observable outputs and scoring guidance)
Overall scoring: total 100 points. Entry-level threshold: 80+ points to pass the basic exam.

Suggested weighting
- Task A — Bug Fix (50 points)
  - Reproduces failure and shows pre-fix failing output (5 points)
  - Fix correctness: all provided tests pass after fix (30 points)
  - Minimal and appropriate patch (10 points)
  - Clear root-cause explanation (5 points)

- Task B — Environment Adaptation (20 points)
  - Adapts code/config to run in the new environment and demonstrates run output (12 points)
  - Explains the changes and notes residual risks (8 points)

- Task C — Performance (20 points)
  - Measures and reports before/after benchmark numbers (8 points)
  - Demonstrates meaningful improvement (e.g., >=15–20% speedup on benchmark) (8 points)
  - Explanation of optimization and trade-offs (4 points)

- Communication & Packaging (10 points)
  - Proper test_submission.json format (3 points)
  - Patch/diff clarity and ability to reproduce (4 points)
  - Concise, clear run instructions and logs (3 points)

Grading thresholds and indicators of competence:
- Must pass Task A tests to be considered competent (fail = automatic major penalty). An entry-level candidate should be able to fully pass Task A for >60% of available points.
- Task B should be fully correct for at least an 80% pass in the basic exam: a single, simple adaptation is expected.
- Task C: small improvement is required; if there is no measurable improvement but the candidate shows correct methodology and explains why no safe improvement exists, partial credit applies.
- Minimal invasive edits: awarding more points if the diff is concise and well-scoped. Large unrelated edits reduce points.
- Evidence of proper verification: providing pre/post logs and benchmark numbers is mandatory — absence loses most of the associated points.

Sample automatic checks an evaluator can run:
- Apply the candidate’s patch; run ./run_tests.py and check for PASS markers.
- Run the benchmark with provided command(s) and compare the reported ms to the claimed numbers in JSON.
- Verify that the modified files listed actually match the provided diffs or contents.

Examples of “red flags”
- Candidate gives only abstract descriptions without logs or diffs.
- Candidate removes failing tests instead of fixing code.
- Patch introduces new failing tests or regressions.
- No measurement supplied for performance task or obviously unstable benchmarking (no repeated runs).

### Final notes for exam creators and evaluators
- Use Python 3 for maximum accessibility; ensure no third-party dependencies.
- Make the repo small and deterministic. Provide clear reproducible commands.
- Keep task complexity modest so an entry-level developer can finish in ~70–80 minutes, leaving buffer for packaging.
- Provide a sample solution and expected outputs for evaluators to speed grading and to set pass thresholds.

This design gives exam creators a reproducible, hands-on basic practical test that reliably separates candidates who can perform real maintenance and adaptation tasks from those who only understand them conceptually.

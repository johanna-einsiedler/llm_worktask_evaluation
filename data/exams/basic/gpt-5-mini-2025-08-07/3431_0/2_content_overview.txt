### Exam Purpose
To confirm that a candidate can practically modify an existing application to (a) find and correct defects, (b) adapt code to run correctly on constrained or different hardware environments, and (c) improve the runtime/memory performance of code. This exam demonstrates hands‑on ability to read an unfamiliar small codebase, implement correct fixes, make pragmatic architectural changes to cope with hardware constraints, and apply straightforward performance optimizations — all under time pressure as in real maintenance tasks.

### Core Competencies to be Tested
- Reading and understanding a small existing codebase and its tests.
- Debugging and fixing functional defects so that provided tests pass.
- Making safe changes that preserve correctness (regression-aware modification).
- Adapting code to resource-constrained hardware (e.g., low memory, single CPU).
- Identifying and implementing targeted performance improvements (algorithmic or I/O changes).
- Producing clear, concise evidence of what was changed and why (commit/diff + short explanation).
- Basic code hygiene: readable code, small tests or assertions, no breaking of other features.

### Recommended Structure
- Total time: 90 minutes (strict).
- Number of tasks: 3 hands-on tasks, executed in sequence on a provided small codebase.
  - Task A — Bug Fix (35 minutes)
  - Task B — Hardware Adaptation (25 minutes)
  - Task C — Performance Improvement (25 minutes)
  - 5 minutes reserved at the end for preparing the JSON submission file
- Deliverables:
  - Modified source files (in-place in the provided repo).
  - A single JSON file named test_submission.json (see required schema below).
  - Optionally a small unified diff file (if the environment supports saving diffs).
  - All tasks must include the command output evidence that proves correctness (unit test output, benchmark output, memory checkpoints, etc.) embedded in the JSON.

Sequence:
1. Candidate unpacks the exam package (contains codebase, tests, instructions).
2. Run the supplied test and benchmark scripts to observe failing tests and baseline performance.
3. Fix the defect(s) in Task A and re-run tests.
4. Implement the hardware adaptation for Task B and re-run the adapted tests/validation script.
5. Implement the performance changes for Task C and run the performance check.
6. Populate test_submission.json with required structured information and paste outputs.

Notes for exam pack author:
- Provide a small single-language project (recommended: Python 3). Python is easy to run in most environments and requires minimal setup.
- Provide a script run_all.sh (or run_all.py) that runs unit tests and the simple benchmarks; candidate will run that repeatedly.
- Avoid any external network dependencies; use only the standard library.

### Practicality — How to make it hands-on
- Provide a runnable repository (zipped) including:
  - src/ small program (200–300 lines total max) implementing a realistic tiny feature (e.g., CSV aggregator, log parser, or text indexer).
  - tests/ unit tests or simple assertion scripts (some passing, at least one failing).
  - scripts/ run_tests.sh, benchmark.sh or run_all.py that print clear pass/fail and baseline runtime/memory numbers.
  - data/ a medium sized input file (a few MB) to permit measurable performance differences.
- The tasks require direct code edits to pass tests and meet runtime/memory targets. No theoretical answers — all proof must come from running scripts and including their outputs.

Concrete examples of hands-on elements (to include in the package):
- A failing unit test that exercises a bug in parsing or numeric edge case.
- A program that currently reads an entire data file into memory (Task B asks to adapt it to stream processing).
- A function implemented with an O(n^2) approach on the dataset; Task C asks to reduce complexity (e.g., use a dictionary/hash map) so that the included benchmark shows improvement.

### Strategic elements (decision points and multi-step processes)
Design tasks so candidates must make and justify small trade-offs:
- Task A: Candidate must identify the root cause (not just patch). Provide multiple plausible but incorrect quick fixes to trap candidates who do not run tests after changes.
- Task B: Provide an adaptation scenario (e.g., “target hardware has <= 128MB RAM or no floating-point unit”) and require the candidate to modify code to still produce correct output under these constraints. Candidate decisions:
  - Stream the data rather than loading whole file.
  - Provide fallback code path when multiprocessing is not available (use sequential mode).
  - Replace float-heavy calculations with integer math if the dataset is integer-compatible.
- Task C: Candidate must select one focused optimization strategy (algorithmic, data structure, or I/O) and implement it. Decision points:
  - Improve asymptotic complexity vs microoptimizations — the exam should favor asymptotic changes where feasible.
  - Verify changes with supplied benchmark and include before/after measurements in JSON.

These decision points separate candidates who can perform hands-on maintenance from those who only know theory: good candidates will run tests/benchmarks, iterate, and explain trade-offs succinctly.

### Evaluation insights — what to look for and how to score
Structure scoring across three tasks; total 100 points. Passing threshold for the basic exam: 80 points or more.

Suggested point allocation:
- Task A — Bug Fix: 35 points
  - Correctness (unit tests pass) — 25 points
  - Quality of fix (minimal, non-regressive, clear) — 5 points
  - Explanation in JSON (root cause and what changed) — 5 points
- Task B — Hardware Adaptation: 30 points
  - Adaptation correctness (behavior preserved on streaming / fallback) — 15 points
  - Evidence (show that the new mode runs on a simulated constrained setting or with reduced memory; e.g., benchmark script that checks memory) — 10 points
  - Explanation of trade-offs and instructions on how to run adapted mode — 5 points
- Task C — Performance Improvement: 35 points
  - Meets reasonable performance improvement target (e.g., 2–5x faster on provided dataset or memory use reduced by a target) — 20 points
  - Regression free (existing tests still pass) — 10 points
  - Short explanation of the optimization and why it’s safe — 5 points

Grading rubric details / observable outputs:
- Definitive pass indicator: run_all script exits zero and prints “ALL TESTS PASSED” and benchmark script prints before/after numbers. These outputs should be embedded into test_submission.json.
- Evidence of streaming/adaptation: developer must run a provided script that invokes the adapted mode (e.g., ./run_all.py --low-mem) and show it completes without exceeding a memory usage threshold. If the environment cannot measure memory precisely, require the candidate to run the low-memory mode and the script to assert no OOM and correct output (byte-for-byte or checksum).
- Performance evidence: the benchmark script should run baseline then optimized and print both elapsed times; the candidate’s JSON must include these outputs. The grader can check if elapsed_optimized <= threshold * elapsed_baseline.
- Code review: evaluator inspects diffs/modified files for code clarity and potential regressions (e.g., loss of error handling). Minor style problems are OK for a basic exam but egregious breaks are penalized.

What indicates competence
- Candidate passes the provided tests after changes.
- Candidate can show the adapted mode runs correctly (explicit command + output).
- Candidate shows a measurable and sensible performance improvement, and that tests still pass.
- Candidate provides concise, accurate explanations for what they changed and why (in JSON). Explanations should show they located root causes, not just trial-and-error patches.

Common failure modes to penalize
- Fix that hard-codes test inputs instead of fixing logic.
- Performance “optimization” that introduces incorrectness or fails some tests.
- Incomplete evidence (no test outputs in JSON).
- Big-behavior changes that break features not covered by the tests.

### Required submission format (test_submission.json)
Candidates must submit one JSON file named test_submission.json. It must be valid JSON UTF-8 and include the following fields:

- name: string
- email: string
- time_spent_minutes: integer
- environment: string (Python version, OS, any short notes)
- tasks: array of objects, each with:
  - id: string (e.g., "A-bugfix")
  - status: string (one of "fixed", "partially_fixed", "not_fixed")
  - files_changed: array of file paths modified (relative)
  - commands_run: array of objects:
    - cmd: string (command run)
    - stdout: string (captured command stdout/stderr)
    - exit_code: integer
  - explanation: string (short summary of the root cause and what was changed; <200 words)
  - evidence: object (task-specific numeric evidence)
    - For Task A: {"tests_passed": true/false}
    - For Task B: {"low_mem_mode_ran": true/false, "notes": string}
    - For Task C: {"baseline_time_s": number, "optimized_time_s": number, "improvement_factor": number}
- optional_diff: string (unified diff or link to file path in submission)
- final_notes: string (anything else)

Example minimal tasks array entry:
{
  "id": "A-bugfix",
  "status": "fixed",
  "files_changed": ["src/parser.py"],
  "commands_run": [
    {"cmd": "python3 -m pytest -q", "stdout": "...\n1 failed\n", "exit_code": 1},
    {"cmd": "python3 -m pytest -q", "stdout": "...\nAll tests passed\n", "exit_code": 0}
  ],
  "explanation": "The parser incorrectly split fields with quoted commas. Fixed regex and added unit test for quoted fields.",
  "evidence": {"tests_passed": true}
}

Evaluator instructions (manual or automated)
- Run the included run_all script to verify the candidate’s final state reproduces the reported outputs.
- Check that tests pass and examine the output blocks pasted into JSON to confirm authenticity.
- Run the low-memory/alternate-mode command to verify Task B behavior.
- Run the benchmark or inspect reported baseline/optimized times to check improvement factor.
- Inspect files_changed and the diff/changed lines to ensure change scope is reasonable.
- Score by the rubric above.

### Time allocation (recommended)
- 0–5 min: unpack and read README & task descriptions
- 5–40 min: Task A (bug triage + fix + run tests)
- 40–65 min: Task B (implement streaming/fallback + run validation)
- 65–90 min: Task C (optimize, bench, ensure tests) + write test_submission.json and finalize

---

This design yields a compact, hands‑on, 90‑minute practical exam for entry-level Software Developers, Applications, focused on modifying existing software to fix defects, adapt to constrained hardware, and improve performance — all with strict evidence requirements (runnable commands and outputs) and an explicit JSON submission to simplify automated or semi-automated grading.

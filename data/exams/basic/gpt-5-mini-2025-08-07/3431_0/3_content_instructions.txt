### Exam Title
Practical Maintenance & Optimization — Basic (90-minute hands-on)

### Instructions for Candidate
You have 90 minutes total. Use only the provided machine, the local code editor, and the included execution environment (no internet, no external libraries). All work is done in-place in the provided repository.

1. Unpack the exam package and read README and any task notes (0–5 minutes).
2. Run the provided “run_all” script to get the baseline:
   - Try ./run_all.sh or python3 run_all.py (whichever exists). This script runs unit tests and a small benchmark and prints baseline numbers.
   - Capture the full stdout/stderr and exit code.
3. Task A — Bug Fix (35 minutes)
   - Goal: Find and fix the functional defect(s) so that the unit tests pass.
   - Steps:
     - Run the test suite (the run_all script does this) and read failing tests and stack traces.
     - Modify the code in src/ only as needed to fix the bug(s). Keep changes minimal and safe.
     - Re-run the test suite until all unit tests pass.
   - Deliverable for Task A: tests must pass; capture commands and outputs in your JSON submission.
4. Task B — Hardware Adaptation (25 minutes)
   - Goal: Modify the code so it produces the same correct results under a constrained hardware mode (simulated low-memory or no-parallelism).
   - The repository includes a validation/alternate mode script or accepts a flag to run in constrained mode (examples: ./run_all.sh --low-mem or python3 run_all.py --low-mem). Locate the instructions in README; use the provided mechanism to validate low-memory mode.
   - Typical acceptable adaptations (choose one sensible approach; do not try to implement everything):
     - Convert an operation that reads an entire input file into a streaming approach (process line-by-line / chunked).
     - Provide a sequential fallback if multiprocessing is not available.
     - Replace unnecessary large in-memory data structures with smaller or streaming alternatives.
   - Run the provided low-memory validation script or run_all with the low-memory flag and capture the output. The validation must complete successfully without errors and must produce the expected result (the provided script will indicate correctness).
   - Deliverable for Task B: evidence that the low-memory/constrained mode runs to completion and yields correct output.
5. Task C — Performance Improvement (25 minutes)
   - Goal: Implement a focused performance improvement that measurably reduces runtime or memory usage for the provided dataset.
   - Steps:
     - Before making changes, capture the baseline benchmark (from step 2).
     - Implement a targeted optimization (for example: improve algorithmic complexity from O(n^2) to O(n) by using a dict/set, reduce I/O by streaming or buffering, or avoid repeated expensive operations).
     - Re-run the benchmark using the same command used for baseline and capture optimized runtime/memory numbers.
     - Ensure all tests still pass after optimization.
   - Deliverable for Task C: a measurable improvement (the benchmark outputs before and after), with tests still passing.
6. Prepare submission (final 5 minutes)
   - Create a single JSON file named test_submission.json in the repository root following the required schema (see Submission Format below).
   - In the JSON include the commands you ran, captured stdout/stderr, exit codes, files you changed (relative paths), short explanations of root causes and fixes, and numeric evidence (test pass boolean, low-mem run boolean/notes, baseline and optimized times and improvement factor).
   - You may optionally generate a unified diff and reference it in the JSON, but only test_submission.json will be used for automated/manual evaluation.

Important rules
- Maximum time: 90 minutes. Work beyond this is not considered.
- Do not use external network resources or non-standard libraries.
- Make code changes in the local repository only; do not add large external files.
- The grader will re-run the included scripts to verify your reported outputs; do not paste manipulated or fake outputs.

### Expected Outcome
By the end of the test you must provide:
- A modified local repository where:
  - All unit tests pass.
  - The code includes a working low-memory (or no-parallelism) mode that produces correct results via the provided validation script or flag.
  - The code contains a targeted performance improvement with a measurable improvement reported by the benchmark.
- A single submission file test_submission.json (UTF-8 valid JSON) containing:
  - Your name, email, time spent, environment string.
  - Three task entries (A, B, C) listing modified files, commands executed, captured outputs and exit codes, short explanations (<~200 words each), and numeric evidence (tests_passed flag, low_mem_mode_ran flag and notes, baseline and optimized times and improvement factor).
  - Optional: a unified diff string (optional_diff field) or other final notes.

Acceptance criteria (objective)
- Task A: All provided unit tests pass (verifiable by rerunning the provided test command).
- Task B: The provided low-memory validation script or mode runs to completion and indicates correct output (no crashes/OOM).
- Task C: Benchmark shows a measurable improvement (baseline_time_s and optimized_time_s reported, improvement_factor = baseline/optimized > 1), and tests still pass.
- test_submission.json is valid JSON and contains the required fields.

### Submission Format
You must submit a single file named test_submission.json at the repository root. This is the only file that will be used for grading. The JSON must be valid UTF-8 and follow this schema exactly (field types and names):

Top-level fields
- name: string
- email: string
- time_spent_minutes: integer
- environment: string (e.g., "Python 3.10.5 on Ubuntu 22.04")
- tasks: array of three objects (one per task). Each task object must include:
  - id: string — exactly one of "A-bugfix", "B-lowmem", "C-performance"
  - status: string — one of "fixed", "partially_fixed", "not_fixed"
  - files_changed: array of relative file paths (strings). If none, provide an empty array.
  - commands_run: array of objects, each with:
    - cmd: string (command you ran)
    - stdout: string (captured stdout and stderr combined)
    - exit_code: integer
  - explanation: string (short summary of root cause and what you changed; keep under ~200 words)
  - evidence: object (task-specific)
    - For Task A: {"tests_passed": true/false}
    - For Task B: {"low_mem_mode_ran": true/false, "notes": string}
    - For Task C: {"baseline_time_s": number, "optimized_time_s": number, "improvement_factor": number}
- optional_diff: string (optional unified diff text or empty string)
- final_notes: string (optional)

Example minimal task entry
{
  "id": "A-bugfix",
  "status": "fixed",
  "files_changed": ["src/parser.py"],
  "commands_run": [
    {"cmd": "python3 -m pytest -q", "stdout": "...\n1 failed\n", "exit_code": 1},
    {"cmd": "python3 -m pytest -q", "stdout": "...\nAll tests passed\n", "exit_code": 0}
  ],
  "explanation": "Fixed parsing of quoted CSV fields by adjusting split logic so commas inside quotes are ignored.",
  "evidence": {"tests_passed": true}
}

Grading will be objective — the grader will re-run the commands you list to verify outputs. Ensure everything you paste into the JSON is authentic and reproducible in the repository.

Good luck. Manage your time: Task A (35m), Task B (25m), Task C (25m), finalization (5m).

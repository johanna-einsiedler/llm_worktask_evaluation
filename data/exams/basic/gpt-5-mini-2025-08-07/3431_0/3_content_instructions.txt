### Exam Title
Software Developer (Applications) — Practical Maintenance & Adaptation Test (Basic, 90 minutes)

### Instructions for Candidate
You have 90 minutes total to complete three sequential practical tasks (A → B → C) against the provided repository. Use only the local code execution environment and a text editor. No internet or external libraries are available.

Time recommendation (suggested):
- Task A — Bug Fix: 40 minutes
- Task B — Environment Adaptation: 20 minutes
- Task C — Small Performance Improvement + measurements: 25 minutes
- Packaging submission: 5 minutes

General rules
- Work in the provided repo. It contains a small Python 3 codebase, a test runner (run_tests.py), and a benchmark (bench.py). No external dependencies.
- First run the test runner and the benchmark exactly as provided to capture pre-change outputs (you must include these raw outputs in your submission).
- Make only the minimum changes needed to accomplish each task. Avoid unrelated edits.
- If you can use git in the environment, produce a unified diff (git diff). If git is unavailable, include full updated file contents with clear file path headers.
- Record exact commands you ran to produce outputs.
- Collect all deliverables in a single file named test_submission.json (schema below). Also keep the modified files in the repo if possible.

Task sequence (must be done in order)
1. Task A — Bug Fix
   - Reproduce the failing behavior: run the supplied test runner and capture the full console output.
   - Locate the root cause in the code and modify the code to correct the defect so that the provided tests pass.
   - Re-run the test runner and capture the post-fix console output.
   - Provide a minimal patch/diff or updated file(s).
   - Add or modify a small unit test only if the original tests did not cover the failing behaviour and adding a test is necessary to demonstrate the fix.
   - In your JSON submission include a one- to three-paragraph explanation of root cause and why your fix is minimal and correct.

2. Task B — Environment Adaptation
   - The repo includes a short adaptation requirement (README or task note). Update code/configuration so the application runs in the changed runtime mode (e.g., accept stdin instead of file, or use streaming instead of full memory accumulation, or adapt to a simple helper signature change).
   - Demonstrate the adapted mode running by capturing the exact console output of the app in the new mode.
   - Provide the minimal patch/diff or updated file(s).
   - In your JSON submission include a 1–3 paragraph explanation of what changed, why your change is safe, and any residual risks or limitations.

3. Task C — Small Performance Improvement
   - Run the supplied benchmark script on the provided deterministic input and capture baseline timing (exact command and full output).
   - Propose and implement one small, safe optimization (e.g., avoid repeated work, replace an O(n^2) micro-inefficiency, use a more appropriate data structure, stream processing).
   - Re-run the benchmark and capture the after-change timing.
   - Provide the patch/diff or updated file(s).
   - In your JSON submission include the benchmark numbers (in milliseconds), the exact benchmark command, and a brief explanation (1–3 short paragraphs) of what you changed and the trade-offs/risks.

Important notes on outputs and evidence
- Paste exact console outputs (pre- and post-fix) including stack traces and timing lines. Do not paraphrase or summarize them.
- If you supply a unified diff, it must be in standard git unified-diff format. If not using git, include full updated file contents with clear headers like:
  === file: src/example.py ===
  <file contents>
- Keep your code changes small and focused. Large unrelated refactors reduce credit.
- Self-assess your confidence (1 low — 5 high) for Task A in the JSON.

Time & honesty
- Stop when 90 minutes is reached and package your results. Record your total time_taken_minutes honestly.

### Expected Outcome
By the end of the test you must produce:
- A working test suite: run_tests.py should show that the failing test(s) identified in Task A are passing after your fix.
- A working adaptation: the app runs correctly in the new environment/mode required in Task B and you show the run output.
- A measured performance improvement: benchmark numbers before and after Task C showing measurable improvement (a modest target is ~15–30% improvement; smaller or no improvement is acceptable for partial credit if methodology and reasoning are sound).
- One single file test_submission.json containing required metadata, diffs or updated file contents, run outputs and short explanations for each task (schema below).
- All modified source files included alongside the JSON in the repo (if possible).

Deliverables checklist (must be included in test_submission.json)
- candidate_name
- time_taken_minutes
- task_results — array with three objects for "A-bugfix", "B-adapt_env", "C-performance" containing specified fields (see schema)
- any other_notes you wish to state

### Provided Materials
You will find the following in the repository you were given:
- src/ (source files, small codebase, ~150–400 LOC total)
- tests/ (unit tests used by the test runner; at least one failing test for Task A)
- run_tests.py (script that executes the test suite and prints PASS/FAIL and stack traces; must be run first for Task A)
- bench.py (benchmark script with deterministic input used in Task C; prints timing in ms)
- README.txt (short usage notes and the environment-adaptation requirement description)
- (Optional) helper scripts to run the app in alternative modes (see README)

Notes about materials
- Code is plain Python 3, no external packages. All inputs for benchmark are deterministic and included in the repo.
- The environment adaptation requirement is described in README.txt — read it before Task B.

### Submission Format
You must submit a single JSON file named test_submission.json at the repository root. It must be UTF-8 encoded and follow this schema exactly (all string fields must be plain strings; numeric fields must be numbers; arrays must be arrays):

{
  "candidate_name": "<Full name>",
  "time_taken_minutes": <number>,
  "task_results": [
    {
      "task_id": "A-bugfix",
      "status": "fixed" | "not_fixed" | "partial",
      "files_modified": ["src/file1.py", "src/file2.py"],
      "patch_unified_diff": "<string containing unified diff OR 'N/A' if full file contents are provided elsewhere in this JSON>",
      "pre_fix_test_output": "<exact console output from running run_tests.py before edits>",
      "post_fix_test_output": "<exact console output from running run_tests.py after edits>",
      "explanation": "<1–3 short paragraphs: root cause, why fix works, why minimal>",
      "unit_tests_added_or_modified": ["tests/test_bugcase.py"] or [],
      "self_assessed_confidence": "<1-5>"
    },
    {
      "task_id": "B-adapt_env",
      "status": "adapted" | "not_adapted" | "partial",
      "files_modified": ["src/io_adapter.py"],
      "patch_unified_diff": "<string>",
      "run_output_after_adaptation": "<console output showing app running in new mode>",
      "explanation": "<what changed in environment, what you changed in code, why safe>",
      "risks_or_limitations": "<short note about residual issues>"
    },
    {
      "task_id": "C-performance",
      "status": "improved" | "no_change" | "regressed",
      "files_modified": ["src/processor.py"],
      "patch_unified_diff": "<string>",
      "benchmark_before_ms": <number>,
      "benchmark_after_ms": <number>,
      "bench_command_run": "<command used to run bench>",
      "explanation": "<brief explanation of what was optimized and trade-offs>"
    }
  ],
  "other_notes": "<optional: anything else you want to state>"
}

Additional submission guidance
- For any "patch_unified_diff" field: prefer a git-format unified diff. If you cannot produce a unified diff, set that field to "N/A" and instead include the full updated file contents inline in task_results.explanation or in other_notes using the same explicit file headers described above.
- All console outputs must be verbatim copies (include newlines exactly).
- Include the exact shell/commands you used to run tests and benchmarks (for example: python3 run_tests.py ; python3 bench.py --count 1000).
- If a task fails or you run out of time, set the appropriate status ("not_fixed", "not_adapted", "no_change", etc.) and include partial evidence and explanation.

Grading is objective and reproducible: evaluators will apply your diffs and re-run the same run_tests.py and bench.py commands to verify your claims.

Good luck. Start by running:
python3 run_tests.py
and
python3 bench.py
and collect your pre-change outputs before editing any files.

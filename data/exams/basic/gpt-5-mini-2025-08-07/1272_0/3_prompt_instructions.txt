Here is the exam overview written by another exam designer:
<examoverview>
### Exam Purpose
Confirm that a candidate can practically perform maintenance and small-scale enhancement of existing programs: diagnose and fix defects, implement a new small requirement, and make a modest operational improvement (performance or robustness) while keeping changes minimal, tested, and reproducible. This is the core everyday capability for a junior/entry-level computer programmer tasked with revising, repairing, or extending code to meet new or changed requirements.

### Core Competencies to Be Tested
- Reading and understanding an unfamiliar codebase quickly
- Writing correct, minimal, well-structured code changes
- Running and interpreting test harnesses and benchmarks
- Debugging and fixing functional bugs so existing behavior/tests are satisfied
- Implementing a small new requirement that integrates with the existing design
- Making and validating a targeted performance or resource-use improvement
- Producing reproducible artifacts (code changes, tests, instructions) and clear explanations of what was changed and why
- Using only the provided local environment and standard libraries (no internet)

### Recommended Structure (Basic exam, single session, <= 90 minutes)
Overall: one practical repo + test harness provided to candidate. The exam contains 3 small, interrelated tasks. Candidate submits a single JSON file named test_submission.json (schema below) containing changed file contents, test outputs, and explanations. Evaluator runs the candidate’s submission to verify.

Suggested time allocation:
- Task A — Bug Fix (30 minutes): fix 2–3 small but non-trivial failing tests or an obvious runtime exception.
- Task B — Add Small Feature (30 minutes): implement one small, well-specified requirement (e.g., support an additional input case or a flag / option) plus one small unit test.
- Task C — Modest Optimization or Robustness Improvement (20–25 minutes): improve performance or memory use of a hot function or make the program handle a large edge-case dataset; provide before/after timings or resource measurements and a short justification.

Deliverables (all placed into test_submission.json):
- metadata: candidate name, language, time_taken_minutes
- for each task: status, list of modified files (full file contents or unified diffs), test results, run commands, any benchmark numbers, and a short explanation of changes and trade-offs
- final reproducible commands and instructions to re-run tests/benchmarks

Logical sequence
1. Candidate clones or opens the provided baseline code (local package).
2. Runs the provided test script to observe failing tests and baseline performance measurements.
3. Task A: Fix failures until the tests indicated for Task A pass.
4. Task B: Implement the new feature; add a test verifying it; ensure existing tests still pass.
5. Task C: Profile/measure a targeted function, implement a small optimization or defensive change, and show measurable improvement or improved robustness.
6. Package results into test_submission.json and submit.

Constraints to ensure fairness and reproducibility:
- Only standard libraries available in the provided execution environment may be used (no external downloads).
- A single command (documented in the exam package, e.g., ./run_all.sh or python -m pytest) must run all automated checks in the baseline; candidate must provide the command(s) that reproduce their final results.

### Practicality — Making it hands-on
- Provide a runnable baseline repository (small: ~300–600 lines split across several files) with:
  - A small set of unit tests that demonstrate expected behavior (some intentionally failing for Task A).
  - A small dataset or input files for performance measurement for Task C.
  - A single-run script to produce baseline test and timing outputs.
- Require the candidate to run tests and bench locally and include actual outputs in JSON (not just claims).
- Require the candidate to include the actual modified source files in the JSON (not just textual description).
- Include at least one failing runtime or logic issue that only becomes apparent by running the code (so the assessment cannot be completed by purely answering questions).
- Make Task B require integrating with existing interfaces (e.g., modifying a function used by other code) to test reading and integrating with code rather than creating isolated snippets.

Example minimal exam contents to provide the candidate:
- code/
  - main.py (or similar)
  - utils.py
  - processor.py
- tests/
  - test_task_a.py (initially failing)
  - test_task_b_spec.py (describes feature; candidate expected to implement and add a test that passes)
- data/
  - sample_input_small.txt
  - sample_input_large.txt (for Task C measurement)
- run_all.sh (runs tests and baseline timing)
- README.md with clear task descriptions and exact time limit notice

### Strategic elements (how to distinguish competent doers)
- Multi-step dependency: Task B builds on the same modules fixed in Task A (so candidates must understand and preserve earlier fixes). This prevents copy-paste toy answers and highlights comprehension of code interactions.
- Decision points:
  - For Task C, candidates must decide whether to optimize algorithmically, cache results, or reduce allocations. Ask them to justify their choice in the JSON explanation and to implement the chosen change.
  - Ask candidates to choose trade-offs when implementing Task B (e.g., conservative change vs refactor). Their choice and justification reveal practical judgment.
- Data dependency: provide small and larger sample inputs for performance checks. The “large” input should be big enough to reveal naive O(n^2) vs O(n log n) behavior in timing.
- Failure modes: include an edge-case in tests that can be handled either by a small guard clause or by adjusting a central algorithm; candidates who understand the codebase will pick the minimal, maintainable fix.

### Evaluation Insights (observable outputs / success criteria)
Scoring (example weights to be used by evaluators; total 100):
- Task A — Bug Fix correctness: 40 points
  - 30 pts: All Task A tests pass in the candidate-submitted code
  - 10 pts: Changes are minimal and well-scoped (no unrelated modifications); code style/readability acceptable
- Task B — Feature & tests: 30 points
  - 20 pts: The new feature works and its test(s) pass
  - 10 pts: Integration with existing code is correct and the candidate added at least one unit test
- Task C — Measurable improvement & justification: 25 points
  - 15 pts: Demonstrable quantitative improvement (timings, memory) or improved robustness on supplied large input (candidate must include before/after numbers)
  - 10 pts: Clear explanation of change, alternatives considered, and trade-offs
- Submission quality & reproducibility: 5 points
  - JSON is correctly formed per schema, includes full modified files or unified diffs, includes commands to reproduce test and benchmark results

Pass conditions for basic exam (goal: entry-level should score >80%):
- Full credit on Task A and Task B and reasonable improvement on Task C (or clear partial progress with correct approach and explanations) should exceed 80 points. The tasks are sized so a competent entry-level candidate can complete them in 90 minutes.

Observable outputs to collect and verify (automatable where possible)
- Automated:
  - Unit test run: which tests pass/fail (pytest/unittest output)
  - Benchmark run: wall-clock times (e.g., using time module or simple wrappers) before and after changes
- Manual/qualitative:
  - Content of modified files (ensure changes are localized and correct)
  - Clarity of written explanations in JSON: what was changed, why, and options considered
  - Presence and quality of any new tests added by candidate
  - Whether candidate preserved or improved error handling and edge cases

Required format of test_submission.json (candidate must produce exactly this file name). Provide this schema to candidates and evaluators:

- top-level keys:
  - name (string)
  - email (string, optional)
  - language (string, e.g., "python")
  - time_taken_minutes (integer)
  - run_commands (array of strings) — exact commands to reproduce tests and benchmarks in order
  - tasks (array of task-objects)
- each task-object keys:
  - id (string: "A" | "B" | "C")
  - status (string: "completed" | "partial" | "not attempted")
  - modified_files (object): map from filename -> full file content (string) [must include all files changed]
  - diffs (optional string): unified diff text if candidate prefers to submit diffs
  - test_output (string): raw stdout/stderr of test runs after candidate changes
  - benchmark_before (optional number): baseline time (seconds) as observed before changes
  - benchmark_after (optional number): time (seconds) after changes
  - explanation (string): 3–6 sentences describing what was changed, why, and any trade-offs
- final_notes (string): any other info or known issues

Example minimal validation checks for evaluator
- Parse JSON; ensure required keys exist.
- For each modified file in modified_files, write content to disk and run the provided run_commands to verify the candidate’s claimed test_output and benchmark numbers.
- Ensure Task A tests pass fully for full Task A credit.
- Ensure candidate’s new test for Task B is present and passing.
- Verify improvement or reasonable justification for Task C.

Notes and tips for exam creators and evaluators
- Keep each task small and self-contained but connected: do not create a multitudes of hidden tricky corner cases that require deep domain knowledge.
- Favor a small codebase with clear module boundaries and well-named functions to reduce time spent understanding irrelevant complexity.
- For Task C, set measurable but modest targets (e.g., reduce runtime by ~30–50% on provided large input or reduce memory allocation that causes the baseline to fail). Make the target achievable with a clear local change.
- Provide a short README with exact commands to run baseline tests and timers.
- If language flexibility is offered, require candidate to declare language in JSON and provide the run commands needed so evaluator can reproduce results locally.

This structure ensures a practical, hands-on assessment that exercises the typical day-to-day tasks of a programmer performing repair, revision, and small expansion of existing programs while remaining completable in a 90-minute window by an entry-level candidate.

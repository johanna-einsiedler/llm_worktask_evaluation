### Exam Title
Practical Code Maintenance and Small-Scale Enhancement — Basic (90 minutes)

### Instructions for Candidate

You have up to 90 minutes to complete a short, practical programming exam that tests your ability to read an unfamiliar codebase, fix defects, add a small feature, and make a modest performance or robustness improvement. You will work only with the local repository and tools provided in the exam environment: a code execution environment (interpreter/runner) and a text editor. No internet or external libraries are allowed—use only standard libraries available in the environment.

Follow these steps in order. Record the exact terminal output for each run (stdout/stderr) and include it in your final JSON submission.

1. Start the clock (max 90 minutes).
2. Inspect the repo and README. Run the provided baseline script to observe current test results and baseline timings:
   - Run: ./run_all.sh
   - If the repo does not include a run_all.sh, run: python -m pytest -q then run the provided benchmark script(s) per README.
   - Capture and save the raw output.
3. Task A — Bug Fix (target time: 30 minutes)
   - Objective: Diagnose and fix the failing tests and/or runtime exception(s) that are marked for Task A in the tests folder.
   - Requirements:
     - Make minimal, well-scoped changes so the Task A tests pass.
     - Do not add unrelated refactors or new features.
   - Deliver:
     - Modified source file contents (full files).
     - The exact test output after your changes showing Task A tests passing.
     - Short explanation (3–6 sentences) of what was wrong and how you fixed it.
4. Task B — Small Feature (target time: 30 minutes)
   - Objective: Implement one specified small feature that is described in the README or tests (e.g., support an extra input case, add a command-line flag, or extend a function's behavior). Add a unit test that verifies the new behavior.
   - Requirements:
     - Integrate with existing interfaces; do not create a totally separate module for the feature.
     - Add exactly one unit test (or a very small test case) that demonstrates the feature.
     - Ensure all existing tests still pass after your change.
   - Deliver:
     - Modified source file contents (full files) and the new test file content.
     - Test output showing Task B tests (and the full test suite) passing.
     - Short explanation (3–6 sentences) describing your implementation and any trade-offs.
5. Task C — Modest Optimization or Robustness Improvement (target time: 20–25 minutes)
   - Objective: Measure a provided "hot" function or processing pipeline on a small and a larger sample input, then implement a focused change that improves runtime or memory usage, or that makes the program handle a large edge-case reliably.
   - Requirements:
     - Before making changes, record the baseline timing(s) and/or failure on the large sample provided.
     - Implement a small targeted improvement (caching, algorithmic tweak, fewer allocations, guard clause, etc.). Keep changes minimal and well-documented.
     - After change, re-run the same timing(s) and include before/after numbers.
     - If no meaningful time improvement is achievable, you may instead make the program handle a large edge case that previously failed; include before/after behavior and numbers.
   - Deliver:
     - Modified file contents (full files).
     - Raw benchmark output before and after your change (wall-clock seconds; simple time.time measurements are fine).
     - Short explanation (3–6 sentences) describing the change, measured improvement (or improved robustness), and trade-offs.
6. Final packaging
   - Prepare a single JSON file named test_submission.json containing all required fields and artifacts per the Submission Format below.
   - Do not submit anything else—this single file is the only artifact the evaluator will use.
7. End the session. Record total time_taken_minutes (elapsed minutes).

Rules and constraints (must be followed):
- Use only the provided execution environment and standard libraries.
- Work independently; do not use the internet or external code.
- Keep changes minimal and limited to files you must change to satisfy tasks.
- The evaluator will automatically re-create your changes from the file contents in test_submission.json and re-run your provided run_commands to verify your claims. Make sure your run_commands are accurate.

### Expected Outcome

By the end of the exam you must produce:
- A working codebase (in your local environment) where:
  - All Task A tests (the failing tests you observed initially) pass.
  - The new feature for Task B is implemented and its unit test passes.
  - A focused improvement was implemented for Task C and you captured before/after measurements (or fixed a previously failing large-input case), with a short justification of the chosen approach.
- A single JSON file named test_submission.json with:
  - Your metadata (name, language, time taken).
  - Exact commands needed to reproduce your final test and benchmark runs (in order).
  - For each task A/B/C: status, the full contents of any files you modified, raw test and benchmark outputs you captured, and a short explanation.
- All test outputs and benchmark numbers must be the actual raw outputs you produced during the exam session (not reconstructions).

Success criteria (objective):
- Task A: the tests flagged for Task A pass in your submitted run_commands output.
- Task B: your new test for the feature is present in modified files and passes.
- Task C: you provide measurable before/after timing numbers showing an improvement, or show that your change prevents a failure on the large input and provide before/after evidence.
- The JSON file is well-formed and contains the required artifacts so the evaluator can re-run your commands to reproduce your results.

### Provided Materials

You will be given a small runnable project in the exam environment containing:
- A small codebase (approx. 300–600 lines total) split across a few files (e.g., main.py, utils.py, processor.py).
- A tests/ directory with unit tests. Some tests will pass; 2–3 tests or a runtime exception will be intentionally failing and marked for Task A.
- A README.md that:
  - Describes the three tasks and points out which tests are Task A tests and what Task B feature is required.
  - Explains the baseline run command (./run_all.sh or python -m pytest) and any benchmark script or data files for Task C.
- A data/ directory with:
  - sample_input_small.txt for quick runs.
  - sample_input_large.txt for timing and robustness checks (large enough to reveal a naive O(n^2) problem or to trigger an edge-case failure).
- A run_all.sh script that runs the test suite and prints baseline timing results. (If missing, use python -m pytest and the benchmark script described in README.)

You will not be provided internet access or external libraries. All needed test scaffolding and data are in the repo.

### Submission Format

You must submit a single file named exactly test_submission.json at the repository root. It must be valid JSON UTF-8. The evaluator will programmatically read this file, apply your modified files to the baseline repo, then run the commands you list and compare outputs.

Required JSON structure (fields and types). Include exactly these keys and types:

- name (string) — your full name
- email (string or null) — optional
- language (string) — e.g., "python"
- time_taken_minutes (integer) — total elapsed minutes (<= 90)
- run_commands (array of strings) — exact shell commands to reproduce, in order (first command should run the full test suite and benchmarks on your final code)
- tasks (array of 3 task objects) — one object per Task A,B,C (order not enforced, id must be "A", "B", "C")

Each task object must contain:
- id (string) — "A" or "B" or "C"
- status (string) — one of "completed", "partial", "not attempted"
- modified_files (object) — map of filename -> full file content (string). Include every file you changed. If you changed no files for a task, put an empty object {}.
- diffs (string or null) — optional: a unified diff text if you prefer to submit diffs instead of full file contents (still include modified_files).
- test_output (string) — the raw stdout/stderr when you ran the test suite after your changes (or the relevant subset of tests). Include full raw output.
- benchmark_before (number or null) — baseline time in seconds you recorded before implementing Task C changes (if applicable)
- benchmark_after (number or null) — new time in seconds after changes (if applicable)
- explanation (string) — 3–6 sentences describing what you changed, why, and trade-offs/alternatives you considered

Top-level final_notes (string or empty) — any extra remarks (optional).

Additional submission notes (strict):
- Filename must be test_submission.json; nothing else will be used by the evaluator.
- modified_files must contain the full file contents for every file you changed so the evaluator can overwrite the baseline with your version exactly.
- run_commands must be runnable in the repository root and must reproduce the outputs you include in test_output and benchmark fields.
- Capture and include exact raw outputs (not summaries). If the output contains ANSI color codes, include them as-is.
- If you include diffs, they are for reviewer convenience; the evaluator will rely on modified_files to re-create your changes.
- Keep each explanation concise and factual—3–6 sentences each.

Good luck. Work clearly and concisely; prioritize making correct, minimal changes and including reproducible outputs in test_submission.json.

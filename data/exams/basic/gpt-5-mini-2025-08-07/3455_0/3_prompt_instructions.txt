Here is the exam overview written by another exam designer:
<examoverview>
### Exam Purpose
Confirm that a candidate can practically collect, store, retrieve, and manipulate system-related data (logs/telemetry/configuration) to produce measurements and summaries needed for systems-capability analysis and requirements decisions. This exam verifies the candidate can design a simple storage model, load data reliably, write correct queries/transformations, produce analysis-ready summaries, and package results and runnable artifacts in a reproducible way.

Real-world capability validated:
- Turning raw system telemetry/logs into queryable, consistent data.
- Extracting correct operational metrics (counts, aggregates, rollups).
- Performing joins, deduplication, basic time-window analysis and filtering.
- Exporting results and documenting assumptions so a systems engineer can act on them.

### Core Competencies
- Data ingestion and storage design (schema choice for simple telemetry/logs).
- Use of local storage (SQLite or file-based) and standard language I/O (no external DB servers).
- Data cleaning (type coercion, missing/invalid value handling, de-duplication).
- Retrieval & manipulation: SQL or equivalent (group-by, time-window aggregation, joins, filters).
- Scriptable, repeatable workflow: single command runs end-to-end.
- Reproducible output packaged as structured JSON for automated evaluation.
- Clear, concise documentation of steps and decisions.

### Recommended Structure
Total time: 90 minutes. The exam package (delivered to candidate) contains:
- A small dataset file: system_logs.csv (approx. 1–5 MB, ~1–10k rows). Columns: timestamp (ISO8601), host, component, level (INFO/WARN/ERROR), event_id, metric_name, metric_value (nullable), message.
- A README.txt with allowed languages (prefer Python 3 + sqlite3 as default) and required deliverable filename: test_submission.json.

Organize as three sequential tasks (expected completion times in parentheses):
1. Ingest & Store (30 minutes)
   - Build a script that creates a local SQLite DB (or local file storage) and loads system_logs.csv into a normalized table schema. Coerce types (timestamp -> datetime, metric_value -> numeric), ensure event_id uniqueness, and remove exact duplicate rows.
   - Deliverable: DB file (system_logs.db) and ingestion script with run instruction.
2. Query & Analyze (35 minutes)
   - Using the stored data, produce the following outputs (exact numbers must match authoritative expected answers for automatic grading):
     a. Total number of unique hosts.
     b. Count of ERROR events per host (top 5 hosts by ERROR count).
     c. Time-series: hourly count of ERROR events for the last 24 hours of data (ISO hour -> count).
     d. For each component, average metric_value for metric_name = "cpu_usage" (ignore nulls).
     e. Identify the 10 most frequent event_id values and their counts.
   - Deliverable: Query scripts or a combined analysis script that outputs the required aggregates when run.
3. Manipulate & Export (20 minutes)
   - Create a filtered export (CSV) of all ERROR events in the last 7 days with columns: timestamp, host, component, event_id, message, metric_value.
   - Create a summarized JSON (report) with top-5 hosts by ERROR and hourly error counts as an embedded array.
   - Deliverable: error_events_7days.csv, summary_report.json.

Final packaging (part of submission)
- A single JSON file named test_submission.json containing:
  - metadata: candidate_name, language, command_to_run (one-liner to run ingestion+analysis), runtime_seconds (approx).
  - required numeric outputs for automated checking (items from Query & Analyze).
  - small sample of exported CSV first 5 rows and path to files produced.
  - short (<=200 words) explanation of schema choices, deduplication logic, and any edge-case assumptions.

Note: All scripts must run without network access and must use only the language's standard library or pre-installed tooling documented in the README.

### Practicality — making it hands-on
- Provide a real CSV dataset resembling system telemetry/logs (not questions). Candidate must actually load and operate on that file.
- Require producing an actual store (SQLite DB file) rather than just writing SQL statements on paper.
- Require runnable scripts that perform the full pipeline from ingest to export; evaluator runs the candidate's command to verify reproducibility.
- Provide automatic checks against deterministic expected results (counts, top lists) so scoring can be partly automated.

### Strategic elements (distinguish doing vs. knowing)
Include decision points and multi-step dependencies:
- Schema choice: candidate must decide whether to keep metric_name/value in a wide table vs normalized separate metrics table — their choice affects query complexity and must be explained briefly in test_submission.json.
- Deduplication: define "duplicate" as rows identical across all fields; candidate must implement removal and justify handling of partially duplicated rows (e.g., identical event_id at different timestamps).
- Type coercion: timestamp parsing and timezone handling (explicit assumptions allowed but must be documented).
- Indexing: candidate may optionally create indexes to speed queries — presence/choice of index is extra credit and shows awareness of scaling.
- Aggregation windows: hourly roll-ups require correct truncation of ISO timestamps; off-by-one hour errors are common and reveal practical mistakes.
- Null/invalid metric handling: candidate must decide to ignore or impute null metric_values—must document and implement.

These elements force the candidate to implement, test, and make explicit operational choices rather than answer conceptual questions.

### Practical Elements to Include (for the exam creator to supply)
- system_logs.csv (well-documented format, includes edge cases: null metric_values, duplicate rows, malformed timestamps in a few rows).
- README.txt specifying:
  - Time limit (90 minutes).
  - Allowed languages/tools (recommend Python 3 with sqlite3 preinstalled).
  - Exact required filenames: system_logs.db, error_events_7days.csv, summary_report.json, test_submission.json.
  - Single-command run requirement (e.g., ./run.sh or python3 run.py).
  - JSON schema required for test_submission.json (see Evaluation Insights).
- An example run command and an example test_submission.json (small template) to reduce ambiguity.

### Evaluation Insights (what to check and how to score)
Scoring (suggested, total 100 pts):
- Ingestion & Storage correctness (30 pts)
  - DB created and table(s) exist with appropriate types (10).
  - Duplicates removed correctly (5).
  - Malformed timestamps/values handled (5).
  - Script runs end-to-end with a single command (10).
- Queries & Analysis correctness (40 pts)
  - Unique hosts count correct (5).
  - Top-5 hosts by ERROR count correct and ordered (10).
  - Hourly ERROR time-series correct for last 24 hours (10).
  - Average cpu_usage per component correct (10).
  - Top-10 event_id frequencies correct (5).
- Exports & Reporting (15 pts)
  - error_events_7days.csv contains correct filtered rows and correct columns (8).
  - summary_report.json contains properly structured arrays and top-5 host list as per required schema (7).
- Code quality & reproducibility (10 pts)
  - Clear, concise README/run instruction; scripts exit cleanly (5).
  - Use of standard library only and no network calls; small, tidy code with comments (5).
- Documentation & rationale (5 pts)
  - Short explanation in test_submission.json of schema decisions, dedup rules, timestamp handling, and any edge-case choices (evaluated for clarity and appropriateness).

Automation checks:
- The evaluator should run candidate's one-line command; then:
  - Open system_logs.db and run a deterministic SQL query to compute ground-truth aggregates (exam author provides expected outputs when generating dataset) and compare to values in test_submission.json.
  - Verify exported CSV columns and sample rows against DB query.
  - Validate summary_report.json structure and embedded arrays match computed aggregates.

Pass criteria for basic exam:
- Candidate should achieve >= 80/100. The tasks are designed so a competent entry-level developer using standard libraries and commonsense will reach that threshold within 90 minutes.

Required structure of test_submission.json (exact fields for automated checking)
- candidate_name: string
- language: string (e.g., "python3")
- run_command: string (one-liner)
- runtime_seconds: number (approx)
- outputs: object with keys:
  - unique_hosts: integer
  - top5_hosts_error: array of {"host": string, "error_count": integer} ordered desc
  - hourly_errors_last24: array of {"hour": "YYYY-MM-DDTHH:00:00", "count": integer} ordered asc
  - avg_cpu_by_component: array of {"component": string, "avg_cpu": number}
  - top10_event_ids: array of {"event_id": string, "count": integer}
- sample_error_csv_rows: array of first up to 5 rows of error_events_7days.csv (each row as object with exported columns)
- files_produced: array of produced filenames and sizes (e.g., [{"file":"system_logs.db","bytes":...}, ...])
- notes: string (<=200 words) explaining schema choice, dedup rules, timestamp handling

Example (short) test_submission.json skeleton (exam author provides full template to candidate):
{
  "candidate_name": "<your name>",
  "language": "python3",
  "run_command": "python3 run.py",
  "runtime_seconds": 42,
  "outputs": {
    "unique_hosts": 12,
    "top5_hosts_error": [{"host":"host-1","error_count":120}, ...],
    "hourly_errors_last24": [{"hour":"2025-10-12T10:00:00","count":3}, ...],
    "avg_cpu_by_component": [{"component":"web","avg_cpu":23.4}, ...],
    "top10_event_ids": [{"event_id":"E1001","count":53}, ...]
  },
  "sample_error_csv_rows": [
    {"timestamp":"...", "host":"...", "component":"...", "event_id":"...", "message":"...", "metric_value":12.4}
  ],
  "files_produced": [{"file":"system_logs.db","bytes":123456}, ...],
  "notes":"Schema: single table logs(...). Dedup: drop exact duplicate rows. Timestamps parsed as UTC..."
}

Evaluator workflow:
1. Run candidate run_command on exam folder.
2. Validate test_submission.json format and required fields.
3. Run a deterministic validation script that reads system_logs.db and computes the expected aggregates (the exam pack author supplies expected outputs but the validator can recompute to be robust) and compares to outputs in test_submission.json.
4. Check presence and non-empty exported files.
5. Apply scoring rubrics and provide feedback for each item failed or warning.

---

This structure keeps the exam practical and reproducible, verifies end‑to‑end ability to store, retrieve, and manipulate system data, and provides an automated way to evaluate correctness while leaving room for assessors to grade code quality and rationale.

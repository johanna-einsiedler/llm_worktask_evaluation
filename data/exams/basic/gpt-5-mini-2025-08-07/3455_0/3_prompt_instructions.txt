Here is the exam overview written by another exam designer:
<examoverview>
### Exam Purpose
This basic practical exam verifies that a candidate can take raw system telemetry/log data, design a simple persistent schema, reliably store the data, retrieve and manipulate it to produce analysis-ready aggregates and reports, and provide reproducible, runnable code that performs these steps. In real world terms it confirms the candidate can perform the core job of collecting and preparing system metrics data to support capacity planning, performance troubleshooting, and requirements analysis.

Intended outcome: after running the candidate’s submission, an evaluator (or an automated grader) can confirm that the candidate’s code created a persistent store, executed expected queries and aggregations, handled simple data issues, and produced the requested outputs in the required JSON submission.

---

### Core Competencies to be Tested
1. Data ingestion/parsing
   - Read and validate CSV/log input, parse timestamps and numeric fields, handle missing values and duplicates.
2. Data modeling and persistence
   - Design a compact, sensible schema for telemetry data and implement it in a file-backed DB (SQLite recommended).
3. Data storage & performance basics
   - Create tables and appropriate indices; demonstrate awareness of basic performance tradeoffs for read-heavy queries.
4. Querying & aggregation
   - Write SQL (or equivalent) to select, filter, join, aggregate, and compute time-window metrics (averages, max, percentiles or counts).
5. Reporting / export
   - Produce structured outputs (JSON, CSV) required for downstream analysis.
6. Reproducibility & automation
   - Provide a single runnable script/CLI to perform the steps; include minimal but clear instructions.
7. Documentation & reasoning
   - Briefly justify schema/approach and propose one or two simple improvements.

These competencies map to the kinds of work performed by junior systems-software developers working with system telemetry and capacity analysis.

---

### Recommended Structure (Basic exam)
Total time allowance: 90 minutes.

High-level: 4 timed tasks + final submission metadata. Expected deliverables: scripts and one JSON file named test_submission.json with prescribed fields.

Tasks:
1. Setup & Ingest (25 minutes)
   - Input: a single CSV file (provided by exam creator) named telemetry.csv.
   - Candidate implements a script (e.g., ingest.py or run_exam.py) that:
     - Creates an SQLite DB file telemetry.db.
     - Creates table(s) and indices.
     - Loads data from telemetry.csv into the DB, performing minimal validation/normalization (parse timestamps, convert numeric types, skip or coalesce bad rows).
   - Deliverable: DB file (telemetry.db) and ingest script.

2. Query & Analysis (30 minutes)
   - Using the DB created, candidate must run specific queries and return results:
     - Q1: Time range count: total number of records.
     - Q2: Top 3 hosts by average CPU usage over the entire dataset (host + avg CPU value).
     - Q3: For a given host (specified in the task), compute hourly average CPU and peak memory for the last 24 hours in the data. Return results as an array of (hour-start-timestamp, avg_cpu, max_mem).
     - Q4: Identify periods where CPU > 90% for at least 3 consecutive samples for any host (return host, start_ts, end_ts).
   - Deliverable: Query results captured in test_submission.json exactly in the specified schema.

3. Update & Small Manipulation (15 minutes)
   - Implement a small function/CLI to insert one new telemetry record (provided in the task text) into the DB and update any derived table(s) if used.
   - After insertion, re-run one relevant query (e.g., host average CPU) and provide the updated numeric result in the submission.

4. Short Explanation & Recommendations (10 minutes)
   - In test_submission.json, include:
     - A short explanation (1–3 sentences) of the schema design choices (why columns typed that way, any normalization decisions).
     - Two practical improvements you would make in a production setting (e.g., retention policy, partitioning, compressing, sharding, monitoring, batching writes).

Final deliverable required: a single file test_submission.json with required fields (see below), plus code files and DB/outputs as allowed by evaluator.

Note: Candidate must not require external network or non-standard libraries; exam should be solvable with common standard libraries (e.g., Python standard library including sqlite3, csv, datetime). The exam creator provides telemetry.csv as part of the test package.

---

### Practicality — How to ensure this is hands-on
- Provide an actual telemetry.csv file (sample size 500–2000 rows) with realistic columns: timestamp (ISO 8601), host, cpu_percent (0–100), mem_mb, disk_io_kb, net_io_kb, event_type (INFO/WARN/ERROR), and possibly small controlled edge cases (a few missing CPU fields, one duplicate row, one malformed timestamp).
- Require the candidate to run code in the provided environment (no internet) and produce a DB file and results JSON.
- Require the output values to match exact expected results for deterministic parts so the grader can validate automatically (e.g., total row count, top 3 hosts must match).
- Provide a single new record to insert in Task 3, so graders can automatically recompute expected updated numbers.
- Make it clear that they should submit code, DB, and the test_submission.json; but the official required file for grading is test_submission.json (it will also contain the outputs so a grader can quickly verify).

---

### Strategic elements (decision points and multi-step processes)
Design these to separate the candidates who can do and those who only know theory:

1. Multi-step dependency
   - Queries rely on the DB created in Task 1, so failure to ingest correctly will cascade. This tests end-to-end ability.
2. Data normalization decision
   - Candidate must choose whether to normalize host metadata (separate host table) or use a single flat table. For basic exam, either is acceptable—but the candidate must explain the choice briefly.
3. Handling messy data
   - The dataset contains a few malformed or missing values; candidate must either skip or coerce them, and results must match expected choices. This forces practical handling rather than theoretical answers.
4. Indexing trade-off
   - Candidate may create indices to make queries faster. The evaluator inspects whether indices exist (PRAGMA index_list) and whether they are sensible (e.g., index on host + timestamp).
5. Time grouping and windowing
   - Require hourly aggregation and detection of consecutive-high CPU windows — forces correct time parsing and ordering logic.
6. Deterministic outputs for grading
   - Provide specific hosts and timestamps to check for expected output so the grader can automatically confirm correctness.

These strategic elements reveal mastery of practical skills rather than rote knowledge.

### test_submission.json — required schema (make this exact)
The candidate must produce this single JSON file named test_submission.json. Fields:

- candidate: { name: string, email: string (optional) }
- env: { language: string (e.g., "python3"), entrypoint: string (filename to run), db_file: string (path to created DB) }
- ingestion: { rows_loaded: integer, rows_skipped: integer, note: string (optional) }
- results:
  - total_rows: integer
  - top_hosts_by_avg_cpu: [ { host: string, avg_cpu: number } ]   (length 3)
  - hourly_stats_for_host: [ { hour_start: ISO8601 string, avg_cpu: number, max_mem_mb: number } ]   (for 24 hours or fewer as applicable)
  - cpu_spike_periods: [ { host: string, start_ts: ISO8601 string, end_ts: ISO8601 string } ]
- after_insert:
  - inserted_record_ok: boolean
  - updated_avg_cpu_for_host: number   (for the host used in Task 3)
- schema_and_choices:
  - schema_description: string  (1–4 sentences describing tables/columns and rationale)
  - suggested_improvements: [ string, string ]  (two short suggestions)
- run_instructions: string (exact commands to run the script(s) from the exam root; one line or a couple of lines)
- optional: errors: [ string ] (any non-fatal warnings/errors encountered)

All numeric values should be numbers (not strings) with reasonable precision (two decimal places OK). Timestamps must be ISO 8601 strings.

Provide an example minimal test_submission.json skeleton in the exam materials so candidates know structure.

### Evaluation Insights — observable outputs and scoring rubric
Total: 100 points. Passing threshold: 80+ points for basic exam.

Suggested scoring breakdown:
- Task 1: Ingest & DB creation (30 points)
  - DB created at specified path (10)
  - Table(s) with sensible types and columns (10)
  - rows_loaded equals expected count and rows_skipped consistent with malformed data (10)
- Task 2: Query & Analysis (40 points)
  - total_rows correct (5)
  - top 3 hosts by average CPU correct (10)
  - hourly stats correct format and plausible numbers for the given host (10)
  - cpu spike detection correct (15)
- Task 3: Insert/update (15 points)
  - insert operation succeeds, updated_avg_cpu is correct per expectation (10)
  - code handles duplicates/validation for inserted record (5)
- Task 4: Documentation & reproducibility (10 points)
  - run_instructions correct and scripts runnable (5)
  - schema_description + two practical improvements present and reasonable (5)
- Code hygiene & robustness (5 points)
  - minimal error handling, readable code, comments, no reliance on non-standard libraries

Automatic grader checks:
- Parse test_submission.json and verify numeric results against expected ground truth (derived from the provided telemetry.csv and known inserted record).
- Verify DB file exists and optional PRAGMA checks (table/indices) if the grader expects to perform deeper checks.

What indicates competence:
- End-to-end working script that produces telemetry.db and the exact result numbers in test_submission.json.
- Correct handling of timestamps and consistent hours in hourly aggregation.
- Correct identification of continuous CPU spike periods (requires ordering and grouping).
- Clean, reproducible run instructions and a short but sensible explanation of schema and production improvements.

What flags a weak candidate:
- Delivering only SQL or conceptual answers without executable ingest script or DB file.
- Incorrect counts or aggregates that indicate misunderstanding of grouping/time windows.
- No handling of malformed data, causing crashes or wildly incorrect row counts.
- Missing run instructions or inability to reproduce outputs.

---

### Practical tips for the exam creator / evaluator
- Provide telemetry.csv and a short README that states allowed languages (e.g., Python/3, Bash, etc.), time limit (90 minutes), and that no external internet or libraries are allowed.
- Include an exact new-record JSON/CSV line to be inserted for Task 3 and precompute the expected updated numbers to enable automatic scoring.
- Create a small automated grader script (optional) that opens test_submission.json, checks expected numeric fields and existence of telemetry.db to compute score automatically.
- Keep dataset size moderate (500–2000 rows) so queries run quickly without needing tuning beyond a basic index.
- Provide one known corner-case row to test robustness (e.g., timestamp "2020-13-01" malformed) and document that candidates should either skip or coerce rows and reflect skipped rows in ingestion.rows_skipped.

---

This structure gives a practical, end-to-end hands-on assessment of a junior systems-software engineer’s ability to store, retrieve, and manipulate telemetry data for system capability and requirements analysis, while being straightforward to grade and feasible in a 90-minute remote environment.

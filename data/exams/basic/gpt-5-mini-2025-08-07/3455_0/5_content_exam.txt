### Exam Title
System Telemetry: Ingest, Store, Query, and Export (Basic Practical Exam — 90 minutes)

### Instructions for Candidate
You have 90 minutes. Use only your local code execution environment and a text editor. No network access and no third‑party libraries; use only the language runtime and standard library available on the machine. Python 3 + sqlite3 is recommended but not required.

You must implement a single runnable end‑to‑end pipeline (one command) that:
1. Ingests the provided CSV into a local SQLite database (system_logs.db).
2. Runs the required queries/aggregations on the stored data.
3. Produces the requested exports and a single submission JSON (test_submission.json) containing the required outputs and metadata.

Follow these step‑by‑step tasks:

Step A — Ingest & Store (≈30 minutes)
- Create a script (or small program) that:
  - Reads the provided CSV file system_logs.csv.
  - Parses timestamps (ISO8601). Rule: treat timestamps that include a timezone offset by converting them to UTC; timestamps without timezone are interpreted as UTC. If a timestamp is malformed and cannot be parsed, drop that row (see Submission Format notes).
  - Normalizes and loads rows into a SQLite database file named system_logs.db. Use an appropriate normalized schema but you must store at least the fields: timestamp (as a DATETIME in UTC), host, component, level, event_id, metric_name, metric_value (numeric or NULL), message.
  - Coerce metric_value to numeric when possible; invalid numeric strings become NULL.
  - Remove exact duplicate rows (duplicate = identical values across all incoming CSV fields).
  - If multiple non-identical rows share the same event_id (i.e., event_id collision), apply this deterministic rule: keep the row with the earliest timestamp and drop the others.
  - Ensure event_id is unique in the final table (e.g., enforce a UNIQUE constraint or otherwise guarantee uniqueness).
  - The script must create system_logs.db in the working directory.

Step B — Query & Analyze (≈35 minutes)
- Using the stored data in system_logs.db, compute these deterministic outputs:
  1. unique_hosts: total number of unique host values.
  2. top5_hosts_error: top 5 hosts by count of events where level = "ERROR". Order by error_count descending; break ties by host string ascending.
  3. hourly_errors_last24: hourly counts of ERROR events for the last 24 hours of data. Deterministic definition:
     - Let max_t = the maximum timestamp present in the cleaned DB (UTC).
     - Let H0 = truncate(max_t to the hour (floor to HH:00:00 UTC)).
     - Produce 24 hourly buckets: H0 - 23h, H0 - 22h, ..., H0 (inclusive). For each hour bucket produce {"hour":"YYYY-MM-DDTHH:00:00","count": integer}. Order the array ascending (oldest first).
  4. avg_cpu_by_component: for each distinct component compute the average metric_value where metric_name = "cpu_usage" and metric_value IS NOT NULL. Exclude NULLs. Provide one entry per component as {"component": string, "avg_cpu": number}. Sort this array by component name ascending.
  5. top10_event_ids: the 10 most frequent event_id values (after dedup rules) and their counts. Order by count descending, tie-breaker by event_id ascending.

Step C — Manipulate & Export (≈20 minutes)
- Create two exports from the DB:
  1. error_events_7days.csv — all events with level = "ERROR" whose timestamp >= (max_t - 7 days), where max_t is same as above. Columns (in this exact order): timestamp (ISO8601 UTC, format "YYYY-MM-DDTHH:MM:SSZ" or "YYYY-MM-DDTHH:MM:SS+00:00"), host, component, event_id, message, metric_value (empty or null allowed). Include all matching rows. Do not include header rows other than CSV header.
  2. summary_report.json — JSON object with two top-level keys:
     - top_hosts: array of the same objects as top5_hosts_error (full 5 entries).
     - hourly_errors: array identical to hourly_errors_last24 (24 entries).
- All exported files must be written in the current working directory.

Step D — Packaging & Single Command
- Provide a single one-line command that runs your entire pipeline (ingest → analyze → export → create test_submission.json). This must be runnable from the exam folder without arguments. Example forms allowed: "python3 run.py" or "./run.sh". Your run_command will be recorded in test_submission.json and the evaluator will run it to verify reproducibility.

Other constraints
- No network calls and no non-standard libraries.
- Scripts must exit cleanly with status 0 on success.
- The pipeline must be deterministic (same outputs every run on same input).

Estimated time: 90 minutes total (30 + 35 + 20 + packaging/notes).

### Submission Format
You must submit a single JSON file named test_submission.json in the working directory. This is the only file the automated evaluator will read for aggregated checking (besides opening your produced system_logs.db and exported files). The test_submission.json must exactly follow this structure and formatting rules:

Top-level keys and types:
- candidate_name: string
- language: string (e.g., "python3")
- run_command: string (one-liner used to run your pipeline)
- runtime_seconds: number (approximate total runtime you observed, can be integer)
- outputs: object containing:
  - unique_hosts: integer
  - top5_hosts_error: array of 5 objects, each {"host": string, "error_count": integer}, ordered by error_count desc then host asc
  - hourly_errors_last24: array of 24 objects, each {"hour": "YYYY-MM-DDTHH:00:00", "count": integer}, ordered ascending (oldest first)
  - avg_cpu_by_component: array of objects {"component": string, "avg_cpu": number}, one per component, sorted by component ascending. avg_cpu must be a numeric type (float).
  - top10_event_ids: array of 10 objects, each {"event_id": string, "count": integer}, ordered by count desc then event_id asc
- sample_error_csv_rows: array of up to 5 objects representing the first up to 5 rows of error_events_7days.csv in the order they appear there. Each object must include keys: timestamp, host, component, event_id, message, metric_value (number or null).
- files_produced: array of objects, each {"file": string, "bytes": integer} for the four required files (system_logs.db, error_events_7days.csv, summary_report.json, test_submission.json). Bytes must be the file size in bytes.
- notes: string (maximum 200 words). In this field you must document:
  - Schema choice (brief).
  - Deduplication rule implemented (explicitly state you removed exact duplicate rows and kept earliest timestamp on event_id collisions).
  - Timestamp parsing and timezone assumption (you must state that timestamps without timezone were treated as UTC and that timezone offsets were converted to UTC; note how many rows, if any, were dropped due to malformed timestamps).
  - Any other deterministic edge-case rules you implemented (max ~200 words).

Formatting and deterministic behavior rules (read carefully)
- Hour strings must be exactly "YYYY-MM-DDTHH:00:00" (24-hour time, zero-padded).
- Timestamps you output in CSV and sample rows must be in UTC; acceptable formats include "YYYY-MM-DDTHH:MM:SSZ" or with "+00:00". Be consistent.
- Arrays must be ordered exactly as stated (top5/top10 order and hourly ascending).
- All numeric fields must be numeric JSON values (not strings).
- The notes field must be <= 200 words.

Evaluator behavior (what you should expect)
- The evaluator will run your run_command to produce files.
- It will open system_logs.db and recompute the deterministic aggregates. Your outputs in test_submission.json will be compared to those recomputed values.
- It will verify exported files exist and sample rows match.
- Any deviation in ordering, field names, or formats may cause automated mismatches.

Scoring guidance (what is being checked)
- Correct DB ingest and data cleaning (types, dedup, uniqueness).
- Correctness of the five analytic outputs.
- Correct filtered CSV and JSON summary.
- Reproducible one-command workflow and adherence to format rules.
- Clear, concise notes documenting your deterministic choices.

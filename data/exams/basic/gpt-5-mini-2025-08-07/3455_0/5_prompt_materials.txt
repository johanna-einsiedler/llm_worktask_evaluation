### Strategic Elements (to distinguish real ability)
Multi-step dependencies and decision points that separate doers from knowers:
- Schema design affects query simplicity and performance. A candidate who can map analytics needs to a schema will produce simpler, correct SQL; someone who only knows theory may create a poor schema and struggle with queries.
- Handling missing/duplicate data: candidates must choose how to treat these and document their approach. Real practitioners will pick reasonable strategies and explain tradeoffs.
- Index choices: minimal but correct use (e.g., index on hostname+timestamp) indicates practical performance awareness.
- Reproducibility and packaging: someone who can perform the task will provide clear commands and include the exact SQL; someone who knows only conceptually may not make it trivially reproducible.
- Trade-off judgement: when asked to recommend a requirement change (e.g., raise minimum memory), the candidate should justify with specific metrics and a small cost/benefit rationale.

Edge cases to include (small but present so they can be resolved quickly):
- A few telemetry timestamps outside the expected window (should be ignored or flagged).
- Hosts present in telemetry but missing from inventory — candidate must decide to ignore, insert a placeholder inventory row, or flag as unknown.
- Slight timestamp format variance — requires parsing with tolerant code.

These elements force the candidate to make real decisions and implement them.

Pass threshold: ≥ 80/100.

Qualitative evaluation notes:

### Strategic Elements (to distinguish real ability)
Multi-step dependencies and decision points that separate doers from knowers:
- Schema design affects query simplicity and performance. A candidate who can map analytics needs to a schema will produce simpler, correct SQL; someone who only knows theory may create a poor schema and struggle with queries.
- Handling missing/duplicate data: candidates must choose how to treat these and document their approach. Real practitioners will pick reasonable strategies and explain tradeoffs.
- Index choices: minimal but correct use (e.g., index on hostname+timestamp) indicates practical performance awareness.
- Reproducibility and packaging: someone who can perform the task will provide clear commands and include the exact SQL; someone who knows only conceptually may not make it trivially reproducible.
- Trade-off judgement: when asked to recommend a requirement change (e.g., raise minimum memory), the candidate should justify with specific metrics and a small cost/benefit rationale.

Edge cases to include (small but present so they can be resolved quickly):
- A few telemetry timestamps outside the expected window (should be ignored or flagged).
- Hosts present in telemetry but missing from inventory — candidate must decide to ignore, insert a placeholder inventory row, or flag as unknown.
- Slight timestamp format variance — requires parsing with tolerant code.

These elements force the candidate to make real decisions and implement them.

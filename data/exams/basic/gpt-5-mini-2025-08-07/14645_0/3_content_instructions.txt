### Exam Title
Test planning practical — Basic level (90 minutes)

---

### Instructions for Candidate

Goal
- Produce a realistic, time-boxed test schedule and short strategy that converts the provided project brief into an executable test plan the team can use to meet the fixed release date.

Time limit
- 90 minutes total. You must record start and finish times in the submission_metadata (time_started / time_finished) and report time_taken_minutes.

Available tools
- Spreadsheet software (recommended to build a Gantt-like schedule) and a plain text editor. No other resources are available.

Step-by-step tasks and suggested time allocation
1. Read the project brief (Provided Materials) — 5 minutes.
2. State assumptions you make about anything unclear in the brief — 10 minutes.
   - Deliverable: list of assumptions.
3. Create a time-based test schedule (Gantt-like) showing tasks, start/end dates, durations, dependencies and resource assignments — 30 minutes.
   - Use spreadsheet thinking: show concrete dates, respect environment windows, public holiday, code-freeze and release date.
   - Assign tasks to the provided resources only (names given in brief).
   - Use working days only; 1 working day = 8 hours. Public holiday days are non-working.
4. Produce risk-based prioritisation and effort estimates — 30 minutes.
   - For each feature from the brief, list required test types, priority (1–5), and estimated effort (hours) for: test_design, test_execution, automation_setup (if any), and regression.
   - Provide a short (1–2 sentence) rationale for priority for the top 5 items.
   - Propose two concrete contingency options (what to reduce or drop if schedule is too tight, expected quality impact, and brief justification).
5. Produce a concise test strategy summary — 15 minutes.
   - Include entry and exit criteria for phases (e.g., test design complete, system testing entry, release exit criteria), and identify the key open risks and mitigations.
6. Finalize and assemble everything into a single JSON file named test_submission.json — remaining time.

Notes while working
- Be concrete. Dates must be in YYYY-MM-DD format and respect the environment availability and holiday in the brief.
- Use only the resource names given in the brief. Respect availability_percent for capacity calculations.
- Priorities: 1 = highest risk / highest priority, 5 = lowest.
- 1 working day = 8 hours. Use this for converting durations ↔ hours.
- You may optionally export or attach a CSV of your spreadsheet as a string inside optional_attachments, but the evaluator will primarily use the JSON.

---

### Expected Outcome

By the end you must produce a single valid JSON file test_submission.json that contains:

- submission_metadata with your name, email, start/finish timestamps and minutes used.
- assumptions array (≥3 recommended).
- resources list (use provided resource names).
- schedule array (concrete tasks with start/end dates, durations, dependencies and assigned resources).
- test_scope array listing each feature (use feature IDs exactly as given in brief), complexity, required test types and a priority (1–5).
- estimates array with estimated hours per feature-activity (activities limited to the set in the schema).
- risk_prioritisation array with priority and short rationale.
- contingency_options array with two options.
- entry_exit_criteria object mapping phase names to arrays of entry and exit criteria.
- strategy_summary string (max 500 words).
- submission must be syntactically valid JSON and follow the schema exactly (see Submission Format below).

Evaluator will check:
- Schedule is feasible vs code freeze, release, environment windows and public holiday.
- Resource assignments respect availability.
- Estimates are consistent with schedule durations and available tester capacity.
- Prioritisations and contingency options are risk-based and practical.
- Entry/exit criteria are concrete and measurable (e.g., “no open critical defects”, “≥90% regression pass”).
- Strategy summary ties schedule, risk and priorities together and contains a short communication plan for release day.

### Submission Format

You must submit a single file named test_submission.json containing an object that exactly follows the schema below. Field names and types must match.

Top-level object keys (required)
- submission_metadata: object
  - candidate_name: string
  - candidate_email: string
  - time_started: string (ISO-like timestamp or YYYY-MM-DDTHH:MM — free-text but must be present)
  - time_finished: string (same format)
  - time_taken_minutes: integer (whole minutes)
- assumptions: array of strings
- resources: array of resource objects
  - Each resource object:
    - name: string (one of: "Alice", "Bob", "Charlie")
    - role: string (e.g., "Tester" or "Automation Engineer")
    - availability_percent: integer (e.g., 100 or 50)
- schedule: array of schedule task objects
  - Each task object:
    - id: integer (unique, 1,2,3,...)
    - name: string (short task name)
    - start_date: string (YYYY-MM-DD)
    - end_date: string (YYYY-MM-DD)
    - duration_days: integer (working days)
    - dependencies: array of integers (task ids that must finish before this starts; empty array if none)
    - assigned: array of strings (resource names, choose only Alice/Bob/Charlie)
  - Requirements:
    - Dates must be weekdays and respect environment windows and holiday (2025-10-23 is non-working).
    - duration_days must equal the number of working days between start_date and end_date inclusive.
- test_scope: array of feature objects (one per feature in brief)
  - Each feature object:
    - feature_id: string (must be "F1","F2","F3","F4","F5","F6")
    - name: string (use brief names)
    - complexity: string ("L","M","H")
    - required_test_types: array of strings chosen from: ["unit","integration","system","acceptance","regression","perf","security","exploratory"]
    - priority: integer 1–5 (1 = highest)
- estimates: array of estimate objects
  - Each estimate object:
    - feature_id: string (as above)
    - activity: string (one of: "test_design","test_execution","automation_setup","regression","exploratory")
    - estimated_hours: integer (hours; 1 working day = 8 hours)
  - Notes:
    - If an activity does not apply for a feature, omit it.
    - Totals across estimates should be consistent with schedule durations and resource availability.
- risk_prioritisation: array of objects
  - Each object:
    - feature_id_or_risk: string (feature id like "F2" or short risk name e.g., "Third-party API instability")
    - priority: integer 1–5 (1 = highest)
    - rationale: string (one or two short sentences)
- contingency_options: array of two objects (exactly two)
  - Each object:
    - option_id: string (e.g., "C1", "C2")
    - description: string (what will be removed/delayed)
    - expected_quality_impact: string (brief)
    - rationale: string (brief justification)
- entry_exit_criteria: object mapping phase names to criteria objects
  - Each phase key value:
    - entry: array of strings (concrete conditions)
    - exit: array of strings (concrete conditions, e.g., "No open critical defects", "Regression pass ≥ 90%")
- strategy_summary: string (max 500 words)
  - Must include a one-paragraph communication plan for release day: who will be notified and when (name(s) should be roles or resource names).
- optional_attachments: string (optional). You may paste a CSV export of your spreadsheet here if you wish; evaluator will ignore if empty.

Formatting, validation and objective checks
- The JSON must parse cleanly. Keys must match exactly.
- Dates must use YYYY-MM-DD.
- Priorities and complexities must be within allowed values.
- Use feature IDs exactly as provided in the brief.
- Use only provided resource names for assigned fields.
- The evaluator will verify that schedule dates respect:
  - Code freeze 2025-10-20,
  - Test Env A availability 2025-10-21 to 2025-10-30,
  - UAT availability 2025-10-27 to 2025-11-01,
  - Public holiday 2025-10-23 is non-working.

Example minimal content (not exhaustive)
- assumptions: ["Defect fix turnaround 2 working days unless critical"]
- schedule: [{id:1, name:"Test design F1", start_date:"2025-10-21", end_date:"2025-10-22", duration_days:2, dependencies:[], assigned:["Alice"]}, ...]
- test_scope: [{feature_id:"F1", name:"User login & sessions", complexity:"L", required_test_types:["integration","system","regression"], priority:1}, ...]

Submission
- Save your single JSON object to a file named test_submission.json and upload/submit that file.
- Do not submit multiple files. If you include a CSV of the spreadsheet, paste it into optional_attachments as a string inside the JSON.

Good luck.

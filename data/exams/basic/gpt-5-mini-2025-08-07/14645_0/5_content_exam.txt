### Exam Title
Test Planning Practical — Basic (90-minute remote practical)

### Instructions for Candidate
You have 90 minutes total. Use only the tools allowed: a spreadsheet application and a text editor. You may draft in a spreadsheet but your final submission must be a single JSON file named test_submission.json (see Submission Format below).

Read the Project Brief (provided below) first (5 minutes). Then complete the three hands-on tasks and the short metadata/assumptions section. Recommended time split:
- Read brief & assumptions — 5 minutes
- Task 1: Test strategy / plan (text) — 30 minutes
- Task 2: Test schedule & resourcing (spreadsheet-style tasks[]) — 40 minutes
- Task 3: Risk prioritization + contingency + metrics — 15 minutes

Do the tasks in this order. Keep answers concise and factual. Do not attach any files other than test_submission.json.

Tasks (practical, required)
1. Metadata & Assumptions
   - Provide candidate_name and exam_start (date/time).
   - List 4–8 short assumptions you make beyond the brief (e.g., working hours, no additional hires, defect severity definitions).
2. Produce a short Test Strategy text (300–800 characters)
   - Must include: scope/objectives, key test types to be used, measurable entry and exit criteria, brief automation approach, and reporting metrics/cadence.
3. Build a resource-aware Test Schedule (tasks array)
   - Create concrete test tasks that cover the testing lifecycle required by the brief: environment setup, test design/case creation, functional/integration execution, regression (manual + automation), UAT support, reporting, and any automation development tasks needed.
   - For each task include: ID (T1, T2, ...), short description, owner (exactly one of: "Tester A", "Tester B", "Automation"), type (choose from: "test-design", "env-setup", "test-execution", "automation", "regression", "UAT-support", "reporting"), estimate_hours (numeric), duration_days (calendar days used), earliest_start_offset (integer days from project_start_date; 0 = project start), dependencies (array of other task IDs), parallelizable (true/false).
   - Respect the constraints in the brief (environment lead times, automation capacity, dev fix SLA, two testers only). Do not assign more than two owners or invent more testers.
   - Use offsets relative to project_start_date; you may also include schedule_summary with resolved ISO dates (see Submission Format).
   - Identify critical path tasks and include buffer days for defect cycles/environment risk.
4. Risk-based prioritization & contingency
   - Use the provided feature IDs (F1–F6). For each feature provide business_priority, a testing_priority (1–5; 1 = highest), tests_to_run (list of test types or specific focus), and a short note.
   - Provide a concise contingency_plan describing what you will drop, reduce, or compress if testing slips by 1–3 days and if it slips by >3 days. Be specific (e.g., "defer F4 UI polish to post-release", or "reduce regression scope to smoke + high-risk scenarios only").
5. Metrics, reporting, and final comments
   - State what metrics you will report and the reporting cadence (e.g., daily: tests executed, pass/fail, open defects by severity). Provide final_comments summarizing any trade-offs.

Keep the output objective and verifiable: concrete task durations, owners, dependencies, and priorities.

### Expected Outcome
A single valid JSON file named test_submission.json that contains:
- metadata: candidate_name, exam_start, project_start_date
- assumptions: array of short strings
- test_strategy: 300–800 character string
- tasks: array of task objects (IDs T1, T2, ...)
- schedule_summary: overall start/end, total_effort_hours, critical_path (array of task IDs), buffers_days
- risk_prioritization: array mapping F1–F6 to priority, tests_to_run, note
- contingency_plan: string
- metrics_and_reporting: string
- final_comments: short string

Your schedule must be executable within the constraints of the Project Brief (code freeze, release date, environment lead times, 2 testers, automation limits). If you cannot meet the release date without trade-offs, describe those trade-offs clearly in final_comments and the contingency_plan.

You will be graded against objective rubrics: coverage of necessary tasks, realistic estimates, correct handling of dependencies and environment lead times, resource allocation respecting two testers, clear entry/exit criteria, and a concrete contingency plan.

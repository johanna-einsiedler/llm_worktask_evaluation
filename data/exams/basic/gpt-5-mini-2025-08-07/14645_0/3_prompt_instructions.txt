Here is the exam overview written by another exam designer:
<examoverview>
### Exam Purpose
Confirm that the candidate can take a short project brief and produce a practical, delivery-oriented test strategy and schedule that align scope, resources, dependencies and delivery dates. In short: can the candidate plan and schedule testing activities (with priorities and contingencies) so the project can meet its committed release date.

This verifies real-world capability to:
- Translate scope and deadlines into a test plan and actionable schedule.
- Allocate limited QA resources across tasks and dependencies.
- Use risk-based prioritization and contingency planning when schedule pressure exists.
- Produce clear, evaluable artifacts that a project manager or dev lead could act on.

---

### Core Competencies to be Tested
- Interpreting scope, constraints and delivery commitments.
- Breaking testing into discrete tasks (test design, environment setup, execution, automation, regression, UAT support, reporting).
- Estimating task durations and effort reasonably for a junior-level tester.
- Creating a resource-aware schedule (start/end dates, dependencies, parallelism) in a spreadsheet.
- Prioritizing tests using risk and business impact.
- Defining entry/exit criteria and contingency/mitigation plans.
- Clear, concise documentation of assumptions and decisions.

---

### Recommended Structure (Basic exam — to be completed in 90 minutes)
Overall: 1 project brief provided to candidate + 3 hands-on tasks. Candidate delivers a single JSON file named test_submission.json containing structured answers and embedded schedule/task data (described below).

Time allocation (recommended):
- Read brief and assumptions: 5 minutes
- Task 1 — Test strategy / plan (text): 30 minutes
- Task 2 — Test schedule & resourcing (spreadsheet-style JSON array): 40 minutes
- Task 3 — Risk-based prioritization + contingencies + final checks: 15 minutes

Total: 90 minutes

Number and sequence of tasks:
1. Read the provided Project Brief.
2. Produce a short Test Strategy document (key headings only) that states scope, objectives, entry/exit criteria, test types, automation approach, and reporting metrics.
3. Produce a detailed, resource-aware Test Schedule: list test tasks (IDs, descriptions), owner(s), estimates (hours/days), start and end (relative dates), dependencies, and identify critical path and any buffer days.
4. Produce a Risk-Priority mapping for features / components and a short contingency plan describing what to cut or compress if schedule slips.
5. Submit all answers in one JSON file (test_submission.json). (Examiner will provide the exact JSON schema the candidate should use.)

Expected deliverables (all packed as JSON):
- metadata (name, start time, assumed project start date)
- assumptions (short list)
- test_strategy (string / bullet text)
- tasks[] (array of task objects; see schema below)
- schedule_summary (critical_path array; overall start/end dates; total test effort hours)
- risk_prioritization[] (feature -> priority / tests to run)
- contingency_plan (string)
- metrics_and_reporting (string)

Note: Candidate may prepare the schedule in spreadsheet but must convert it to the JSON tasks[] format for submission.

---

### Practicality — How this is hands-on and not a quiz
- Candidate is given a short but realistic project brief with exact constraints: release date, code-freeze, number of QA resources, environment availability, developer bug-fix SLA, automation percentage, and a list of features with business-criticality and estimated dev completion dates.
- Candidate must produce actual schedule entries (start/end dates or offsets), assign named resources (e.g., Tester A, Tester B), and set dependencies so the schedule is executable.
- The task requires concrete estimation and resource balancing: the candidate cannot rely on describing concepts only — they must assign durations and demonstrate awareness of critical path and resource contention.
- The candidate must define entry/exit criteria and trade-offs (what to reduce or defer) and build a realistic contingency plan that aligns to given developer SLAs and environment availability.
- Output is structured, enabling automated or semi-automated evaluation rather than just free-form answers.

---

### Strategic elements (decision points that separate thinkers from knowers)
Include these elements in the brief so candidates must make and document decisions:

- Fixed release date and code freeze date (e.g., release in 4 weeks; code freeze at 3 weeks). Candidate must schedule testing within this fixed window.
- Small QA team (e.g., 2 testers). Candidate must balance parallel vs. sequential tasks.
- Partial automation capability (e.g., 40% regression automated; 60% manual). Candidate must schedule handover and automation runs differently.
- Environment lead time (e.g., production-replica test environment available only on day X, or takes 3 days to provision). Candidate must schedule environment setup tasks before execution can start.
- Developer bug-fix turnaround SLA (e.g., 2 working days). Candidate must account for cycles of defect detection & fix/regression retest.
- Features with different business criticalities (High / Medium / Low). Candidate must apply risk-based prioritization.
- UAT or stakeholder acceptance window near the end (e.g., 3 days). Candidate must allocate UAT support and bug-fix time.
- A known high-risk feature (e.g., payment gateway integration) that requires earlier focus and integration tests.

Decision points required of the candidate:
- Which tests are on the critical path and must complete before code freeze?
- Which tests can be deferred or run at a lower depth if the schedule slips?
- How to parallelize tasks without exceeding available QA headcount.
- How much buffer/time to include for defect cycles and environment delays.
- Whether to shift some manual regression to automation runs in late hours (trade-off decision).
- How to report progress and acceptable exit criteria to allow go/no-go decisions.

These decision points distinguish candidates who can apply trade-offs concretely vs those who can only discuss them.

### Required JSON submission schema (test_submission.json)
Provide this schema to candidates so they can build directly to it. Examiner uses same schema to evaluate.

Top-level keys (required):
- candidate_name (string)
- exam_start (ISO date/time or date string) — optional but recommended
- project_start_date (ISO date) — must match brief
- assumptions (array of short strings)
- test_strategy (string) — 300–800 characters; should include scope, objectives, test types, entry/exit criteria, reporting metrics
- tasks (array of objects) — each object:
  - id (string)
  - description (string)
  - owner (string: "Tester A" / "Tester B" / "Automation")
  - type (string: e.g., "test-design", "env-setup", "test-execution", "automation", "regression", "UAT-support", "reporting")
  - estimate_hours (number)
  - duration_days (number) — calendar days used for scheduling (candidate chooses)
  - earliest_start_offset (integer) — days from project_start_date when task can start (0 = project start)
  - dependencies (array of task ids)
  - parallelizable (boolean) — can be performed in parallel with other tasks if resource available
- schedule_summary (object):
  - schedule_start (date)
  - schedule_end (date)
  - total_effort_hours (number)
  - critical_path (array of task ids)
  - buffers_days (number) — total buffer days included
- risk_prioritization (array of objects):
  - feature_id (string)
  - business_priority ("High"/"Medium"/"Low")
  - testing_priority (1-5, 1 highest)
  - tests_to_run (array of strings)
  - note (short string)
- contingency_plan (string)
- metrics_and_reporting (string) — what metrics will be reported and cadence
- final_comments (string) — short summary of any trade-offs

Provide examples of valid values in the exam instructions.

### Evaluation Insights — what to check and rubrics
Overall pass target: a competent junior candidate should score >80%. Use weighted scoring.

Proposed weightings:
- Schedule & resource allocation correctness and completeness: 40 points
- Test strategy clarity and suitability (scope, entry/exit criteria, test types): 30 points
- Risk-based prioritization and contingency planning: 15 points
- Assumptions, clarity, and format conformity (JSON correctness): 10 points
- Metrics and reporting clarity: 5 points
Total = 100 points. Passing threshold: >=80 points.

Evaluator checklist and scoring details:

1. Schedule & resourcing (40)
   - Tasks cover necessary activities (env setup, test design, execution, regression, automation, UAT support, reporting) (8 points)
   - Estimates are realistic vs given constraints (not wildly optimistic) (8 points)
   - Dependencies defined and feasible (8 points)
   - Resource allocation respects headcount (e.g., no more than two simultaneous full-day testing tasks per day without split ownership) (8 points)
   - Critical path identified and start/end dates meet code freeze & release commitments or show trade-offs (8 points)

   Scoring guidance:
   - Full marks if schedule meets release date with realistic buffers and resource constraints.
   - Partial marks if schedule meets date only by exaggerating parallel work beyond given resources or missing environment lead time.
   - Zero for missing schedule or obviously impossible timing.

2. Test strategy (30)
   - Clear scope and objectives (6)
   - Entry and exit criteria are explicit and measurable (6)
   - Appropriate selection of test types (6)
   - Automation approach explained and aligned to automation capability (6)
   - Reporting metrics & cadence declared (6)

   Scoring guidance:
   - Entry/exit criteria should include criteria like "all critical test cases pass", "no P0 defects open", or "UAT sign-off", etc.
   - Automation approach should show what will be automated vs manual and when.

3. Risk prioritization & contingency (15)
   - Mapping of features to priority and tests (6)
   - Clear plan of what to cut/scale back if time pressured (5)
   - Contingency plan covering defect cycles & environment issues (4)

   Good answers include explicit "if slip > 2 days, defer UI polish (F4) and reduce regression depth to smoke + high-risk scenarios" etc.

4. Assumptions and JSON format (10)
   - Candidate listed assumptions (3)
   - JSON is valid and follows the required schema (7)

5. Metrics & reporting (5)
   - Candidate states clear pass/fail metrics and reporting cadence (e.g., daily test progress, open defects by severity, smoke pass) and how it informs go/no-go.

Grading notes:
- If the schedule uses offsets instead of dates, convert offsets to dates using the provided project_start_date.
- If candidate misses environment lead time, deduct in Schedule & resourcing.
- If task durations are underestimates but dependencies and resource constraints are correct, deduct proportionally.

Red flags (automatic deduction or fail if severe):
- No dependencies or resources omitted entirely.
- Single QA resource assigned to perform two full-time parallel tasks across the entire schedule without split hours.
- No buffer for defect turnaround or environment provisioning.
- Entry/exit criteria missing or vague.
- Contingency plan absent.

Positive signs (for higher marks):
- Candidate identifies critical path and suggests realistic compression options (e.g., shift regression to night automation runs but with caveats).
- Proper accounting for bug-fix cycles (e.g., schedule includes days for triage, dev fix, regression).
- Explicit statements about assumptions that differ from brief and their impact.

---

### Example examiner workflow for one submission
1. Open test_submission.json; check metadata & assumptions.
2. Validate JSON against schema.
3. Inspect tasks[]: confirm tasks cover the testing lifecycle and environment tasks, check estimates and dependencies.
4. Convert offsets to calendar dates and check schedule_end <= release date; ensure code freeze tasks finish before code freeze date.
5. Check concurrency vs headcount: sum of estimated tester hours per day should not exceed capacity significantly.
6. Verify critical_path is plausible given dependencies.
7. Read test_strategy and contingency_plan for clear, actionable guidance.
8. Score each section using the rubric and provide pass/fail and feedback.

---

### Practical guidance for exam creators
- Keep the brief compact (one page) with clearly stated constraints. Too much optional detail increases grading time.
- Provide the JSON schema to the candidate as part of the brief so they can format responses correctly.
- Use the example inputs above (2 testers, 4-week release, env lead times, partial automation, list of 5–6 features) — this is complex enough to be realistic yet solvable within 90 minutes.
- Allow spreadsheets for drafting but require JSON submission to make evaluation consistent and fast.
- Consider giving candidates a small amount of leeway: accept duration_days or start/end dates or offsets — but require consistency and clarity.

---

This design produces a focused, time-boxed, practical exam that requires candidates to perform the actual activities of planning testing within scope and delivery constraints, not just describe them. It gives evaluators a clear rubric and structured outputs to assess competency reliably at the junior/entry-level standard (target >80%).

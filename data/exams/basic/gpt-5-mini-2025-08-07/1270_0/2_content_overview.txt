### Exam Purpose
This basic practical exam verifies that a candidate can design, implement, and maintain a small but realistic software component that performs CRUD (create, read, update, delete) operations, persists data, validates inputs, and provides reproducible behavior. It confirms the candidate can turn requirements into working code, handle simple data dependencies, produce a runnable deliverable, and demonstrate the system works via an automated scenario and lightweight tests — skills required in junior/entry-level programming roles (many of which require a Bachelor’s degree).

### Core Competencies to be Tested
- Implementing working software that performs required tasks (coding to spec)
- Data persistence and basic I/O (reading/writing JSON or CSV / SQLite)
- Input validation and simple error handling
- Basic scripting/automation to demonstrate workflows (reproducible runs)
- Ability to produce runnable deliverables and clear run instructions (README)
- Basic test or assertion-based verification of correct behavior
- Code organization and clarity (modularity, comments, naming)

### Recommended Structure
Total time: 90 minutes. The exam is a single, self-contained repository (or set of files) the candidate creates on their machine. Candidate must submit a single JSON file named test_submission.json containing code and required outputs (schema described below).

Number of tasks: 3 small practical tasks to be completed in sequence. Expected deliverables: source code files (one main program and optional modules), a demonstration script that performs a fixed scenario, a few simple tests or assertions, a short README with run instructions, and the test_submission.json with captured outputs.

Suggested time allocation:
- Task 1 (Core CLI + persistence): 45 minutes
- Task 2 (Validation, import/export): 20 minutes
- Task 3 (Demo script + tests + packaging submission JSON): 25 minutes

Tasks (high level)
1. Core Inventory Manager (required)
   - Implement a simple command-line inventory manager with persistent storage (JSON file or SQLite).
   - Required operations: add item, update item, remove item, get item by id, list items.
   - Items must include: id (string), name (string), quantity (integer), price (decimal).
2. Import/Export & Validation (required)
   - Implement import from a CSV file and export to JSON. (CSV format spec provided below.)
   - Enforce validation: unique id, non-negative quantity, price >= 0, required fields present. On invalid input, fail gracefully with clear error messages.
3. Demonstration script & tests (required)
   - Provide a script (demo_runner.sh / demo_runner.py or similar) that executes a deterministic scenario (sequence of operations) and prints the final inventory JSON.
   - Provide at least 4 simple assertions or tests demonstrating correct behavior (e.g., adding duplicate id fails, updating quantity works, import merges or rejects duplicates per your documented choice).

Expected deliverables that the candidate must include in test_submission.json (full schema below):
- Candidate metadata
- Source files content (inventory program, demo runner, tests, README)
- Commands to reproduce demo
- Captured stdout for demo and test runs
- Final inventory JSON (after demo)
- Short notes on assumptions and any limitations

Note: Candidate should use only the environment’s standard libraries. Recommend Python 3 for brevity; other languages are acceptable but must be documented in submission.

### Practicality — making this hands-on
- The candidate must write code that runs locally and manipulates a persistent data file. This ensures the exam is practical: it requires real code execution rather than multiple-choice or purely theoretical answers.
- The evaluator will reproduce the candidate’s steps by running the provided commands which operate on files the candidate submitted.
- The demo script must be fully automated (no interactive prompts) to enable straightforward reproduction and automatic grading.
- The CSV import introduces realistic data dependency (external file ingestion). The candidate must show handling of malformed rows or conflicting IDs.

CSV import format (exact, to avoid ambiguity):
- Columns: id,name,quantity,price
- Example row: I001,Widget A,10,2.50
- The candidate must include a small sample CSV (3–5 rows) they used in the demo; include it in test_submission.json as a file.

### Strategic elements (distinguishing real performers)
The tasks are simple but include multi-step and decision points that reveal the candidate’s practical skills:

- Choice & reasoning for persistence: JSON vs SQLite. A candidate who chooses SQLite should show how to initialize the DB and perform safe updates. A candidate who chooses JSON should show atomic write (write-temp-rename) to avoid corruption — this demonstrates practical thinking about persistence.
- Validation and error handling: candidates must decide whether import rejects or merges duplicates; they must document the chosen behavior and implement it. Real performers will explicitly handle edge cases (e.g., numeric parsing errors, missing fields).
- Reproducible automation: candidates must create a demo runner that executes a defined scenario. Candidates who just implement functions but cannot script the scenario show weaker operational capability.
- Test coverage: small assertion tests are required. Candidates who provide meaningful tests that run automatically show they understand verification.
- Minimal concurrency-safety: basic file-locking or atomic write approach is a distinguishing, but optional, plus for candidates who implement it.

Decision points for candidates (they must document their choice in README/notes):
- How to store data (JSON vs SQLite). If JSON: how to avoid data corruption? If SQLite: ensure schema creation is idempotent.
- On import duplicates: overwrite, skip, or error? Candidate must pick and document behavior.
- Error reporting format (exit codes and stderr messages vs printing JSON error objects).

### Practical Elements to Include (explicit checklist for exam creator)
- Provide candidate with initial empty project folder or ask them to create it.
- Require the candidate to implement:
  - One main executable file (inventory.py or inventory.js) that accepts command-line arguments or a subcommand style (e.g., inventory.py add --id I001 --name "X" --qty 5 --price 3.2).
  - Persistent storage file used by program (inventory.json or inventory.db created at runtime).
  - CSV import (import.csv included in submission).
  - A demo runner script that runs the following sequence (this is the standard scenario the evaluator will reproduce):
    1. Ensure starting with empty storage (delete any existing data file).
    2. Add item I100, name "Screwdriver", quantity 15, price 5.50
    3. Add item I101, name "Hammer", quantity 20, price 9.99
    4. Update I100 quantity to 12
    5. Attempt to add I101 again (should fail or be handled per documented policy)
    6. Remove I101
    7. Import provided CSV (3 rows: one new, one duplicate id, one malformed row)
    8. Export final inventory to final_inventory.json and print its content to stdout
  - At least 4 assertions/tests that run non-interactively (e.g., a small test file that runs commands and checks return codes and final state).
  - README with precise commands to run demo and tests.
- Candidate must capture stdout for the demo and include these transcripts in test_submission.json.

### Submission JSON Schema and Requirements
Name the file test_submission.json and include at minimum the following fields:

- candidate_name: string
- email: string
- time_taken_minutes: integer
- language: string (e.g., "Python 3.10")
- run_commands: array of strings (commands an evaluator can run to reproduce demo; e.g., ["python3 demo_runner.py"])
- files: array of objects { "filename": string, "content": string } — include all source files, sample CSV, README, and demo scripts
- demo_stdout: string (exact stdout captured when running the demo script)
- test_results: array of objects { "name": string, "passed": boolean, "output": string }
- final_inventory_json: object or array (the final inventory data structure produced by demo; embed JSON)
- notes: string (assumptions, known issues, design choices like merge vs reject on duplicates)
- self_score_estimate: integer (0–100) — optional candidate estimate of score

Example minimal test_submission.json (excerpt):
{
  "candidate_name": "Jane Doe",
  "email": "jane@example.com",
  "time_taken_minutes": 78,
  "language": "Python 3.10",
  "run_commands": ["python3 demo_runner.py"],
  "files": [
    {"filename": "inventory.py", "content": "...source..."},
    {"filename": "demo_runner.py", "content": "..."},
    {"filename": "import.csv", "content": "I200,Plier,5,3.25\n..."},
    {"filename": "README.md", "content": "..."}
  ],
  "demo_stdout": "Final inventory: [ ... ]",
  "test_results": [
    {"name":"add_duplicate_id","passed":true,"output":"Duplicate id rejected"},
    ...
  ],
  "final_inventory_json": [ { "id": "I100", "name": "Screwdriver", "quantity": 12, "price": 5.5 }, ... ],
  "notes": "On import, duplicates are skipped. Data stored in inventory.json via atomic rename."
}

Evaluator must be able to save the provided files and run the listed commands to reproduce demo and run tests.

### Evaluation Insights — What to inspect and how to score (rubric)
Total: 100 points. Passing for basic exam: >= 80 points.

1. Functional correctness (60 points)
   - Core commands implemented and behave as specified: add/get/update/remove/list (40 pts)
     - Each operation: add (10), get (10), update (10), remove (10)
   - Persistence works: data file is created and subsequent runs reflect stored state (10 pts)
   - Export/import behave to spec (10 pts)

2. Validation & error handling (15 points)
   - Unique ID enforcement and proper handling of duplicates (5)
   - Quantity and price validation (non-negative, numeric) with clear errors (5)
   - Graceful handling of malformed CSV rows (5)

3. Demonstration & tests (15 points)
   - Demo runner executes the required sequence and outputs final inventory (7)
   - At least 4 automated assertions/tests that run and correctly reflect behaviors (8)

4. Code quality & documentation (10 points)
   - README with exact run instructions and explanation of design choices (4)
   - Code is readable, modular, and commented (3)
   - No reliance on external libraries beyond standard library unless documented/allowed (3)

Scoring notes:
- Deduct points for runtime errors when evaluator reproduces the demo.
- If candidate selects SQLite, require scripts to initialize DB on first run (no manual steps). If this works, award full persistence points.
- Partial credit allowed (e.g., if add/get/update work but import/export missing, award partial).

Observable outputs that indicate competence
- The demo_stdout shows the expected sequence of operations and final inventory JSON that matches the evaluator’s expected final state given the scenario.
- test_results all passing and non-flaky when re-run.
- Files array contains runnable source and a clear README. The run_commands work as-is.
- Code handles invalid inputs with clear errors (stderr or exit codes).
- Data file produced (inventory.json or inventory.db) contains the persisted state consistent with demo.

### Minimal evaluator checklist (quick reproduction)
1. Save files from test_submission.json to a temp folder.
2. Run the run_commands in order (or the demo_runner command).
3. Verify demo_stdout matches produced stdout; ensure final_inventory_json equals produced final JSON file.
4. Run tests script(s) and check test_results.
5. Score according to rubric.

This design ensures hands-on coding, data persistence, error handling, scripted reproducibility, and simple test coverage within a 90-minute window. It differentiates candidates who can implement working software with operational considerations from those who only understand concepts theoretically.

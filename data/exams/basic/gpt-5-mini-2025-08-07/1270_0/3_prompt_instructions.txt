<examoverview>
### Exam Purpose
This basic practical exam verifies that a candidate can design, implement, and maintain a small, working software component that performs everyday programmer tasks: designing a data model, implementing CRUD operations, validating input, persisting state, and providing a reproducible interface (CLI) to use the solution. It confirms the real-world capability to build and maintain a simple inventory/tracking utility that can be used to store, retrieve and update item data—skills directly transferable to tasks such as inventory tracking, small data services, or device-control helpers.

### Core Competencies
The exam will test these concrete skills:
- Problem decomposition and program design (data model, CLI contract)
- Implementation of functional requirements (add/list/update/delete/search)
- Local data persistence (file-based or embedded DB) and correct load/save semantics
- Input validation and error handling (robustness)
- Reproducible operation (clear run instructions, deterministic outputs)
- Basic automated verification (produce outputs that can be machine-checked)
- Simple code quality and organization sufficient for maintainability
- Packaging minimal run instructions and a small test log as JSON for remote evaluation

These reflect the minimum expected for an entry-level programmer who will be asked to write and maintain small services and scripts.

### Recommended Structure
Total time allowed: 90 minutes.

High-level layout (what the candidate should do and in what order):
1. Setup & design — (5–10 minutes)
   - Choose a supported language available in the execution environment (e.g., Python, Node.js, Java).
   - Decide on persistence format (JSON file or SQLite recommended).

2. Implementation — (45–55 minutes)
   - Create a single program (or small module + CLI wrapper) that provides the required functionality.
   - Implement a small, deterministic storage format and APIs/commands for:
     - add item
     - list items
     - update item quantity (or other field)
     - delete item
     - search/filter by SKU or name
     - save/load to disk
   - Ensure input validation and clear error messages for invalid operations.

3. Self-tests & sample run — (15–20 minutes)
   - Run the program with a small set of commands that demonstrate each required capability.
   - Save or capture the outputs of those runs.

4. Submission packaging — (5–10 minutes)
   - Create test_submission.json with required fields (see exact schema below).
   - Ensure code files, any generated data file (e.g., data.json or inventory.db), and test_submission.json are present in the submission bundle.

Number of tasks (delivered as a single integrated task):
- One integrated coding task (the inventory manager) with multiple required operations. This keeps it hands-on and realistic without being fragmented.

Expected deliverables (what the candidate will submit):
- Source files implementing the program (language-appropriate; single directory).
- Any generated persistence file(s) created during their sample run (optional but recommended).
- test_submission.json — a structured JSON file (exact schema below) that includes run instructions, the commands the candidate executed, the program outputs (or short excerpts), and self-assessment.

Make the exam language-agnostic but recommend Python for time-limited tasks due to high productivity and standard libraries (JSON/SQLite).

### Practicality — How this is hands-on (not a quiz)
- Candidate must write runnable code that performs each operation and persists data. There are no multiple choice or conceptual questions.
- Graders can execute the candidate’s program (or automated grader script) against predefined test cases to confirm behavior.
- The candidate must demonstrate the program’s state persistence after restart (save/load) by performing operations, exiting/restarting, and showing the persisted state.
- Because the candidate has no internet, they must rely on their ability to program using only builtin libraries—an authentic, practical constraint.

### Strategic elements (multi-step decisions that separate knowing vs doing)
Include these decision points and multi-step requirements in the task so graders can distinguish real implementers from those who only understand theory:

1. Data model & persistence choice
   - Candidate chooses JSON file or SQLite DB. They must implement load/save semantics and show correctness after program restart (persistence test).
   - The grader can inspect the persisted file to validate structure.

2. State transitions and concurrency avoidance
   - Candidate must ensure updates are atomic enough for a single-user CLI (e.g., write-to-temp-then-rename for file writes). This shows practical thinking about real-world file integrity.

3. Input validation and error paths
   - Candidate must check for duplicate SKUs, invalid quantities (negative), missing fields; report errors with non-zero exit codes on failures.

4. Reproducible CLI contract
   - The CLI should accept commands in a way the grader can script (e.g., command-line arguments or a single-run mode that accepts a sequence of commands from stdin). This allows an automated grader to run test scenarios deterministically.

5. Demonstrated persistence test
   - Candidate must run: add item -> save -> run a second invocation -> list items -> show item present. This demonstrates that the candidate wrote working persistence/load logic.

6. Minimal automated verification
   - Candidate should include a short script or provide explicit command sequence and captured outputs in test_submission.json to demonstrate working behavior and allow fast manual or automated checking.

These elements require the candidate to program design choices and implement them correctly rather than simply answering conceptual questions.

### Detailed Required Functionality (Basic scope)
The program must implement the following, reachable within 90 minutes:

Core features (required):
- Data model for items: at minimum fields SKU (string, unique), name (string), quantity (integer >= 0), optional price (decimal) or description.
- Commands:
  - add --sku <SKU> --name <NAME> --qty <N> [--price <P>]
  - list [--sort sku|name|qty]
  - update --sku <SKU> --qty <new_qty> (or --change +N/-N)
  - delete --sku <SKU>
  - find --sku <SKU> or find --name <substring>
- Persistence:
  - Save to a local file (JSON preferred) or SQLite DB.
  - On startup, program loads existing data file if present.
- Return status:
  - Commands must return exit codes: 0 for success, non-zero for error.
  - Appropriate stderr messages for errors.
- Deterministic CLI output:
  - Output should be machine-parseable (e.g., JSON lines or a simple table with consistent separators) so grader can check outputs.
- Simple input validation and informative error messages.

Optional (bonus) features (not required for passing but increase score):
- CSV import/export
- Unit tests or a small automated test script
- Atomic writes (write-to-temp-and-rename)
- Sorting and pagination support on list

Time allocation recommendation:
- Implement core commands + persistence: 45–55 minutes
- Validate and run sample scenarios: 15 minutes
- Write submission JSON and tidy files: 10–15 minutes

### test_submission.json — exact schema for candidate to produce
Require this exact filename and JSON keys in submission root to simplify automated grading. Candidate must include the fields exactly as described.

Required fields:
- language: string — language used (e.g., "python3")
- entry_point: string — command to run the program (for grader; e.g., "python3 inventory.py")
- persistence_file: string — filename used to store data (e.g., "data.json")
- commands_run: array of objects — chronological commands the candidate ran for demonstration, each object:
  - cmd: string — the exact command-line or invocation used
  - stdout: string — the captured standard output of that run (can be a short excerpt if long)
  - stderr: string — captured standard error (empty string if none)
  - exit_code: integer — exit code returned
- short_description: string — ≤ 200 words describing how to run the program and design choices (persistence, format)
- self_assessment: object:
  - implemented_required: boolean
  - bonus_features: array of strings (list of optional features implemented)
  - known_issues: string — any known limitations or bugs
- time_taken_minutes: integer — candidate's estimate of total time used

Example (short) test_submission.json structure:
{
  "language": "python3",
  "entry_point": "python3 inventory.py",
  "persistence_file": "inventory.json",
  "commands_run": [
    {
      "cmd": "python3 inventory.py add --sku SKU001 --name \"Widget\" --qty 10",
      "stdout": "Added SKU001",
      "stderr": "",
      "exit_code": 0
    },
    {
      "cmd": "python3 inventory.py list --format json",
      "stdout": "[{\"sku\":\"SKU001\",\"name\":\"Widget\",\"qty\":10}]",
      "stderr": "",
      "exit_code": 0
    }
  ],
  "short_description": "...",
  "self_assessment": {
     "implemented_required": true,
     "bonus_features": ["csv_import"],
     "known_issues": "search is case-sensitive"
  },
  "time_taken_minutes": 78
}

(Provide the above schema textually to the candidate; graders should require this JSON.)

### Practical elements to include (to ensure hands-on)
- Reproducible commands: candidate must present commands and outputs in test_submission.json.
- Persistence demonstration: include a command sequence showing a restart or separate invocation demonstrates saved state.
- Machine-checkable outputs: prefer JSON output mode or fixed plain text format for list and find commands so automatable verifiers can parse expected results.
- Small sample dataset: candidate should create at least 3 different items during their demonstration, exercise update and delete, and show search results.

### Evaluation Insights — what to look for and scoring rubric
Use an objective scoring rubric to determine whether the candidate meets the basic standard. Total 100 points; passing threshold 80+.

Suggested rubric:
- Core Functionality: 60 points
  - Add/list/find/update/delete implemented and working: 40 points (8 points each)
  - Persistence (save/load across runs): 15 points
  - Correct exit codes and error messages for invalid commands: 5 points

- Robustness & Input validation: 10 points
  - Rejects duplicate SKUs, negative quantities, missing required fields: 6 points
  - Provides clear error messages and non-zero exit codes on failure: 4 points

- Deterministic & Scriptable outputs: 10 points
  - JSON or fixed-format list output for easy parsing: 6 points
  - Reproducible CLI contract (run commands provided and match outputs): 4 points

- Code quality & organization: 10 points
  - Readable code, modular functions, sensible variable names: 6 points
  - Minimal inline comments or README describing run instructions: 4 points

- Submission completeness & clarity: 10 points
  - test_submission.json present and well-formed per schema: 5 points
  - Commands recorded and outputs included: 5 points

Notes on grading and observed outputs:
- Functional checks are primary: graders should run the candidate's entry_point with scripted commands to verify behavior. The commands listed in test_submission.json should match executed outputs; inconsistencies are deductions.
- Inspect persistence file format to ensure it contains expected records (e.g., check that SKU001 exists). If candidate claims JSON persistence, the file should be valid JSON and include the items they added.
- Non-zero exit code on errors is important: having no error codes means less robust CLI design.
- Bonus features can be used to raise final score but are not required for passing.

### Example automated acceptance tests (for exam creator)
Create a small script that runs these steps against the candidate entry_point and checks outputs:
1. Remove candidate persistence file (fresh start).
2. Run: add SKU001 name A qty 5  -> expect exit code 0 and stdout contains "Added" or show item in JSON
3. Run: add SKU002 name B qty 3  -> expect exit code 0
4. Run: list --format json -> parse JSON and assert both SKUs present with expected qty
5. Run: update --sku SKU001 --qty 7 -> expect exit code 0
6. Run: list -> assert SKU001 qty == 7
7. Run: delete --sku SKU002 -> expect exit code 0
8. Run: new process list -> assert SKU002 is absent
9. Introduce invalid command: add without sku -> assert non-zero exit code and error message.

These checks mirror the rubric and can be performed within a minute or two if the candidate implemented deterministic output.

### Final guidance for exam creators & evaluators
- Make the environment clear: supply a language runtime (Python3 recommended) and tell candidates they may use only standard libraries.
- Provide the test_submission.json schema to the candidate exactly as above before starting so they know how to present evidence.
- Allow exactly 90 minutes; require single submission directory with code and test_submission.json. Automatic or manual grading should follow the scoring rubric.
- Candidate must not access external resources; the environment should permit only standard library usage to keep time and reproducibility bounded.

This structure ensures the exam is hands-on, practical, time-bounded, and distinguishes candidates who can actually implement and maintain simple software from those who can only describe it.

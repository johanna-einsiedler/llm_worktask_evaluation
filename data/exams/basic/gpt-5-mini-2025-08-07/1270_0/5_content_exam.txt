### Exam Title
Basic Practical Exam — Inventory Manager (CRUD, persistence, CSV import/export, demo & tests)

---

### Instructions for Candidate

You have 90 minutes total. Use only the tools available on your machine: a code execution environment and a text editor. Do not use external packages or the internet; use only the language standard library. You must submit a single file named test_submission.json (schema specified below). This single JSON file is the only file the evaluator will use.

Follow these steps and requirements exactly.

1. Core program (required)
   - Implement a command-line inventory manager program named exactly inventory.py (use another language only if you document that change in README and supply an equivalent main program file name; Python is recommended).
   - Persistent storage: choose either JSON (inventory.json) or SQLite (inventory.db). Document your choice and any initialization logic in README.md.
   - The program must support the following non-interactive operations (each callable from the command line; subcommand or flags acceptable):
     - add --id ID --name NAME --quantity QTY --price PRICE
     - update --id ID [--name NAME] [--quantity QTY] [--price PRICE]
     - remove --id ID
     - get --id ID
     - list
     - import --file FILEPATH   (CSV import)
     - export --file FILEPATH   (export inventory to JSON)
   - Item fields: id (string), name (string), quantity (integer), price (decimal). IDs are treated case-sensitively.

2. Validation rules (required)
   - Enforce unique ID across items.
   - quantity must be integer >= 0.
   - price must be numeric >= 0.
   - Required fields must be present for add.
   - CLI actions must return non-zero exit code on failure and print a clear error message to stdout or stderr.

3. CSV import (required)
   - CSV format (exact): columns id,name,quantity,price (header optional).
   - Candidate must include a sample file named import.csv with exactly 3 rows: one valid new item, one row with duplicate id (duplicate of existing ID in storage per demo sequence), and one malformed row (e.g., missing fields or invalid numeric).
   - On encountering invalid rows, your import must handle them gracefully: either skip + report or abort with an error. You must document the chosen behavior in README and implement it consistently.

4. Demo runner (required)
   - Provide an automated, non-interactive demo runner script named demo_runner.py that executes the exact scenario below in order and prints the final inventory JSON to stdout.
   - The demo runner must start by ensuring the storage is empty (delete inventory.json or inventory.db if present).
   - Demo sequence (must be performed in this order):
     1. Add item I100, name "Screwdriver", quantity 15, price 5.50
     2. Add item I101, name "Hammer", quantity 20, price 9.99
     3. Update I100 quantity to 12
     4. Attempt to add I101 again (duplicate ID) — must behave as implemented/published in README (fail/skip/overwrite)
     5. Remove I101
     6. Import the provided import.csv (3 rows: one new, one duplicate id, one malformed)
     7. Export final inventory to final_inventory.json and print the exported JSON content to stdout (this printed JSON must be what you include as final_inventory_json in test_submission.json)
   - demo_runner.py must be runnable non-interactively (e.g., python3 demo_runner.py) and must exit with code 0 on success.

5. Tests / assertions (required)
   - Provide an automated test file tests.py that runs non-interactively and contains at least 4 assertions / test cases covering important behavior. Example test cases (you may implement similar):
     - adding an item succeeds
     - adding a duplicate id fails (or is handled as documented)
     - updating quantity changes stored value
     - import skips or reports malformed rows and merges/handles duplicates according to documented policy
   - tests.py must produce an output summary that the evaluator can capture; however your test results will also be reported in test_submission.json (see schema). tests.py must exit with code 0 if all tests pass and non-zero otherwise.

6. README and notes (required)
   - Provide README.md with exact commands to run the demo and tests (e.g., python3 demo_runner.py, python3 tests.py).
   - Document: chosen persistence (JSON or SQLite), import-duplicate policy (overwrite / skip / error), and any assumptions or known limitations.
   - State which language and runtime you used (e.g., Python 3.10).

7. Packaging files into the submission JSON
   - You will not upload multiple files. Instead you must include the full contents of every file you created (source code, README.md, import.csv, final_inventory.json if produced) inside the single test_submission.json file following the schema below.

Time guidance (suggested):
- Core program & persistence: 45 minutes
- CSV import & validation: 20 minutes
- Demo, tests, README, and packaging into JSON: 25 minutes

- final_inventory_json: the JSON object/array produced by the demo runner export step.
- run_commands: at least these two commands clearly listed: "python3 demo_runner.py" and "python3 tests.py".
- Candidate metadata (name, email), time_taken_minutes, language, notes describing choices.

Evaluator must be able to reconstruct files from your test_submission.json and run the listed commands to reproduce demo and tests.

Scoring will be objective: correct implementation of listed CLI operations, persistence, import/export, validation and demo sequence, and passing tests are required to reach passing threshold.

### Submission Format

You must submit one file named exactly test_submission.json. The evaluator will parse this JSON and recreate files and run commands as-is. The JSON must be UTF-8 encoded and follow this schema (all top-level fields except self_score_estimate are required):

- candidate_name: string
- email: string
- time_taken_minutes: integer
- language: string (e.g., "Python 3.10")
- run_commands: array of strings
  - Must include at minimum: ["python3 demo_runner.py", "python3 tests.py"]
- files: array of objects, each with:
  - filename: string (exact filenames you used, e.g., "inventory.py", "demo_runner.py", "tests.py", "README.md", "import.csv", optionally "final_inventory.json")
  - content: string (full text content of the file)
  - Note: Include all files necessary to run the demo and tests.
- demo_stdout: string (exact stdout captured when running python3 demo_runner.py)
- test_results: array of objects, each with:
  - name: string (test name)
  - passed: boolean
  - output: string (captured stdout/stderr for that test)
  - Provide at least 4 test result objects.
- final_inventory_json: JSON object or array (the data structure representing the final inventory — must match the printed/exported JSON from demo)
- notes: string (short explanation of assumptions, persistence choice, duplicate-import behavior, and any limitations)
- self_score_estimate: integer 0–100 (optional)

Important constraints and expectations
- The demo_runner.py must perform the exact demo sequence in the Instructions section and must print the final exported inventory JSON to stdout as the last significant stdout content (so evaluator can capture it).
- inventory.py CLI names and option names must match the semantics above, but exact flag names can be adapted if documented in README (e.g., --qty instead of --quantity only if documented).
- If you choose SQLite, include schema creation code inside inventory.py or demo_runner.py so the evaluator does not need to initialize the DB manually.
- The import.csv included in files must be the same file your demo_runner imports.
- All commands referenced in run_commands must work when the evaluator writes the files to disk and runs them with the standard interpreter.
- Use atomic write for JSON storage or safe SQLite transactions if you implement either (recommended, but optional for basic credit).

Minimal example run_commands entry:
["python3 demo_runner.py", "python3 tests.py"]

Evaluation reproduction steps the evaluator will perform:
1. Write files listed in files array to disk.
2. Run the run_commands in order.
3. Compare demo_stdout to produced stdout, and parse final_inventory_json to check correctness.
4. Examine test_results and run tests.py to confirm.

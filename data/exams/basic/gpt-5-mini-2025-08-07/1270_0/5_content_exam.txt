### Exam Title
Inventory CLI — Basic Practical Programming Exam (90 minutes)

---

### Instructions for Candidate

Goal
- Build a small, single-author CLI program that manages an inventory of items and persists data to disk.
- The program must be runnable in the provided execution environment using only built-in/standard libraries. You may choose any language available (e.g., python3, node, java), but you must state your language in the submission.

Time limit
- You have 90 minutes total. Suggested pacing:
  - 5–10 min: design & choose persistence format (JSON file or SQLite recommended)
  - 45–55 min: implement functionality
  - 15–20 min: run demonstration commands and capture outputs
  - 5–10 min: prepare test_submission.json and finalize files

What you must implement (required)
- Data model: each item must include at minimum:
  - sku (string, unique)
  - name (string)
  - qty (integer, >= 0)
  - optional: price (decimal) or description

- CLI commands (exact names and flags are required):
  1. add
     - Syntax: <entry_point> add --sku <SKU> --name <NAME> --qty <N> [--price <P>]
     - Adds a new item. If SKU already exists, error (non-zero exit) and message on stderr.
  2. list
     - Syntax: <entry_point> list [--sort sku|name|qty] [--format json|text]
     - Lists all items. When run with --format json, stdout must be valid JSON array of item objects.
  3. update
     - Syntax: <entry_point> update --sku <SKU> (--qty <new_qty> | --change +N|-N)
     - Updates quantity (either absolute or relative). Invalid quantities (<0) must be rejected with non-zero exit.
  4. delete
     - Syntax: <entry_point> delete --sku <SKU>
     - Deletes an item by SKU. If SKU does not exist, return non-zero exit and stderr message.
  5. find
     - Syntax: <entry_point> find --sku <SKU>
       OR
       <entry_point> find --name <substring>
     - Returns matching items. When run with --format json, stdout must be a JSON array with matching item objects.

- Persistence:
  - Your program must save inventory to disk and load it on startup.
  - Use either:
    - a JSON file (recommended) OR
    - an SQLite DB (acceptable)
  - If you choose a JSON file, implement safe write semantics (e.g., write to a temp file then atomically rename) to avoid corrupted files on save.
  - On startup, if the persistence file exists, it must be loaded and subsequent commands should operate on that data.

- Deterministic, machine-parseable output:
  - list and find must support --format json and produce valid JSON on stdout when asked.
  - Error messages must go to stderr.
  - Exit codes: 0 = success, non-zero = error.

- Robustness / validation:
  - Reject duplicate SKUs when adding.
  - Reject negative quantities.
  - Return informative error messages on stderr and non-zero exit codes for invalid operations.

Demonstration requirements (must be shown in your recorded commands)
- Create at least 3 distinct items with add.
- Update the quantity of at least one item.
- Delete at least one item.
- Search/find at least one item by SKU or name substring.
- Demonstrate persistence across program invocations: perform add(s), exit, run a new invocation that lists items and shows previously added items still present.

What you may NOT use
- No internet access or external packages. Only standard libraries in the provided execution environment are allowed.

Files you must produce in your submission directory
- Source code files implementing the CLI.
- Any persistence file(s) your program creates during your demonstration (e.g., data.json or inventory.db).
- test_submission.json (exact filename required) — see schema below.

How to capture demonstration runs
- For every run you show in test_submission.json, capture:
  - exact command you ran
  - stdout (or a short excerpt if long) — when using --format json, include the JSON output
  - stderr (empty string if none)
  - exit code

Hints
- Prefer JSON persistence for speed.
- Provide an easy-to-run entry point (example: python3 inventory.py ...).
- You do not need to implement concurrency beyond single-user CLI. A simple atomic write is sufficient for file durability.
- Keep CLI parsing simple and deterministic so the grader can script checks.

### Expected Outcome

By the end of the test you must produce:
- A working CLI program implementing add, list, update, delete, find with persistence and validation.
- A short sequence of commands (minimum: add 3 items, update one, delete one, find one, restart and list to prove persistence) with captured outputs and exit codes recorded in test_submission.json.
- test_submission.json (exact name) describing the program, entry command, persistence filename, the demonstration commands and outputs, a short description of design choices, and a brief self-assessment.

Evaluation will be automated or manual against objective checks:
- Correct commands exist and behave as specified (add/list/find/update/delete).
- Persistence works (items remain after program restart).
- JSON output for list/find when requested.
- Proper exit codes and stderr on error cases.
- The test_submission.json file is complete and well-formed.

Passing criteria (informal)
- You must implement all required commands and persistence and provide the required demonstration. The grading rubric will check functional behavior and required validations. Aim to complete fully within 90 minutes.

<MATERIALS_EXPLANATION_FOR_EVALUATOR>
How and why these materials were created
- Purpose: provide a minimal, deterministic dataset and a small CSV with targeted edge cases so the candidate has concrete, coherent data to use during implementation and demonstration within a 90-minute window.
- seed_items.json contains 5 distinct, valid inventory records covering normal, zero-quantity, and low-stock cases. Fields match the required data model: sku (unique string), name (string), qty (integer >= 0), price (decimal), description (string).
- import_extra.csv supplies three rows designed to test candidate validation logic: one row duplicates an existing SKU (SKU003) to exercise duplicate-rejection logic; one is a valid new item (SKU006); one has a negative qty (SKU007) to test rejection of invalid quantities.

Data patterns and relationships
- SKU pattern: "SKU" followed by a three-digit numeric suffix (SKU001 .. SKU007). This consistent SKU naming makes validation straightforward and machine-checkable.
- Names include keywords ("Widget", "Gadget", "Tool", "Accessory", "Part") so substring searches (find --name) are deterministic.
- Quantities intentionally include: positive (>0), zero (SKU005), and negative (SKU007 in CSV) to separate valid and invalid cases.
- Prices are decimals with two fractional digits to test parsing/serialization of numeric types.

What to check / expected evaluator actions
- Verify seed_items.json is valid JSON and contains the five items. If the candidate chooses to load this file into their program at startup (optional), the initial state should reflect these items.
- When grader runs the candidate's CLI commands (as recorded in test_submission.json), check:
  - add/list/update/delete/find behave per spec.
  - list and find produce valid JSON when invoked with --format json.
  - Error operations (e.g., adding duplicate SKU, adding negative qty) write to stderr and return non-zero exit codes.
  - Persistence: after adding items and exiting, a subsequent run of list must show previously added items. Inspect the persistence file named in test_submission.json to confirm saved records.
- If the candidate implemented CSV import, importing import_extra.csv should:
  - Reject the row with SKU003 (duplicate) or report the duplicate and continue/abort depending on implementation; the grader should accept either behavior provided it is deterministic and reported.
  - Reject the row with SKU007 (negative qty) with an appropriate error message and non-zero exit code or skip it with a clear report, depending on the candidate's chosen behavior; grader should ensure there is clear validation.

Common pitfalls and traps to watch for
- Treating numeric qty as string: candidate must ensure qty is parsed and validated as an integer >= 0. Expect failure points if they forget to validate or accept negative values.
- Not returning non-zero exit codes on errors: graders should assert exit_code != 0 for invalid operations.
- Writing persistence unsafely: simple write-to-file is acceptable for this basic exam, but candidates who implement atomic write (temp file + rename) earn bonus credit. Check persistence file integrity (valid JSON).
- Case-sensitive vs case-insensitive find: specification did not mandate case sensitivity; accept either but require the candidate to document behavior in short_description and known_issues.
- Inconsistent CLI flags: commands and flags must match the instruction list (add, list, update, delete, find and their flags). If flag names differ, deduct points for determinism/scriptability.

How these materials differentiate conceptual vs practical skill
- The materials are concretely usable (valid JSON and CSV) so an implementer must write code to parse, validate, persist, and produce deterministic JSON output. A candidate who only knows theory cannot produce the correct program output or a valid persistence file matching the dataset.
- The CSV contains edge cases (duplicate SKU, negative qty) that force implementation of validation, error reporting, and exit codes—practical tasks that reveal attention to detail and error handling.
- The SKU/name patterns let evaluators write short automated checks for presence/absence, quantity updates, and find behavior—making functional verification straightforward.

Evaluator quick-check list (recommended)
1. Confirm candidate provided test_submission.json and the name of persistence file.
2. Run the candidate's entry_point for the sequences recorded in test_submission.json and verify stdout/stderr/exit codes match.
3. Inspect the persistence file for the expected records (SKUs listed in commands_run before restart).
4. Verify list/find --format json output is valid JSON and contains expected objects.
5. Ensure error cases (duplicate SKU, negative qty, missing flags) produce stderr output and non-zero exit codes.

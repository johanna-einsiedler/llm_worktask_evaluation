<MATERIALS_EXPLANATION_FOR_EVALUATOR>
How and why these materials were created
- Purpose: Provide the single external data dependency required by the exam: an import CSV with three deterministic rows that exercise normal import, duplicate-id handling, and malformed-row handling.
- Composition: The file `import.csv` contains four comma-separated columns in this exact order: id,name,quantity,price. The header row is included to make column positions explicit and unambiguous.

Data patterns and relationships
- IDs used in the demo sequence are: I100, I101, I102, I104.
  - I100 and I101 are created during the demo runner steps before import. Therefore the CSV row with id I100 is a deliberate duplicate of an existing item at import time.
  - I102 is a new, valid item intended to be added by import.
  - I104 has an invalid quantity field ("abc") to represent a malformed row.
- The CSV rows:
  1. I102,Pliers,5,3.25  — valid new item (integer quantity, numeric price).
  2. I100,ScrewdriverDuplicate,10,5.50 — duplicate id (duplicate of I100 created earlier in demo).
  3. I104,Chisel,abc,4.00 — malformed row: non-integer quantity ("abc").

Traps, ambiguities, and common errors candidates might make
- Numeric parsing: candidates may parse quantity or price as floats or fail to validate integer requirement for quantity. The quantity must be an integer >= 0.
- Duplicate handling: the CSV intentionally contains a duplicate for I100. Candidates must choose and document a consistent duplicate-import policy (overwrite, skip, or abort). Common incorrect behavior: silently overwrite without documenting, or crash without informative error.
- Malformed rows: candidates must decide whether to skip malformed rows with a warning or abort the whole import; either is acceptable if documented and implemented consistently. A frequent mistake is failing with an unhandled exception.
- Header handling: the file includes a header row. Candidates must either handle an optional header or explicitly parse all rows and ignore the header. Failing to accommodate the header may lead to treating the header as a data row.
- Whitespace and quoting: commas separate fields exactly; no quoted fields are used. Candidates should trim whitespace and handle basic CSV parsing using the language standard library CSV handling to avoid splitting errors.

What correct/expected answers depend on
- The candidate’s documented import-duplicate policy and malformed-row policy in README.md. The final inventory produced by the demo depends on those choices:
  - If duplicates are skipped and malformed rows are skipped: final inventory should include I100 (as updated earlier in the demo) and I102 added from CSV.
  - If duplicates overwrite: I100’s stored fields may be replaced by the CSV row for I100.
  - If malformed rows abort import: the import may fail and the final inventory may remain unchanged depending on implementation.
- The evaluator should verify that the candidate’s README documents the chosen behavior and that the implementation follows it.

How these materials differentiate conceptual vs practical skill
- The three-row CSV is small but forces candidates to implement real parsing, validation, error handling, and a documented policy for conflicting inputs.
- Correct handling requires working code (not just pseudo-code): parsing CSV, validating numeric types and ranges, enforcing unique IDs, and producing reproducible, automated outputs (demo and tests).
- The malformed row ensures candidates demonstrate graceful failure modes rather than only the happy path.

Evaluator notes
- The file must be provided to the candidate exactly as shown (filename `import.csv`).
- When reproducing the demo, the evaluator should observe the candidate’s chosen behavior for the duplicate (I100) and malformed (I104) rows and compare it to the README documentation included by the candidate.
- Accept any consistent, documented policy (skip/overwrite/abort) implemented by the candidate; deduct for mismatches between README and implementation or for crashes/unhandled exceptions.

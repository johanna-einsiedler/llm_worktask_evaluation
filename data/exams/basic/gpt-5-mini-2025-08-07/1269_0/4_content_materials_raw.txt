<MATERIALS_EXPLANATION_FOR_EVALUATOR>
Rationale for materials
- I created two compact CSV files that exercise the required parsing, aggregation, rounding, sorting, and error-handling behaviors for the sales_agg task.
- sample_sales.csv provides normal, well-formed data that yields clear aggregated totals per product_id.
- malformed_sales.csv intentionally contains a variety of edge cases that the candidate must handle gracefully:
  - A completely malformed line without commas ("BADLINEWITHOUTCOMMAs") — must be ignored.
  - A line with a missing quantity (empty between commas) — treat missing numeric field as zero for that line.
  - A line with a non-numeric unit_price ("notanumber") — treat as zero for that line.
  - A line with fewer fields plus an inline comment ("2025-01-06,BAD,4     <-- malformed...") — should be treated as malformed and ignored.
  - An empty line — should be ignored.
  - A negative quantity entry (NEG001 with -1) — allowed and must affect revenue (negative revenue).
- The additional filter test (--min-revenue 50.00) is deterministic and demonstrates the follow-up revision feature expected in the exam.

Patterns and relationships
- Aggregation key: product_id (string). Sorting must be lexical ascending by product_id.
- Per-line revenue: quantity * unit_price. If quantity or unit_price is missing or not parseable to a number, treat that field as zero for that line (but ignore lines that do not have the expected number of fields at all).
- Aggregation: sum per product_id across all valid lines, then round final per-product totals to exactly two decimal places.
- Negative quantities are valid and reduce total revenue accordingly (this appears in malformed_sales.csv as NEG001,-1,15.00 -> revenue -15.00).
- Rounding must be applied after aggregation to avoid subtle precision differences. Evaluators should accept only exact string matches to the expected outputs provided above.

Common traps and likely candidate errors
- Parsing: splitting on commas without trimming may leave trailing comment text in a field — the line with the inline comment has too few fields and should be ignored.
- Numeric conversion: candidates may crash on empty strings or non-numeric tokens; correct behavior is to treat missing/non-numeric quantity or unit_price as zero for that line (except for completely malformed lines).
- Line counting: failing to skip the header row will shift results; candidate must detect and skip it.
- Rounding: rounding per line before aggregating versus after aggregation will produce different totals; the required behavior is rounding the final per-product total to two decimal places.
- Sorting: sorting numerically vs lexically could change ordering; evaluator expects lexical ascending sorting by product_id.
- Output formatting: extra blank lines or trailing spaces will cause automated exact-match checks to fail.

What correct answers depend on
- Proper detection of malformed lines vs lines with missing numeric values.
- Treating missing/non-numeric numeric fields as zero (for that single field) rather than discarding the whole line (unless the line has fewer than 4 comma-separated fields).
- Summing per product_id correctly, then rounding once at the end.
- Filtering with --min-revenue must apply after aggregation and rounding or at least use the final numeric totals for comparison (use consistent rule and document it in README); for automated checking we supply expected output for threshold 50.00 to be exact.

How materials distinguish skills
- Conceptual-only candidates might describe correct behavior but fail to produce an executable program that:
  - Does not crash on malformed input.
  - Produces the exact expected stdout strings for both CSV files and for the filter test.
  - Implements the --min-revenue flag correctly and documents assumptions (e.g., when rounding is done).
- Practical candidates will implement parsing, aggregation, rounding, sorting, implement the optional filter flag, provide test commands, capture outputs, and include README and changelog explaining decisions.

Evaluator hints
- Check that candidate reproduces the exact provided expected outputs (byte-for-byte, no trailing spaces/newlines).
- Verify candidate's handling of the malformed line with inline comment is to ignore it (not to attempt to parse comment text).
- Confirm negative quantity handling yields negative revenue for NEG001 in malformed_sales.csv.
- Verify the filter test uses the provided threshold 50.00 and matches the provided expected output.

These materials are compact (two small CSVs and one deterministic filter test) and fully deterministic so the candidate can complete the exam within the 90-minute time limit.

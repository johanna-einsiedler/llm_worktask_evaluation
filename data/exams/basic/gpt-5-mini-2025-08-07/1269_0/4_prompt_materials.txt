### Exam Purpose
Confirm that the candidate can independently produce a small, working program, compile/run it (or provide runnable instructions), and produce clear, usable development documentation and inline code comments describing design and subsequent revisions. This verifies real-world capabilities needed for collaboration: producing reproducible builds/runs, maintainable code, and readable revision history so others can pick up and maintain the work.

### Core Competencies to be Tested
- Implementing a small, correct program that reads input and produces expected output.
- Creating reproducible build/run instructions (compile or run command).
- Writing clear, explanatory inline comments and docstrings so others understand code intent and structure.
- Producing concise developer-facing documentation: README, assumptions, usage, and a changelog describing revisions.
- Performing a simple revision/feature change and documenting that revision.
- Packaging deliverables in a reproducible format so an evaluator can run and verify results.

### Practical Elements to Include (to make this hands-on)
- Provide a small sample dataset (e.g., data.csv with 20 rows) and a one-paragraph functional spec. Candidate must produce code that reads the sample and produces exact expected results described in the spec.
- The primary task should be a real minimal engineering task, e.g.:
  - Implement a CLI CSV summarizer: reads data.csv, computes for each numeric column: count, sum, mean, min, max and outputs JSON (stable ordering). Must skip empty/missing values.
- Revision task (single, small but non-trivial change): e.g.
  - Add an optional argument --group-by <column> to compute those statistics per group (categorical column), update output, and document the change. Or, implement argument to write output to a file vs stdout. This forces the candidate to change code and comments and to document the reason.
- Require robust but minimal input validation: program must detect missing file and invalid numeric values and show a clear error message.
- Require a reproducibility artifact: a one-line run command (e.g., "python3 summarizer.py data.csv --output out.json") that the evaluator can execute. If compiled language is used, the candidate must provide build instructions and a build script (e.g., makefile or simple compile command).
- Require the candidate to capture program outputs (stdout or output file) into files and include them in the JSON (so evaluator can compare expected outputs without re-running, and can re-run to verify).

Why these elements make it practical:
- Candidate actually writes code that runs on provided data.
- Revision step tests ability to evolve codebase, not only write initial version.
- Documentation and run instructions test whether candidate can communicate the work reproduction steps.

### Strategic Elements (distinguishing real ability from conceptual knowledge)
- Multi-step dependency: program must be written, then modified for new requirement. Candidates who only conceptually understand will fail to update all necessary parts (code, tests, comments, README) consistently.
- Data dependency: The code must read actual input data and handle missing/invalid rows. This forces error-handling and data-validation behavior.
- Decision points:
  - Design trade-offs: how to represent output JSON (flat vs nested for group-by); require candidate to choose and document the choice in README.
  - Rounding/precision: specify desired numeric formatting (e.g., two decimal places) so candidate must make an explicit decision and document it.
- Reproducibility check:
  - Provide a small automated test harness (optional in basic exam) or demand captured run outputs for the sample input. Candidate who understands reproducibility will include a run_command that reproduces exactly the submitted outputs.
- Minimal scaffolding but explicit acceptance criteria: the sample dataset and the expected format makes the task deterministic and prevents purely conceptual answers.

Scoring model (weights and pass threshold)
- Overall passing score for Basic exam: 80% required.
Suggested weighting:
- Functional correctness and reproducibility (60%)
  - Program runs with the given primary_run_command and produces correct output for the sample input (40%)
    - Exact or numerically tolerant match to expected values (tolerance for floats specified in README; default: absolute error <= 1e-6 or formatted to two decimal places as asked).
  - Revision correctness (20%)
    - The added feature or bugfix works and produces the expected revised output.
- Code readability and commenting (20%)
  - Presence of top-of-file header comment describing file purpose.
  - Clear function/method docstrings or comments per non-trivial function.
  - Inline comments explaining non-obvious logic.
  - Consistent naming conventions and reasonable structure.
- Documentation and change history (15%)
  - README contains purpose, usage examples, exact run commands, assumptions, and error handling instructions.
  - Changelog documents what was changed for the revision, why, and what files were modified.
- Packaging and reproducibility (5%)
  - test_submission.json follows schema, includes all files and captured outputs, and run commands reproduce outputs.

Guidance to examiners for each criterion:
- Reproducibility: Run the candidate's primary_run_command in the provided environment. If it fails, try to compile if a build_command is provided. If still fails, deduct substantial points in reproducibility and correctness.
- Correctness: Compare produced outputs to the expected outputs (provided by exam creator). Allow minimal numeric tolerance for floats or require specified formatting. For group-by results, check both keys and values.
- Comments: Open the main source file(s). Expect @top-level header, docstrings for each top-level function, and inline comments where non-obvious transformations occur. For basic exam, require at least one-line docstring per function and comments at entry/exit points.
- README: Must contain at least — project purpose (one paragraph), exact run command(s) copyable, specification of any non-standard assumptions, and changes summary.
- Changelog: Must show at least two entries (initial implementation and revision), each with short description and what files changed.

Concept-only respondents often leave run instructions vague, provide incomplete captured outputs, or forget to update comments/documentation after modification.

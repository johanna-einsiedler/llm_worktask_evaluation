### Exam Title
Basic Practical Programming Exam — "sales_agg" CSV Aggregator (90 minutes)

### Instructions for Candidate

Overview
- Time limit: 90 minutes total. Work offline on your local computer with only the code execution environment and a text editor. No internet or external resources allowed.
- Goal: produce working, documented, commented code that compiles/runs, plus a short revision and tests — all submitted as a single JSON file named test_submission.json (instructions below).

Tasks (perform in order)
1. Implement the command-line program named sales_agg:
   - It must accept the input CSV filename as a required positional argument:
     sales_agg <input_file> [--min-revenue N]
   - Behavior:
     - Read the CSV file whose columns are: date,product_id,quantity,unit_price (comma-separated).
     - The file may include a header row. If present, skip it.
     - For each well-formed line, compute line revenue = quantity * unit_price and aggregate total revenue per product_id.
     - If quantity or unit_price is missing for a line, treat the missing value as zero.
     - Ignore malformed lines (lines that cannot be parsed into the expected number of fields or have non-numeric quantity/unit_price that cannot be treated as missing).
     - After aggregating, round each product's total revenue to exactly two decimal places (e.g., 123.456 -> 123.46).
     - Sort the output by product_id in ascending lexical order.
     - Print the result to stdout in CSV format, no header: product_id,total_revenue
   - Follow-up (revision) requirement: implement the optional command-line flag --min-revenue (or short -m) that, when provided, filters out products whose total_revenue is less than the numeric threshold N. The flag is optional and defaults to no filtering.
   - Program name: the executable/script must be called sales_agg (or sales_agg.py, sales_agg.go, sales_agg.java, etc., but indicate exactly how to run it in your build_instructions).

2. Create and run automated/script-driven tests (at least two):
   - Test A (normal): run sales_agg on provided sample_sales.csv and verify it matches the provided expected output.
   - Test B (malformed/edge): run sales_agg on provided malformed_sales.csv and verify it matches the provided expected output for malformed data handling.
   - Additionally run a test exercise that demonstrates the --min-revenue filter (for example run with --min-revenue 20.0 on sample_sales.csv).
   - Tests may be small shell scripts or simple commands saved in your instructions; they must be runnable locally with the commands you list in build_instructions.

3. Document your work:
   - Add clear inline comments in source files explaining non-trivial logic and the revision you made.
   - Create a short README describing how to build/run, the exact assumptions you made, and example usage.
   - Maintain a changelog recording the sequence of edits (implement, tests run, revision) with short rationale and timestamps.

4. Revision step (during the same session):
   - Implement the --min-revenue option described above (if you initially left it out, add it now).
   - Update inline comments and the changelog to reflect this revision.
   - Re-run tests and include the updated test outputs.

Time guidance (suggested, but stay within 90 minutes)
- Implement core feature: ~40 minutes
- Create & run tests: ~15 minutes
- Write README, comments, changelog: ~20 minutes
- Implement small revision (--min-revenue) and re-run tests: ~10 minutes
- Package submission: ~5 minutes

Important constraints
- Do not use the internet. Do not include any external libraries that are not part of the standard runtime for the language you choose.
- You may use any programming language, but your submission must include exact build/run commands so an evaluator can reproduce your results.
- You must include the source code itself inside the submission JSON (see Submission Format).

Checklist of required deliverables (everything must be present inside test_submission.json)
- Source code file(s) (complete content).
- build/run commands used to compile and execute the program.
- README content (plain text).
- Changelog entries.
- At least three test runs: normal case, malformed case, and a --min-revenue case with expected outputs and actual outputs captured.
- A brief statement of assumptions you made.
- Candidate self-evaluation and signature statement.

### Expected Outcome

By the end of the test you must deliver a valid test_submission.json file that demonstrates:
- A working sales_agg program (source included) that runs and produces the correct CSV output for the provided sample tests.
- The program handles header rows, missing quantity/price (treated as zero), ignores malformed lines, and rounds final per-product totals to two decimal places.
- The program accepts and implements the --min-revenue filter.
- At least two automated/scripted test runs were executed and their outputs (stdout/stderr) captured and included.
- README explains how to reproduce build and test commands, describes assumptions, and documents the --min-revenue flag behavior.
- Inline comments exist in code explaining non-trivial logic and the revision(s).
- A changelog records the initial implementation and the follow-up revision and why they were made.
- The JSON submission follows the required schema detailed below.

Evaluation criteria (objective)

- Presence and reproducibility of build/run commands.
- Inclusion of code, README, changelog, tests, and captured outputs in the JSON.
- Inline comments explaining non-trivial code.
- Implementation of the --min-revenue option and test demonstrating it.
- Clear statement of assumptions.

You are expected to score >= 80% to pass the basic exam if you are a qualified entry-level programmer.

### Submission Format

You must submit exactly one file named test_submission.json. This is the only file an evaluator will open. It must be valid JSON and contain the following fields exactly:

- candidate_name: string
- language: string (programming language used)
- time_spent_minutes: integer (total minutes spent, <= 90)
- source_files: array of objects, each with:
  - filename: string (e.g., sales_agg.py)
  - language: string (e.g., python)
  - content: string (the full source code of that file)
- build_instructions: string (exact commands needed to compile and run your program and tests; e.g., "python3 sales_agg.py sample_sales.csv")
- readme: string (plain text README content)
- changelog: array of entries, each an object:
  - time: string (a short timestamp)
  - change: string (what you changed)
  - reason: string (why)
- tests: array of test objects (one per test run), each with:
  - test_name: string (e.g., "normal_sample")
  - command: string (the exact command you ran to execute this test)
  - expected_output: string (exact expected stdout for that test)
  - actual_output: string (captured stdout from your run; include stderr if any)
  - passed: boolean (true if actual_output exactly equals expected_output)
- run_output_summary: string (brief summary of program run behavior and any issues)
- assumptions: array of strings (all assumptions you made, e.g., header handling, numeric parsing rules)
- comments_coverage: string (self-assessment of how well code is commented, e.g., "All functions documented; complex loops explained")
- self_score_estimate: number (0-100) and a one-sentence justification
- signature: string (a one-line statement asserting the submission is your own work, e.g., "I certify this submission is my own work — <Name>")

Additional submission rules
- All source file contents must be placed inside source_files[]. Do not attach files separately—everything must be in the JSON.
- expected_output strings must match the exact expected outputs provided earlier for sample files without extra blank lines or trailing spaces.
- actual_output must be what your program printed when you ran the command (captured exactly).
- The evaluator will reject submissions missing required fields or with invalid JSON.

- With min filter: python3 sales_agg.py sample_sales.csv --min-revenue 50.00

### Exam Purpose
Confirm that a candidate can, in a real-world (junior) setting:
- Produce working, compilable/runnable code for a small but realistic feature.
- Explain design decisions and development steps in written documentation (README and changelog).
- Insert clear, useful inline comments in code so others can understand the program and later revisions.
- Demonstrate minimal test coverage and show the program runs correctly on sample inputs.

This validates both hands-on programming ability and the documentation discipline needed for collaborative development.

### Core Competencies
The basic exam tests these practical skills:
- Coding to a working, buildable/runnable state (syntax, compilation/run).
- Implementing a simple but complete feature with input/output.
- Writing a concise README that documents how to build/run, expected inputs and outputs, and any assumptions.
- Writing inline comments explaining non-trivial code blocks and algorithm intent.
- Producing a brief changelog/revision history describing what changed and why.
- Creating and executing simple tests (manual or automated) and reporting their outputs.
- Communicating assumptions and steps taken during development.

Technical focus (entry level):
- Basic language syntax, IO, control flow, data structures.
- Minimal error handling and input validation.
- Simple unit or integration tests (can be script-driven).
- Clear, professional documentation style.

### Recommended Structure (one 90-minute session)
Total time: 90 minutes. Candidate uses only their local code execution environment and text editor. No internet or external resources.

Number of tasks: 4 sequential, dependent tasks.

Deliverables: A single JSON file named test_submission.json containing structured fields (source files, README, changelog, test outputs, assumptions, self-evaluation). See "Submission schema" below.

Time allocation (suggested):
- Task 1 — Implement feature (40 min)
- Task 2 — Add and run tests + capture outputs (15 min)
- Task 3 — Write README, inline comments, and changelog (20 min)
- Task 4 — Minor revision/bugfix or feature extension and update changelog/comments (10 min)
- Pack and prepare submission (5 min)

Logical sequence:
1. Implement: Build a working program according to a short specification.
2. Validate: Create runnable tests and show program outputs.
3. Document: Write README, inline comments, and a development changelog.
4. Revise: Make a small follow-on change (new requirement or bug fix), comment the change, update changelog, re-run tests.

Concrete suggested problem (basic): Implement a command-line tool named "sales_agg" that:
- Reads a CSV file of sales records (date, product_id, quantity, unit_price).
- Produces aggregated output for total revenue per product_id (sorted by product_id).
- Accepts input filename as a CLI argument; prints results to stdout in CSV form: product_id,total_revenue (two columns).
- Requirements: ignore malformed lines, treat missing quantity or price as zero, round revenue to 2 decimal places.

This is simple, realistic, involves parsing, aggregation, rounding, and IO — good for an entry-level practical test.

Alternative simpler task: word frequency counter for a text file, outputting top N words.

(Exam creator may pick one of these depending on language/role.)

### Practicality — Making it hands-on
- Real code must be written, compiled, and executed locally. No multiple-choice or essay-only items.
- Include a small sample input file the candidate can use for testing. (Provide one or require the candidate to create it.)
- Require the candidate to produce program output and include the captured stdout/stderr in the submission JSON.
- Require at least one automated or script-driven test (for example, a small shell script or language test runner invocation). This proves they can run tests, not only claim they passed them.
- Require a second-stage change (feature addition or bugfix) that forces the candidate to modify code and update comments/changelog — tests must still pass. This proves ability to revise and document changes.

Constraints that ensure hands-on:
- No internet access; candidate must rely on their local environment.
- Must submit the code itself, not screenshots or external links.

### Strategic elements (distinguish concept vs. practice)
Include these exam design features to separate those who can actually do the work from those who only know the theory:
- Ambiguous but reasonable edge cases: e.g., malformed CSV lines, empty files, negative quantities; candidate must choose a behavior and document the assumption in README.
- Dependency on input formatting: candidate must parse and sanitize input; failure to handle a few malformed lines should be visible in test outputs.
- A small refactor or minor feature extension: e.g., “Add optional --min-sales threshold to only include products with total revenue >= threshold” (or implement rounding change). This requires understanding code structure and making safe modifications.
- Require automated verification: include at least two test cases (normal data, and malformed data) and expect program outputs to match provided expected outputs. Candidate must capture actual vs expected results in submission.
- Decision points: allow candidates to choose between implementing rounding before or after aggregation; force them to state and justify choice in README. That shows understanding of correctness vs. precision.

These elements require candidates to actually run and debug code, make design choices, and document them — not just answer conceptual questions.

### Evaluation Insights — observable outputs and criteria
Primary observable outputs:
- Program runs and produces expected outputs for provided test cases (or explains any deviations with evidence).
- test_submission.json includes the code (source files), README, changelog, and the captured build/run/test outputs.
- The modified code after the revision implements the requested change and updated tests still pass.

Measured criteria and suggested weights (basic exam):
1. Correctness / Functionality — 50%
   - Program runs without errors for core test(s).
   - Output format and values match expected for provided normal test case.
   - Handles at least basic malformed input cases in a reasonable way.
2. Documentation (README + changelog) — 20%
   - README includes build/run steps, input format description, sample usage, and clear stated assumptions.
   - Changelog lists the sequence of changes made, why, and timestamps or brief rationale.
3. Code comments & clarity — 15%
   - Inline comments explain non-obvious logic, function roles, and the intent of complex blocks.
   - Clear variable and function names; code is readable and logically organized.
4. Tests and evidence of execution — 10%
   - At least two test cases executed; captured outputs included in submission JSON.
   - Tests demonstrate normal and an edge/malformed case.
5. Minor revision implemented & documented — 5%
   - The follow-on change (feature or bugfix) is present, commented, and recorded in changelog; tests re-run.

Concrete pass threshold (basic exam):
- Entry-level candidates should be expected to score >= 80% overall to pass.

What to look for qualitatively:
- Does the README clearly allow an evaluator to reproduce the run? (If not, score down on documentation.)
- Are comments explaining the why, not just the what? (E.g., “split CSV by comma” comment is weak; “skip header or detect header line” is useful.)
- Does the changelog show purposeful changes with reasoning, or is it cursory?
- Are test outputs directly included and machine-readable in the JSON submission (not just textual descriptions)?

### Submission schema (required file: test_submission.json)
Tell candidates to create a JSON file exactly named test_submission.json containing these fields. Evaluators will parse this to simplify grading.

Required JSON fields:
- candidate_name: string
- language: string
- time_spent_minutes: integer
- source_files: array of objects
  - filename: string
  - language: string
  - content: string (full source)
- build_instructions: string (exact commands used to compile/run)
- readme: string (plain text content of README)
- changelog: array of entries {time: string, change: string, reason: string}
- tests: array of test objects
  - test_name: string
  - command: string (exact command used to run test)
  - expected_output: string
  - actual_output: string
  - passed: boolean
- run_output_summary: string (brief summary of program run behavior)
- assumptions: array of strings (any assumptions candidate made)
- comments_coverage: string (brief assessment by candidate of how well the code is commented, e.g., “All functions have docstrings; complex loops explained”)
- self_score_estimate: numeric (0-100) and brief justification
- signature: string (candidate statement the submission is their own work)

Provide an example minimal JSON snippet in the exam instructions (not included here to keep exam concise). The evaluator should reject submissions missing required fields or with invalid JSON.

### Example evaluator checklist (quick pass/fail)
- Is test_submission.json valid JSON and named correctly?
- Are all required fields present?
- Does source_files include at least one runnable source file?
- Do build_instructions allow reproduction?
- Do tests show at least 1 normal and 1 malformed/edge case, with actual_output included?
- Does the program produce the expected output for the core test?
- Is there a changelog entry showing the follow-up change and evidence tests were rerun?
- Are code comments present and explain non-trivial points?
- Does README document build/run/assumptions?

If the answer is “yes” to most of these, candidate meets basic competency.

### Final notes for exam creator
- Choose a simple, deterministic task (CSV aggregator or word counter) to avoid environment-dependent behavior.
- Provide a sample input file and expected output files to the candidate at the start of the exam.
- Emphasize the naming and JSON schema requirement to streamline automated or semi-automated grading.
- Keep time limit strict (90 minutes). The task complexity and required documentation are calibrated so a qualified entry-level programmer should score >80% if they are capable.

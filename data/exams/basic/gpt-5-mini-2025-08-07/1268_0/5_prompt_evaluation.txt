### Exam Purpose
Confirm that the candidate can perform practical trial runs of programs and small software components to verify they produce the desired information and that the instructions (how to run/use them) are correct. In real-world terms: run provided code, reproduce expected outputs, design simple automated checks, diagnose failures, make minimal repairs or clarifications, and produce reproducible evidence of the steps taken.

### Core Competencies to Be Tested
- Environment setup and deterministic execution (run a program with given inputs and commands)
- Reproducing and capturing expected outputs (console/text file outputs)
- Designing and running simple automated tests (unit tests or small test harnesses)
- Basic debugging and fixing of obvious faults (logic bug, off-by-one, parsing error)
- Clear, reproducible reporting of steps and evidence (commands used, outputs, time spent)
- Judgement about whether to change code vs. change instructions (and documenting that decision)
- Minimal code hygiene for fixes (clear small patches, comments, and minimal error checks)

### Strategic elements that distinguish practical skill
- Multi-step verification:
  - Require the candidate to first run the original program (unmodified) and show the result.
  - Ask them to create an automated check that codifies the acceptance criteria so success can be re-run deterministically.
  - Then require them to alter code or instructions minimally to address a failing case and show the tests now pass.
- Data dependency:
  - Include at least one small input dataset with an edge case that exposes a bug (e.g., trailing newline, empty field, or off-by-one boundary).
- Decision points:
  - Make one issue ambiguous so the candidate must decide to (a) modify the code to accommodate a reasonable interpretation, or (b) update the run instructions to state the precondition; require justification for their decision.
- Monitor reproducibility:
  - Candidate must include exact commands used and capture standard output and exit codes (or test runner output), so evaluator can repeat steps.
- Minimal but meaningful debugging:
  - Bugs should be fixable with small changes (1–15 lines), e.g., wrong operator, incorrect index, improper string split, integer division issue, or inadequate input validation.

#!/usr/bin/env python3
import sys

def main():
    if len(sys.argv) != 2:
        print("Usage: python program.py <input_file>", file=sys.stderr)
        sys.exit(2)

    input_path = sys.argv[1]
    # NOTE: This original file intentionally does not handle blank lines or
    # alternate delimiters robustly. Do not modify program.py for Task 1.
    with open(input_path, "r", encoding="utf-8") as f:
        lines = f.read().splitlines()

    total = 0
    count = 0
    top_score = -999
    top_id = ""

    for line in lines:
        # Deliberately naive parsing (seeded bug: will fail on empty lines or wrong delimiter)
        parts = line.split(',')
        id = parts[0]
        score = int(parts[1])
        total += score
        count += 1
        if score > top_score:
            top_score = score
            top_id = id

    avg = total / count
    print("Summary Report")
    print("Total records: {}".format(count))
    print("Average score: {:.2f}".format(avg))
    print("Top scorer: {} ({})".format(top_id, top_score))

if __name__ == "__main__":
    main()

How materials were constructed and why
- program.py: A short, dependency-free Python 3 script that reads a single input file (specified on the command line), parses each line as "ID,score", computes a total record count, the average score (printed with two decimals), and the highest-scoring record. This forces the candidate to diagnose and apply a minimal and robust fix (e.g., skip empty lines and strip whitespace).
- Ambiguity: README-run.txt intentionally mentions comma-separated fields but also notes that some sources may use semicolons.

### Exam Purpose
Confirm that the candidate can perform practical trial runs of programs and small software components to verify they produce the desired information and that the instructions (how to run/use them) are correct. In real-world terms: run provided code, reproduce expected outputs, design simple automated checks, diagnose failures, make minimal repairs or clarifications, and produce reproducible evidence of the steps taken.

### Core Competencies to Be Tested
- Environment setup and deterministic execution (run a program with given inputs and commands)
- Reproducing and capturing expected outputs (console/text file outputs)
- Designing and running simple automated tests (unit tests or small test harnesses)
- Basic debugging and fixing of obvious faults (logic bug, off-by-one, parsing error)
- Clear, reproducible reporting of steps and evidence (commands used, outputs, time spent)
- Judgement about whether to change code vs. change instructions (and documenting that decision)
- Minimal code hygiene for fixes (clear small patches, comments, and minimal error checks)

### Recommended Structure (Basic exam — entry level)
Total time allowed: 90 minutes. Candidate submits a single JSON file named test_submission.json containing structured answers and embedded artifacts (see JSON schema below). Candidate may also include corrected source files as fields inside JSON.

Overview — 3 hands-on tasks, increasing complexity:
1. Task 1 — Run & Reproduce (20 minutes)
   - Objective: Run one small provided program/script with an included input file and reproduce the expected output (expected output provided).
   - Deliverable: console output captured, exact commands used, whether output matched. If not matched, brief note of observed mismatch.
2. Task 2 — Automated Checks (30 minutes)
   - Objective: Create and run a small automated test harness (e.g., a few unit tests or a script that validates core outputs) that verifies key behaviors of the program.
   - Deliverable: test files (source), test run logs (pass/fail for each test), commands used, and short explanation of test coverage.
3. Task 3 — Diagnose & Fix (30 minutes)
   - Objective: Find and fix a deliberate, small bug or ambiguity in the program or run instructions that prevents correct behavior for a small extra input case. Make a minimal patch and re-run Task 1 and Task 2 to show success.
   - Deliverable: patched source (embedded in JSON), patch notes (what changed and why), re-run outputs and test logs, and brief commentary on alternative fixes if any.

Final packaging: A single JSON file test_submission.json containing:
- candidate metadata (name, candidate_id, start_time, end_time)
- per-task structured evidence (commands, outputs, files added/edited, time spent)
- embedded corrected source files (text fields) and test files
- optional short self-evaluation (areas confident vs. uncertain)

Suggested time allocation:
- Setup & Task 1: 20 min
- Task 2 (tests): 30 min
- Task 3 (fix + verification): 30 min
- Finalize & create JSON: 10 min (this overlaps; ensure total ≤ 90)

### Practicality — Making it a hands-on assessment
- Provide the candidate with a small codebase (single-file script or 2–3 files) and a small dataset (text/CSV/JSON) packaged for offline use.
- Do not provide expected answers beyond one canonical expected output file for Task 1 and a short description of the extra-case behaviour for Task 3.
- Candidate must run the code locally, capture real console logs and include them in the JSON; they cannot rely on conceptual descriptions.
- Candidate must implement and run actual tests (not just explain what they would test).
- Candidate must submit the actual corrected source and test files as part of the JSON so the evaluator can re-run them.

Notes on technology choices (exam creator):
- For a basic exam expect language = Python 3 (common availability); provide a requirements-free script (no external packages). If another language is used, provide a single Dockerfile or clear run commands, but prefer avoiding external dependencies to keep exam fair without internet access.

### Strategic elements that distinguish practical skill
- Multi-step verification:
  - Require the candidate to first run the original program (unmodified) and show the result.
  - Ask them to create an automated check that codifies the acceptance criteria so success can be re-run deterministically.
  - Then require them to alter code or instructions minimally to address a failing case and show the tests now pass.
- Data dependency:
  - Include at least one small input dataset with an edge case that exposes a bug (e.g., trailing newline, empty field, or off-by-one boundary).
- Decision points:
  - Make one issue ambiguous so the candidate must decide to (a) modify the code to accommodate a reasonable interpretation, or (b) update the run instructions to state the precondition; require justification for their decision.
- Monitor reproducibility:
  - Candidate must include exact commands used and capture standard output and exit codes (or test runner output), so evaluator can repeat steps.
- Minimal but meaningful debugging:
  - Bugs should be fixable with small changes (1–15 lines), e.g., wrong operator, incorrect index, improper string split, integer division issue, or inadequate input validation.

### Evaluation Insights (what to look for and scoring)
Scoring model (100 points total). Entry-level expected pass ≥ 80% for qualified candidates.

- Task 1 — Run & Reproduce (25 pts)
  - 10 pts: Correct commands given and executed (including any environment commands).
  - 10 pts: Captured outputs match the expected output exactly (or acceptable documented differences).
  - 5 pts: Clear explanation if mismatch (observed vs expected).
- Task 2 — Automated Checks (25 pts)
  - 10 pts: Test harness exists and runs with a single command.
  - 10 pts: Tests correctly assert the important behaviors (at least 2–3 meaningful tests).
  - 5 pts: Test outputs/logs included and documented.
- Task 3 — Diagnose & Fix (35 pts)
  - 10 pts: Correct identification of root cause (bug or ambiguous instruction).
  - 15 pts: Correct, minimal patch applied; code included and runnable.
  - 10 pts: Re-run shows passing tests and expected outputs; explanation of trade-offs/alternatives.
- Documentation & Reproducibility (15 pts)
  - 5 pts: JSON is properly formatted, contains all requested fields and artifacts.
  - 5 pts: Commands, timestamps, and time_spent entries are complete and plausible.
  - 5 pts: Clear, concise patch notes and decision justification.

Partial credit rules:
- If tests were written but do not run due to syntax errors, award partial credit for intent and coverage.
- If a candidate correctly diagnoses the issue but does an inferior fix (e.g., brittle workaround), award partial credit but deduct for maintainability concerns (noted in comments).

Observable outputs that indicate competence
- Exact console logs matching expected output file(s)
- Test harness output showing PASS for all listed tests
- Patched code embedded in JSON that is runnable and minimal
- Clear sequence of commands that allow the evaluator to re-run the steps
- Reasoned explanation for any decision to change instructions vs. code
- Time_spent values consistent with 90-minute limit (majority of time spent on test/fix tasks)

### Deliverable JSON schema (recommended fields)
Provide this schema to candidates. The evaluator will rely on these fields.

{
  "candidate": {
    "name": "string",
    "candidate_id": "string",
    "start_time": "ISO8601 timestamp",
    "end_time": "ISO8601 timestamp"
  },
  "tasks": [
    {
      "task_id": "T1",
      "title": "Run & Reproduce",
      "time_spent_minutes": number,
      "commands_executed": ["string", "..."],
      "raw_console_output": "string",
      "expected_output_match": "yes|no|partial",
      "difference_note": "string"
    },
    {
      "task_id": "T2",
      "title": "Automated Checks",
      "time_spent_minutes": number,
      "test_files": {
        "filename1.py": "string contents",
        "..."
      },
      "test_command": "string",
      "test_output": "string",
      "tests_passed": number,
      "tests_failed": number,
      "coverage_note": "string"
    },
    {
      "task_id": "T3",
      "title": "Diagnose & Fix",
      "time_spent_minutes": number,
      "root_cause": "short description",
      "patch_files": {
        "filename1.py": "string contents",
        "..."
      },
      "patch_summary": "string",
      "commands_exexecuted_after_patch": ["string"],
      "post_patch_console_output": "string",
      "post_patch_test_output": "string",
      "final_status": "fixed|not_fixed|partially_fixed",
      "decision_justification": "string"
    }
  ],
  "self_evaluation": {
    "confidence_level": "1-5",
    "notes": "string"
  }
}

Evaluator instructions
- Re-run the exact commands listed in commands_executed fields to verify outputs.
- Save embedded source/test files to disk and run the declared test command.
- Use the scoring rubric to assign points per task. Inspect patch size and quality for Task 3.
- If any ambiguity remains, check whether the candidate documented a justification; give credit when the justification is reasonable.

### Final notes for exam creators
- Keep the codebase small and dependency-free.
- Seed one clear but non-trivial bug and one ambiguous instruction to evaluate judgment.
- Make expected outputs precise (byte-for-byte) for Task 1 to force exact runs.
- Ensure tests can be executed with a single command (e.g., python -m pytest or python run_tests.py).
- Limit total work so a competent entry-level candidate can comfortably score >80% in 90 minutes.

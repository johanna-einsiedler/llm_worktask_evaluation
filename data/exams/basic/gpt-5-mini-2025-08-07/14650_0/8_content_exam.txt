### Exam Title
Update an existing automated test suite so it is current, reliable, and maintainable (Basic practical exam — 90 minutes)

### Instructions for Candidate
You have 90 minutes to complete this hands-on practical assessment. Use only the computer, the provided code execution environment, and a text editor. No internet access or external packages are available. Start a timer when you begin and record start/end times in UTC (ISO 8601).

High-level goal: reproduce failing tests from the provided project, diagnose root causes, make minimal and correct edits to the automated tests or test helpers so the suite becomes current and more robust, re-run tests, and document everything in a single JSON file named test_submission.json.

Step-by-step (follow this order):
1. Read the README and examine the repo contents (0–5 minutes).
   - Identify the single command in the README to run the test suite (e.g., ./run_tests.sh or python -m pytest tests/). Use that command for all runs.
2. Run the test suite once as-is and capture the complete raw console output (5–15 minutes).
   - Save the exact command you executed and its raw output.
3. Diagnose failing tests by inspecting:
   - The failing test files under tests/
   - The application files under app/ (static HTML/JS) and any test data files
   - Any test helpers or config files used by the tests
   - Identify the root cause(s): broken selector(s), hard-coded sleeps, config/API changes, deprecated helper usage, or test logic mismatch.
4. Make targeted edits to the test files or test helpers to fix three focused issues (15–55 minutes). Typical edits expected:
   - Task A (Selector fix): Fix one or two tests where an element id/class/text changed — update locator(s) to a stable approach.
   - Task B (Timing/stability): Replace a hard-coded sleep with an explicit wait/poll (or otherwise make the test deterministic).
   - Task C (Config/API/deprecation): Update a broken config value, test data path, or replace a deprecated helper/API call used by tests.
   - Do not delete whole tests or silence assertions; changes should be minimal and reasonable.
5. Re-run the test suite iteratively until you reach a stable final run (55–75 minutes).
   - Capture the final raw console output.
6. Add one small improvement if time permits (75–85 minutes). Examples: refactor a repeated selector into a helper function, add a short comment explaining a non-obvious wait, or minor test cleanup.
7. Prepare and save test_submission.json (name must be exact) with all required fields (75–90 minutes).
   - Ensure start_time_utc, end_time_utc and total_minutes are included.

Important rules
- Use only the provided repository and the local environment.
- Do not fetch external libraries or services.
- Do not remove tests to make the suite pass; prefer targeted fixes.
- Keep edits minimal and focused. The evaluator will review original vs updated file contents.

### Expected Outcome
By the end of the session you must provide:
- Evidence that you reproduced failing tests: the initial test run command and its raw console output showing failing tests.
- The final test run command and its raw console output after your edits.
- A set of changed files with both the original and updated full file contents, along with a short rationale for each change (1–3 sentences).
- A short high-level summary (<= 300 words) describing what you changed and why.
- A short list of remaining risks and recommended next steps.
- Optional: brief description of any small improvement you added (bonus).

Minimum objective expectations (for scoring):
- You must have captured the original failing output.
- You must have made at least the three kinds of fixes described (selector, timing/stability, config/API/deprecation), unless a provided repo already has fewer eligible issues — in that case fix all failing issues present.
- The final test run output should show that the previously failing tests you targeted now pass (evidence in final_test_output).

### Provided Materials
You will be given a self-contained exam package (zip or repo) that includes:
- README (includes the single command to run the tests).
- run_tests.sh (or equivalent script) and/or instructions to run the tests locally (do not alter these unless you must to make tests pass; document any such change).
- app/ — a small static application used by the tests (HTML/CSS/JS).
- tests/ — pytest-based tests (or the runner described in README) that currently fail for realistic reasons:
  - at least one test uses a selector whose id/class/text has changed
  - at least one test contains a hard sleep (e.g., time.sleep(...) or similar) causing flakiness
  - at least one test requires a config/data/path/API change or deprecated helper usage
- test data files (JSON, fixtures) referenced by tests, possibly with a changed path/format.
- CHANGELOG.txt or SCENARIO.txt that briefly states that the app changed in a few small ways and tests must be updated.

Notes:
- The provided environment includes all required runtimes for the tests (Python and pytest and any included drivers). You do not need to install packages.
- All needed files are included in the repo; no network access is required.

### Submission Format
You must submit one file named exactly test_submission.json placed at the repository root. The file must be valid JSON and include these fields (all required unless marked optional):

- candidate_name: string
- start_time_utc: string (ISO 8601)
- end_time_utc: string (ISO 8601)
- total_minutes: integer
- commands_run: array of objects, each:
  - command: string (exact command you executed)
  - purpose: string (short description of what that run was for)
- initial_test_output: string (raw console output captured from the first run)
- final_test_output: string (raw console output after your edits)
- changed_files: array of objects, each:
  - file_path: string (relative path)
  - original_content: string (full file text as you received it)
  - updated_content: string (full updated file text after your edits)
  - short_rationale: string (1–3 sentences: what you changed and why)
- summary_of_changes: string (plain text, max 300 words — high-level summary of all edits and rationale)
- risk_notes_and_next_steps: string (short list of remaining risks, assumptions, or recommended improvements)
- optional_bonus: string (optional — brief description of any extra improvement you added)

Formatting and content requirements
- Provide exact commands and raw outputs (copy/paste full console output). Do not edit or truncate the logs except to remove machine-specific timestamps if absolutely necessary — in that case indicate you redacted timestamps.
- For changed_files, include full original and updated file contents so the evaluator can verify diffs.
- Keep short_rationale concise and factual.
- Ensure JSON is well-formed. Submissions missing required fields will be marked down.

Evaluator will verify:
- That the initial output shows the stated failures.
- That the candidate made minimal, targeted edits and did not simply delete tests.
- That the final output shows the previously failing tests now passing (or documents why full passing was not feasible).
- That the explanations justify the changes and mention trade-offs or remaining risks.

def get_page_content(path):
    """Return raw file content for a given path."""
    with open(path, 'r', encoding='utf-8') as f:
        return f.read()

def find_by_id(content, elem_id):
    """Naive find: return the start tag containing id='elem_id' or None."""
    token = 'id="' + elem_id + '"'
    start = content.find(token)
    if start == -1:
        return None
    tag_start = content.rfind('<', 0, start)
    tag_end = content.find('>', start)
    if tag_start == -1 or tag_end == -1:
        return None
    return content[tag_start:tag_end+1]

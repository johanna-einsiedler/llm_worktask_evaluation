tests/utils.py

# Minimal utilities used by tests (no external dependencies)
import re

def load_html(path):
    with open(path, 'r', encoding='utf-8') as f:
        return f.read()

def find_by_id(html, id_name):
    # Very simple literal check for id attribute
    return f'id="{id_name}"' in html

def get_welcome_message(html):
    m = re.search(r'<div class="welcome-message">(.*?)</div>', html, re.DOTALL)
    return m.group(1).strip() if m else ""

tests/test_login.py
---
import time
import json
from tests.utils import load_html, find_by_id, get_welcome_message
from tests.conftest import get_data_path

def test_login_button_exists():
    """
    Task A: This test checks for a button with id 'login-button'.
    The app's button id was changed; update the locator accordingly.
    """
    html = load_html('app/index.html')
    assert find_by_id(html, 'login-button'), "Expected login button with id 'login-button'"

def test_welcome_message():
    """
    Task B: This test uses a hard sleep and asserts exact welcome text.
    Make the assertion more robust and replace the hard sleep.
    """
    html = load_html('app/index.html')
    # Fragile sleep introduced previously
    time.sleep(1)
    assert get_welcome_message(html) == "Welcome, User"

def test_user_data_loaded():
    """
    Task C: This test loads users.json using a DATA_DIR from conftest.
    The test data directory changed; update config so this test can find the file.
    """
    path = get_data_path('users.json')
    with open(path, 'r', encoding='utf-8') as f:
        data = json.load(f)
    assert isinstance(data, list)
    assert data[0]['username'] == "TestUser"

<MATERIALS_EXPLANATION_FOR_EVALUATOR>
How the materials were constructed and the intended assessment flow:

Overview
- This is a minimal, deterministic pytest-based project. There are three failing checks that align with the exam core competencies:
  1) Selector mismatch (test_login_button_exists) — app button id changed to "btn-login" while the test looks for "login-button".
  2) Timing / fragile assertion (test_welcome_message) — test includes an unnecessary hard sleep and asserts exact text "Welcome, User" while app now shows "Welcome, TestUser".
  3) Config/data path mismatch (test_user_data_loaded) — tests use DATA_DIR = "data" (in tests/conftest.py) but test file is actually located at test_data/users.json.

Files and relationships
- app/index.html: the application under test (static HTML). It contains:
  - button id="btn-login"
  - div.welcome-message "Welcome, TestUser"
- test_data/users.json: JSON test data containing a list with the first object's username == "TestUser".
- tests/conftest.py: defines DATA_DIR = "data" and helper get_data_path(filename). This is intentionally incorrect to require a config fix.
- tests/utils.py: small parsing helpers (load_html, find_by_id, get_welcome_message). These are simple to keep edits minimal and self-contained.
- tests/test_login.py: three tests, each demonstrating one of the required fix types:
  - test_login_button_exists -> selector fix
  - test_welcome_message -> timing/stability fix (replace sleep with explicit wait or remove it and make assertion robust)
  - test_user_data_loaded -> config/data path fix by updating DATA_DIR or get_data_path

Deterministic behavior
- All files use fixed strings and paths. There are no external dependencies, no randomness, and no network usage.
- Running ./run_tests.sh executes pytest over the tests directory; the initial run will produce three failing tests or errors reproducibly.

Common traps and candidate mistakes
- Deleting tests or silencing assertions: evaluator should flag edits that remove assertions or tests instead of fixing them.
- Changing app files: candidate should update tests/config, not app/index.html. The app is the "source of truth" and should remain unchanged.
- Overly broad fixes: e.g., changing the assertion to always pass (assert True) will pass but is not acceptable; evaluator should check changed_files for reasonable fixes.
- Wrong path edits: candidate might move test_data to 'data' in repo rather than update tests/conftest.py. Moving files is not prohibited but is less desirable than updating test config; evaluator should accept either but prefer minimal test edits.
- For timing fix: candidates might simply remove time.sleep(1) and still assert exact text "Welcome, User" — that will still fail. Correct fix is to either:
  - change assertion to accept dynamic username (e.g., assert message.startswith("Welcome,")), and remove sleep; or
  - replace sleep with a short poll loop that waits for the welcome message to contain "Welcome," up to a timeout.

Expected correct changes
- Update the selector in test_login_button_exists to 'btn-login' OR adjust find_by_id to accept multiple locator strategies (e.g., check id or class or button text). Minimal acceptable change: change the test assertion to find_by_id(html, 'btn-login').
- Replace the hard sleep in test_welcome_message with a simple polling loop (with a short timeout), and make the assertion robust (e.g., check that the message starts with "Welcome," or contains "Welcome").
- Update tests/conftest.py DATA_DIR from "data" to "test_data" so test_user_data_loaded can find test_data/users.json.

How these materials assess practical skill
- The candidate must run the suite, inspect failing outputs, map failures to lines in tests and helpers, open the app HTML and test_data to discover root causes, implement targeted fixes, and re-run tests — exactly the real-world workflow required.
- The three discrete issues evaluate different skills:
  - selector reasoning and stable locator choice
  - replacing fragile sleeps with explicit checks and writing robust assertions
  - understanding configuration and file path dependencies

Evaluator guidance
- Confirm that initial test run (as-provided) shows failures: a failed assertion about login-button, a failed exact equality for welcome message, and a file-not-found or failed open for data file.
- Verify changed_files in the submission include full original and updated file contents and that edits are minimal and targeted.
- Verify that final_test_output shows the previously failing tests now pass.
- Prefer edits that improve robustness (e.g., assertion that checks startswith or contains) rather than hacks.
- Consider small acceptable alternative fixes (e.g., altering tests/conftest.py DATA_DIR vs moving test_data), but prefer changes to tests/config rather than modifying app.

Time sizing
- The project is intentionally small so a qualified junior SQA engineer can reproduce failures and complete three fixes within the 90-minute window.

--- tests/helpers.py ---
import json

# Internal counter to simulate a stateful endpoint that becomes ready only after several polls.
_state = {"status_calls": 0}

def get_status():
    """
    Simulates querying a status endpoint that only returns 'ready' after 3 calls.
    Each call increments an internal counter. This deterministic behavior is used
    to exercise polling logic in tests.
    """
    _state["status_calls"] += 1
    if _state["status_calls"] >= 3:
        return "ready"
    return "not ready"

def load_fixture(path):
    """
    New helper API: load JSON fixture from 'path'. Tests should call this instead of the older
    load_test_data function (which was removed).
    """
    with open(path, "r") as f:
        return json.load(f)

How materials were constructed and why:

Goal: provide a small, deterministic, self-contained test project that fails in three realistic ways that commonly occur when applications evolve: selector/id changes, fragile timing assumptions, and helper API/config changes. The materials require only standard Python and pytest (both assumed present); no network or external libraries are required.

Files and relationships:
- app/pages/home.html is the "application under test". It intentionally contains:
  - The login button with id="btn-login" and data-test="login-button".
  - A status div and version string.
- tests/helpers.py mimics the test helper module. It purposely:
  - Implements get_status() that only returns "ready" after being called 3 times (deterministic, stateful).
  - Exposes load_fixture(path) to load JSON fixtures. Note: it does NOT expose load_test_data(path) to simulate a deprecation/removal.
- tests/test_selector.py simulates a UI test that looks for id="login-button". Because app/pages/home.html now uses id="btn-login" (and provides data-test), the assertion fails. This tests a selector fix: candidate should update the test to use a more robust locator (e.g., data-test attribute or new id).
- tests/test_timing.py simulates a fragile timing test that uses one fixed sleep and a single call to helpers.get_status(). Because get_status requires 3 calls before returning "ready", this test fails. Candidate should replace the fixed sleep+single-call with an explicit polling loop (retry until helpers.get_status() == "ready" or a timeout).
- tests/test_config.py simulates a deprecation/config issue: it calls helpers.load_test_data(...) and reads an outdated fixture path. helpers.py does not provide that function and fixtures are located at tests/data/fixtures/users.json. Candidate should update the test to use helpers.load_fixture("tests/data/fixtures/users.json") (or provide a minimal compatibility shim).

Deterministic patterns and expected fixes:
- Selector fix (test_selector.py)
  - Expected correction: change assertion to look for 'data-test="login-button"' or 'id="btn-login"'. Prefer data-test as a stable selector.
  - Evaluator should verify candidate did not modify app/pages/home.html.
- Timing/stability fix (test_timing.py)
  - Expected correction: replace time.sleep(...) + single check with a small polling loop (e.g., loop up to 10 iterations with short sleeps) calling helpers.get_status() until it returns "ready" or timeouts. This demonstrates replacing brittle sleeps with explicit waits.
  - Evaluator should ensure test still fails if candidate simply increases the sleep to a huge value or removes assertion; prefer polling logic.
- Config/API/deprecation fix (test_config.py)
  - Expected correction: update test to call helpers.load_fixture("tests/data/fixtures/users.json") and verify content. Alternatively, adding a small compatibility wrapper in tests/helpers.py (e.g., def load_test_data(path): return load_fixture(path) with path translation) is acceptable if minimal and documented.
  - Evaluator should check candidate made minimal, targeted edits rather than deleting tests or disabling assertions.

Common traps and mistakes candidates might make:
- Editing app/pages/home.html to match the old selectors (not allowed by scenario). Evaluator should reject such approach.
- Removing or commenting out assertions to force tests to pass. Ensure changed_files show minimal, purposeful edits.
- Adding heavy time.sleep increases (works but is brittle). Prefer polling; evaluator should prefer polling fixes.
- Changing helpers.py to reintroduce the old API is acceptable but should be minimal and include rationale in submission.

How the materials separate practical vs conceptual skills:
- The candidate must run pytest, read failing stack traces, inspect test files and app files, map failures to causes, and implement code edits to tests/helpers. This validates hands-on debugging and editing skills rather than purely theoretical answers.

### Exam Purpose
Confirm that the candidate can keep automated tests current in a real-world setting: run an existing automated test suite, diagnose why tests fail after a small, realistic change in the application surface (API response, UI text/locator, or test data), update the automated tests (not the application code) so they become reliable and correct again, and document the changes so they are reproducible and reviewable.

This verifies practical abilities needed on the job: reading and running tests, debugging failures, making minimal correct updates to test code, knowing good locator/assertion choices, and producing clear evidence of what was done.

### Core Competencies
- Running an automated test suite and interpreting test runner output and stack traces.
- Locating the single point(s) of failure in test code (e.g., outdated locators, assertions, test data).
- Modifying test scripts to match a changed behavior or interface while following best practices (keep tests maintainable, use stable selectors/assertions).
- Adding or adjusting test data / mocking stubs when required.
- Producing a clear, reproducible submission describing changes and showing before/after results.
- Keeping changes minimal and focused, avoiding changing application code or bypassing test intent.

  - Example scenarios:
    - API shape changed: a response field renamed from userName → username.
    - UI change: a button label text changed, and the test used label-based selector instead of stable data attribute.
    - Flaky timing: a test uses a fixed sleep instead of waiting for an element; the app now takes longer occasionally.
    - Test data expiry: sample date value in test data is now in the past.

### Strategic Elements (multi-step processes & decision points)
These are the elements that separate someone who "knows the theory" from someone who can actually perform the task:

- Repro Steps: Candidate must first run the tests and show failing output. This tests ability to operate the test environment.
- Root-cause analysis: Candidate must read stack traces and test code to decide what to change. Decision points include:
  - Update selectors vs. update application stubs? (Must update tests only)
  - Make test more robust (use data-test-id/wait-for element) vs. change assertion to accept both old and new values (not recommended).
  - Fix test data vs. change fixture code — choose minimal correct fix.
- Minimal-change principle: Candidates should prefer minimal, targeted edits that restore the test's intent, not broad rewrites. This shows judgement.
- Robustness trade-offs: If a test used fragile selectors, a stronger candidate will replace them with stable alternatives (data attributes) or restructure assertion. This shows maintenance-awareness.
- Re-run and verify: Candidate must iterate — run tests, make small change, re-run — demonstrating debugging skills.
- Documentation: Candidate must explain why each change was made and how to reproduce the passing run. This demonstrates traceability for reviewers.

Include one explicit decision point in the task instructions: the candidate must explain any instance where they chose to broaden an assertion vs. tighten selectors and justify the choice.

### Evaluation Insights (how to judge competence)
A suggested scoring rubric (basic, totals to 100):

- Tests passing after changes: 50%
  - All required tests green: full marks in this category.
  - If some non-required tests remain failing or extra tests added fail: partial deduction.
- Correctness and minimality of changes: 20%
  - Changes only in test code and supporting fixtures/mocks, and focused edits rather than broad rewrites.
  - Avoided modifying application logic.
- Clarity of explanations and reproducibility: 15%
  - Clear explanation_of_changes for each modified file.
  - Reproduce instructions work and updated_test_results plausibly match what would run.
- Test quality / maintainability improvements: 10%
  - Use of stable selectors, proper waits, good assertions, removal of brittle sleeps, better fixture usage.
- Time management and completeness: 5%
  - Submitted within time and included all required fields in test_submission.json.

Observable outputs to look for:
- initial_test_results showing clear failing stack traces (confirms candidate actually ran baseline).
- updated_test_results showing successful runs (or clear, justified partial fixes).
- modified_files: diffs that demonstrate minimal, appropriate edits.
- explanation_of_changes: shows reasoning and root cause analysis, not generic statements.
- Repro instructions that match the commands a reviewer would run.

Red flags that indicate lack of competence:
- Candidate modifies application source rather than test code.
- Candidate simply comments out failing assertions instead of fixing them.
- Missing before/after test results or incomplete modified_files contents.
- Large, unnecessary refactors with no justification.
- Incorrect or unsafe fixes (e.g., changing test to assert nothing meaningful).

- Purpose: Provide a small, deterministic repo where the application code reflects the updated/current behavior and tests intentionally reference the old behavior. The candidate must update only the test code (including fixtures/helpers) to make the tests reflect the current application surface.

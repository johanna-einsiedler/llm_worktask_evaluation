SCENARIO.txt
------------
The web application changed in three small ways. Automated tests were not updated and now fail.
- The login button ID changed to a new id and a data-test attribute was added.
- The dashboard welcome loader is asynchronous; a helper function name changed and tests use a fixed sleep.
- The backend API was updated from version v1 to v2 and tests still assert v1.

Your task: run the provided test runner, inspect failures, update test scripts or helpers (minimally) so tests are reliable and pass, replace fragile sleeps with an explicit wait/poll, and document everything in test_submission.json.

tests/helpers.py
----------------
import time
def get_welcome_message(file_path):
    """
    Read the dashboard HTML and return the inner text of the welcome div.
    (This is a simple parser; tests import this helper.)
    """
    with open(file_path, 'r') as f:
        html = f.read()
    start = html.find('<div id="welcome"')
    if start == -1:
        return ""
    start = html.find('>', start) + 1
    end = html.find('</div>', start)
    return html[start:end].strip()

Overview of construction
- Purpose: Provide a compact, deterministic repo with three failing tests that map to common, realistic causes:
  1. Selector/id change (login button id changed; test expects old id).
  2. Timing/flakiness + deprecated helper usage (test uses a hard sleep and imports a helper by an old name).
  3. API/config mismatch (tests expect API v1 while config.py reflects v2).

Why these files and relationships
- app/index.html: includes a deliberate change: id="btn-login" and a stable data-test="login-button". The intended candidate action is to prefer the stable data-test attribute rather than brittle id or to adapt the test to the new id in a minimal, robust way.
- app/dashboard.html: contains the welcome message; in the real world this message might be produced asynchronously. The tests simulate waiting by including a hard sleep; the helper has the canonical function name get_welcome_message while the test imports get_dashboard_message (nonexistent) causing an ImportError/NameError. The candidate must reconcile timing and the function name mismatch (either update the test import to the new function name and replace the hard sleep with an explicit wait/poll, or add an alias/wait inside the helper).
- config.py: reflects an app-level API change (v2). tests/test_api.py still asserts v1. Candidate must update tests or update config to reflect current API; the exam expects the candidate to update the automated tests or test helpers to be current and maintainable.

Deterministic behavior and verifiable outcomes
- All files are static; test execution is deterministic (no randomness). The three tests will fail on first run with clear messages:
  - test_login.py assertion failure shows missing id "login-button".
  - tests/test_dashboard.py will fail due to ImportError or NameError for get_dashboard_message (depending on import resolution) and even if import succeeded the hard time.sleep is fragile; the candidate should remove the hard sleep and implement an explicit wait/poll.
  - tests/test_api.py fails asserting config.API_VERSION == "v1".

Expected correct fixes (one straightforward path)
- Fix 1 (Selector): Update tests/test_login.py to assert presence of data-test="login-button" (stable selector) or to search for either id or data-test. This demonstrates using stable selectors.
- Fix 2 (Timing / deprecation): Update tests/helpers.py to provide a compatibility alias get_dashboard_message that implements an explicit wait/poll (e.g., check file for welcome div in a loop with a short sleep interval and a timeout) and update tests/test_dashboard.py to remove the hard-coded time.sleep and rely on the helper. Or update the test to import get_welcome_message and implement an explicit wait that polls for message existence. Either approach shows diagnosing helper name mismatch and removing brittle fixed sleeps.
- Fix 3 (Config/API): Update tests/test_api.py to assert current API version ("v2") or make the assertion robust (e.g., check it startswith 'v'). Minimal, just update expected value to "v2". This shows recognizing app version change and updating tests.

Traps and common candidate errors
- Deleting tests or commenting out assertions: evaluator should mark down; candidate must not remove assertions.
- Only changing config.py to lie about version (instead of updating tests) is acceptable in some contexts, but better practice is updating test expectations to match app. The evaluator should check rationale in submission.
- Moving the hard sleep to a helper without making it condition-based (e.g., keeping a fixed time.sleep(2)) does not demonstrate improving robustness; the helper must implement polling with timeout to earn full credit.
- Candidates might change tests to accept multiple values (v1 or v2). That's acceptable but they should justify it in rationale.

How this differentiates conceptual vs practical skill
- Candidate must run tests and paste raw console output — shows they can reproduce failures.
- Candidate must read test traces and find which lines lead to failures (practical debugging).
- Candidate must edit code (tests or helpers) minimally and re-run tests to show the fixes worked (hands-on coding).
- Correct solutions show awareness of maintainable testing practices: prefer stable selectors (data-test), use explicit waits/polling rather than fixed sleeps, and update test expectations for API changes with clear rationale.

Scoring guidance
- Reproducing failures: initial pytest output should show three failing tests with clear assertion or import errors.
- Selector fix: tests/test_login.py should be updated to use data-test or to check for both new id and data-test.

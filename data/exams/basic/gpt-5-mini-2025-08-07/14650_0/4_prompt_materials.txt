### Exam Purpose
Confirm that the candidate can take an existing automated test-suite, identify why tests are failing or brittle after changes to the application or requirements, and update the automated tests so they are correct, resilient, and maintainable. This mirrors the real-world skill of keeping automation current when the SUT (system under test) evolves.

### Core Competencies
- Running and interpreting automated test suites (pytest / test runner basics).
- Diagnosing failing tests: reading stack traces, locating broken assertions, and identifying brittle test patterns.
- Modifying automated test scripts to match updated application behavior or to increase robustness (selectors/inputs/assertions/fixture usage).
- Adding a minimal, correctly structured automated test that follows project style and runs with the suite.
- Clearly documenting what was changed and why so the change is reviewable and reproducible.

These competencies combine technical test-editing ability, debugging, and communication — all critical to keep automation current.

### Recommended Structure
Total time: 90 minutes maximum.

Number of tasks: 4 sequential, practical tasks that must be completed and documented in a single JSON submission file named test_submission.json.

High-level sequence and expected time allocation:
1. Environment & baseline run — 10 minutes
   - Start from a prepared exam repository (bundled with the exam). Run the test suite and capture the failing tests output.
   - Deliverable: captured "before" test output.

2. Diagnosis & plan — 10 minutes
   - Inspect the failing tests and small SUT files provided. Note the root causes and decide which tests should be changed (not the product code).
   - Deliverable: short decision log of planned changes.

3. Implement updates to automated tests — 45 minutes
   - Make required changes so the test suite reflects the new, correct behavior and is more robust (as specified in provided README/spec).
   - Make small refactors to remove obvious brittleness (e.g., replace hard-coded waits or fragile string matches with regex/contains; use fixtures for repeated setup).
   - Add one new test for a small new requirement described in the repo README.
   - Deliverable: modified/added test files (content included in the JSON), and the commands used.

4. Run, verify, and document — 25 minutes
   - Run the full test suite, capture "after" output showing tests pass.
   - Provide a concise explanation (per modified file) of what changed and why, and reproduction steps.
   - Deliverable: test_submission.json with fields described below and any final notes.

Expected final deliverables (all inside test_submission.json):
- commands_run: list of commands the candidate executed
- test_output_before: raw output (or first/last 40 lines) of the initial failing test run
- test_output_after: raw output (or first/last 40 lines) after changes
- modified_files: array of objects { path, reason, content }
- added_files: array (if any) { path, reason, content }
- succinct decision_log: step-by-step short rationale
- reproduce_instructions: commands an evaluator can re-run to reproduce results

Why this structure:
- It forces a candidate to do a realistic diagnosis-edit-run loop.
- It is simple enough to complete in 90 minutes but contains multiple decision points that separate junior vs. more practiced candidates.

### Practical Elements to Include
To ensure this is a hands-on practical test (not a knowledge quiz), the exam package given to candidates must include:
- A small self-contained SUT implemented in a language available in candidate environment (recommendation: Python module + simple CLI or functions). No external network or dependencies needed beyond the bundled venv or pure-Python code.
- A pytest-based automated test suite that initially fails because the SUT has changed from the tests’ expectation. Typical realistic failure patterns:
  - Output format changed (e.g., additional field in a printed JSON or a header change).
  - Function signature slightly changed (optional parameter introduced/renamed) but business logic is similar.
  - Tests using brittle assertions (exact timestamp match, strict full-string comparisons, fragile ordering) that need to be updated to robust checks.
  - Tests relying on hard-coded test data that no longer apply.
- A README/mini-spec describing:
  - the intended new behavior (so candidate knows what tests should assert)
  - one small new requirement to create a new automated test for (e.g., a new flag or an edge-case)
- Inline comments in tests to hint at common fragility patterns (but not full solutions).

Make it hands-on:
- Candidate must run pytest locally, edit the test files, add one test, and re-run pytest to produce passing results.
- No internet or external lookup required — all needed code & spec included.

### Strategic Elements (distinguish conceptual from capable)
Design the tasks to require multi-step reasoning and small trade-offs:
- Diagnosis step: Candidate must read stack trace and SUT code and decide whether to update test assertions or change setup fixtures. This reveals practical diagnostic skills.
- Decision point: Should the candidate update the test to match the new spec, or make the test more tolerant (e.g., partial match / regex)? A sound candidate will prefer correctness and maintainability over brittle quick fixes.
- Trade-offs in test design: e.g., update a test from checking full JSON equality to checking essential keys/values — this shows judgement.
- Data dependencies: Provide a test-data file the tests depend on; SUT uses that file. Candidate may need to update the test-data or write the test to be independent (e.g., mock or parametrize). This distinguishes those who can reason about test isolation.
- Small refactor: instruct candidate to remove an obvious anti-pattern (like time.sleep in tests) and replace with a synchronous or mocked approach. This tests their familiarity with best practices.

These elements require candidates to do more than apply rote edits; they must think about durability and maintainability of tests.

### Evaluation Insights
What to look for in the submission to indicate competence:

1. Functional correctness (required)
   - All tests pass after candidate updates: test_output_after shows pytest summary with 0 failures.
   - Candidate included commands_run and reproduce_instructions that actually rerun tests.

2. Evidence of correct diagnosis (required)
   - test_output_before shows the failing tests and error messages.
   - decision_log explains root cause for each failing test and why they chose the change they made.

3. Quality of test updates (important)
   - Changes are limited to test code (the SUT normally should not be edited for this basic exam). If SUT was edited, candidate must justify why.
   - Assertions updated to check relevant behavior (contain/regex/key checks) rather than brittle full-string matches.
   - Use of fixtures/parametrization where appropriate; no unnecessary duplication.

4. Maintainability & best practice (important)
   - No re-introduction of brittle constructs (e.g., sleeps). If timing issues exist, they used proper mocking or retries/timeouts when appropriate.
   - Test naming and structure are clear and consistent with project style.
   - New test added follows the same test conventions (naming, setup) and tests one clear behavior.

5. Communication & reproducibility (important)
   - Modified files are submitted as content in JSON with concise reason for each change.
   - Reproduction instructions are exact and short (commands_run and any env setup).
   - Decision_log lists alternatives considered and why they were not chosen (short bullet points are fine).

Suggested scoring rubric for a basic-level exam (total 100 points):
- Baseline execution (ran tests and captured before/after outputs) — 15 pts
- All tests passing after changes — 25 pts
- Correct diagnosis of failures (decision_log quality) — 15 pts
- Quality of test edits (correctness of assertions, reduced brittleness) — 20 pts
- Added test correctness & style — 10 pts
- Documentation & reproducibility (clear commands, file contents, reasoning) — 15 pts

Passing guideline for basic exam:
- A competent junior/entry-level candidate should score >= 80/100.

Minimum evaluator checks (fast pass/fail):

- Check that modified_files and added_files in test_submission.json contain the updated test content.
- Spot-check decision_log to ensure candidate understood root cause (1–3 short sentences per failing test is sufficient).

### Exam Purpose
To confirm that a candidate can take an existing automated test suite that has become out-of-date and, by inspecting failures and limited local resources, update the automated test scripts so they are current, reliable, and maintainable. In real work this means finding why tests fail after app changes (selectors, timing, API changes, config), fixing the tests (selectors/page objects, waits, assertions, config), re-running the suite and documenting the changes.

### Core Competencies to be Tested
- Reproducing test failures by running an existing test suite in a local environment.
- Diagnosing the root cause(s) of failing automated tests (selector changes, timing/flakiness, config/API changes, or test logic mismatches).
- Making minimal, correct edits to automated test scripts so they pass and are more robust.
- Replacing fragile constructs (hard sleeps, brittle selectors) with more reliable alternatives (explicit waits, stable selectors or page objects).
- Documenting changes clearly and justifying trade-offs.
- Producing reproducible evidence (test output/logs, before/after code snippets) that tests now pass.

### Recommended Structure (Basic exam — single-session, up to 90 minutes)
Overview: Provide the candidate with a small zipped exam package (or repo) they can run locally; candidate completes a sequence of 4 hands-on tasks and submits a single JSON file named test_submission.json containing required elements (see submission schema below).

Time allocation (90 minutes total):
- 0–5 minutes: Read instructions and examine repo layout and files.
- 5–15 minutes: Run the test suite and capture failing test output (Task 1).
- 15–55 minutes: Fix tests and re-run iteratively (Tasks 2, 3, 4).
- 55–75 minutes: Add one small improvement (stabilize a flaky test or update a config variable) and re-run.
- 75–90 minutes: Prepare test_submission.json and final notes.

Number of tasks and logical sequence:
- Task 1 (Reproduce): Run provided test runner. Capture failing tests and raw logs.
- Task 2 (Diagnose & quick fix): Fix an obvious selector mismatch in one or two test files so a core test passes.
- Task 3 (Stabilize): Replace a hard sleep with an explicit wait and/or update an assertion to be robust.
- Task 4 (Config/API or deprecation fix): Update a broken config (base URL, new endpoint path) or replace a deprecated API call used in tests.
- Optional small Task 5 (Bonus): Add one small test improvement (e.g., use a data-test attribute, refactor repeated selector into a page object or helper function).

Expected deliverables (all must be embedded in test_submission.json):
- Candidate metadata: name, start and end times, total minutes spent.
- Commands run (exact commands used to run tests) and their raw console output before and after fixes.
- A list of files changed; for each, include original content (as provided) and updated content (full file text).
- A short written summary for each change: what was wrong, what you changed, why, and risk/trade-off notes.
- Final pass/fail status of the test suite after fixes (explicit pass indication plus last run output).
- Optional: one or two short suggestions for further improvements.

Naming requirement: The candidate sends one file named test_submission.json containing the structured submission.

### How to make it a hands-on practical assessment (not a quiz)
- Provide a runnable local test project (small web app or static HTML pages) plus automated tests that currently fail because of obvious but realistic changes:
  - A test referencing an element whose id/class changed.
  - A test including a hard-coded time.sleep or sleep-based retry causing flakiness.
  - A test referencing a deprecated helper function or config variable that needs to be updated.
- The candidate must run the tests in the provided environment, inspect console logs, modify test code, re-run tests, and produce evidence of corrections.
- The exam package must be self-contained (no external downloads) so the candidate truly edits and runs code locally.

Suggested exam package contents (for exam creator to prepare):
- README with instructions and the single command to run tests (e.g., ./run_tests.sh or python -m pytest tests/).
- app/: a very small static app or mock server files (HTML/JS) used by tests.
- tests/: failing automated tests written in a single familiar stack (recommended options for basic level):
  - Option A (recommended): Python + pytest + Selenium WebDriver + local headless webdriver stub, OR
  - Option B: Node.js + Playwright test scripts (if environment supports node).
  Use one stack only. For the basic exam, Python + pytest is often the simplest.
- run_tests.sh (or run_tests.bat) that runs tests and exits with the test run output.
- A small "CHANGELOG.txt" or "SCENARIO.txt" that states: "The web app changed in three small ways; update the tests to match."

Important: Because candidates have no internet, include any required test runner or preinstalled environment, or instruct that the environment the candidate uses will already include required runtime dependencies.

### Practical Elements to Include (to separate practical skill from conceptual knowledge)
- Multi-step debugging flow:
  1. Run tests, find failing stack traces and assertion messages.
  2. Inspect test files to map failures to test code.
  3. Inspect the app under test (static files) to identify what changed (different id, missing element, changed text).
  4. Decide whether to change test locator or test logic (e.g., do not change app content; tests should adapt).
- Data dependencies:
  - Provide a simple test data file (JSON) that tests read; require candidate to update a path/format if tests fail.
- Decision points (distinctly observable):
  - If a selector changed location or id, does candidate use a robust selector (data-test attribute) or just brittle xpath/class?
  - For timing issues: does the candidate replace sleep/wait with an explicit condition-based wait?
  - For deprecated API calls: does the candidate update test helper to new API usage or workaround with temporary fix?
- Simulated time pressure: 90-minute timebox.
- Evidence collection: candidate must include before/after logs and full file diffs (original and modified contents in JSON) so evaluator can verify what changed and why.

### Evaluation Insights — what to look for in candidate submissions
Primary pass/fail indicators:
- Test run evidence:
  - Did the candidate run the initial tests and include the failing output? (Shows they can reproduce)
  - After their edits, do the test-run logs show the targeted tests (at minimum the previously failing ones) now pass? (Shows successful fix)
- Code edits:
  - Are the edits minimal, targeted and reasonable? (Don't accept solutions that simply delete failing tests)
  - Did the candidate improve robustness? Examples:
    - Replaced brittle class-based selectors with more stable identifiers (e.g., data-test-id).
    - Replaced sleep(3) with an explicit wait that polls for element visibility or state.
    - Updated test helper usage to current API (if applicable).
- Diagnosis quality:
  - Does the candidate clearly explain root cause and why the chosen fix is appropriate?
  - Does the candidate mention potential side effects or remaining risks?
- Best practice awareness:
  - Prefer changes that adhere to common test automation practice: use of page objects or helper functions (even minimal), explicit waits, clear assertions, not disabling assertions or removing tests.
- Completeness and format:
  - Submission follows the required JSON schema precisely (file named test_submission.json) and includes all required fields (commands & outputs, changed files with original and updated content, brief rationales).
- Time management:
  - Submission includes start and end times; finishing within 90 minutes is expected.

Suggested scoring rubric (basic exam, pass threshold 80% for junior):
- Task 1 (Reproduce & capture failures): 15 points
  - Captured initial failing output and correctly identified failing test(s) (15). Partial capture or wrong identification (7). Missing (0).
- Task 2 (Selector fix): 25 points
  - Correct, minimal selector change that fixes the test and uses a stable approach (25). Fix works but is brittle (15). Incorrect or deletes test (0).
- Task 3 (Timing/stability fix): 20 points
  - Replaced sleep with explicit wait/poll and test becomes stable (20). Partial fix (10). No fix or disabled test (0).
- Task 4 (Config/API fix): 20 points
  - Correctly updated config or API usage and tests pass (20). Partial or risky fix (10). Missing/incorrect (0).
- Documentation & submission quality: 10 points
  - Proper JSON structure, before/after contents, clear rationales (10). Some missing elements (5). Missing or poor (0).
- Bonus (up to 10 points): small refactor, added simple helpful test, or suggestions for improvements.

Minimum passing score: 80/100.

### Required JSON submission format (test_submission.json)
Provide this exact schema to candidates. All fields required unless marked optional.

- candidate_name: string
- start_time_utc: ISO 8601 string
- end_time_utc: ISO 8601 string
- total_minutes: integer
- commands_run: array of objects { "command": string, "purpose": string }
- initial_test_output: string (raw console output captured when first running the provided test run)
- final_test_output: string (raw console output after candidate changes)
- changed_files: array of objects:
  - file_path: string
  - original_content: string (full file text as provided)
  - updated_content: string (full file text after candidate edits)
  - short_rationale: string (what you changed and why in 1–3 sentences)
- summary_of_changes: string (max 300 words — high-level summary)
- risk_notes_and_next_steps: string (short list of remaining risks or improvements)
- optional_bonus: string (optional short description if candidate did extra work)

Evaluator will:
- Confirm the initial_test_output shows the original failures described in exam scenario.
- Review changed_files to validate edits are minimal, sensible, and sufficient.
- Run the final tests locally (or inspect final_test_output) to confirm passed tests.
- Score using the rubric.

### Practical grading tips for the evaluator
- Re-run the candidate’s final code in a clean instance of the provided exam environment to verify the final_test_output reproducibility.
- Check that candidate did not circumvent the intent (e.g., by removing assertions or deleting tests).
- Prefer solutions that demonstrate stable test design rather than quick hacks.
- For borderline cases, weigh the quality of reasoning in short_rationale and summary_of_changes heavily.

### Final notes for the exam creator
- Choose a simple stack the candidate is likely to know; keep the app and tests concise (total lines of code small) so editing is quick.
- Design the failing scenarios to be realistic but unambiguous (changed ID value, replaced a visible text string, introduced small timing delay).
- Ensure no external network dependencies; pack any drivers or runtime bits in the environment candidate will use.
- Provide clear instructions and the required run command in README so the candidate can spend time on fixing tests rather than setup.

This basic exam should allow a qualified junior/entry-level SQA Engineer to demonstrate practical ability to update and stabilize automated tests within a 90-minute window and score 80% or higher when following good practices.

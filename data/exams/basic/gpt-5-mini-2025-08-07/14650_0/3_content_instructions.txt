### Exam Title
Updating Automated Tests to Match Evolving Application Behavior (Basic Practical Exam)

---

### Instructions for Candidate

You have 90 minutes to complete this practical exam. Work only in the provided repository using the tools available on your machine (code execution environment and text editor). Do not access the internet or any external resources.

Overview — what you must do (four sequential tasks):
1. Environment & baseline run — (≈10 minutes)
   - Run the provided test suite exactly as-is and capture the test output that shows failing tests.
   - Save the exact commands you ran (order matters). Example commands you might use: pytest -q, python -m pytest.
   - Deliverable for this step: include the command list and the raw test output before any edits.

2. Diagnosis & plan — (≈10 minutes)
   - Inspect failing tests, their stack traces, and the small SUT files and README/spec in the repository.
   - Decide which tests need to be changed (do not change product/SUT code unless absolutely necessary; if you do, you must explain and justify it).
   - Write a short decision log describing the root cause for each failing test and your planned edits (one entry per failing test or issue).
   - Deliverable for this step: decision_log entries.

3. Implement updates to automated tests — (≈45 minutes)
   - Edit existing test files to fix failures and to make tests more robust (reduce brittleness). Typical acceptable edits:
     - Update assertions to match the new behavior (e.g., check essential keys/values rather than exact string equality).
     - Replace fragile exact matches with contains/regex/partial checks.
     - Remove hard-coded sleep/waits and use fixtures or mocks where appropriate (mocking may be simulated by small helper functions provided in repo).
     - Fix or parametrize fixtures and repeated setup to avoid duplication.
   - Add one new pytest test that implements a small new requirement described in the README.
   - Keep edits limited to tests (tests/ files). If you believe the SUT must be changed, do so only with explicit justification in your submission (this may reduce score).
   - Deliverable for this step: include full contents of all modified test files and any added test files in your submission JSON.

4. Run, verify, and document — (≈25 minutes)
   - Re-run the full test suite and capture the after-edit output that demonstrates all tests pass.
   - Prepare concise per-file explanations of what changed and why.
   - Prepare reproducible commands so an evaluator can re-run your steps exactly.
   - Final deliverable: a single JSON file named test_submission.json containing all required fields described below.

Important rules
- Time limit: complete within 90 minutes. Record time_spent_minutes in JSON.
- Only one file will be accepted for evaluation: test_submission.json. Do not submit any other files.
- The evaluator will only examine the repository you were given plus the contents you place into test_submission.json. Therefore include full contents of any modified or new test files in that JSON.
- Do not use the internet. Do not install external packages. Use only tools and files provided.

---

### Expected Outcome

By the end of the exam you must produce a single file named test_submission.json that demonstrates:

- You ran the initial failing test suite and captured the failing output.
- You diagnosed root causes and produced a concise decision_log describing changes to be made.
- You updated the automated tests (and added one new test) so that the complete test suite passes.
- You provide the exact commands you used to run tests before and after edits, the raw test outputs (before and after), and the full text of any modified and added test files.
- You give short per-file reasons for each change and clear reproduction instructions so an evaluator can re-run your results.

To pass this basic-level exam you should ensure:
- Tests run before edits show failures.
- Tests run after edits show zero failing tests (pytest summary of 0 failures).
- All modifications are limited to test files unless a strong justification is provided.

---

### Provided Materials

The exam repository you will receive contains:
- A small Python SUT (module/package) implementing the application logic under test. (Pure Python, small size — no network access.)
- tests/ — a pytest-based test suite (5–12 tests). Some tests are intentionally failing or brittle because the SUT behavior or outputs changed.
- testdata/ or sample data files used by the SUT (if applicable).
- README.md — contains:
  - A short description of the intended new behavior (so you know what tests should assert).
  - One small new requirement you must write a test for.
  - How to run the test suite (example command).
- A single command to run the tests is supported (e.g., pytest -q). Use that command unless you have good reason to run pytest differently; record any variations in commands_run.

No external dependencies or network access will be necessary.

### Submission Format

You must submit exactly one file named test_submission.json. This JSON must be valid JSON (UTF-8). The evaluator will use only this file to assess your work. Include all required fields exactly as specified below.

Required JSON schema and content expectations:

- candidate_name: string
  - Your full name.

- time_spent_minutes: integer
  - Total minutes you actually spent (<= 90).

- commands_run: array[string]
  - Ordered list of exact shell commands you executed while performing the exam. Include commands to run tests before and after edits, any helper commands, and any commands used to show file contents if you want. Example entries: "pytest -q", "python -m pytest", "sed -n '1,200p' tests/test_example.py"

- test_output_before: string
  - Raw output of the initial failing pytest run, or a clipped subset (first/last ~40 lines) that clearly shows failing tracebacks and pytest summary. Preserve formatting/newlines inside the string.

- test_output_after: string
  - Raw output of the final pytest run after your edits, or a clipped subset (first/last ~40 lines) that clearly shows a passing summary (e.g., "X passed, 0 failed").

- modified_files: array of objects
  - Each object must have:
    - path: string — path to the modified file relative to repo root (e.g., "tests/test_calc.py")
    - reason: string — brief reason why you changed this file (one sentence)
    - content: string — full text content of the modified file after your edits (include entire file).

- added_files: array of objects (empty array [] if none)
  - Each object must have:
    - path: string — path of the added file (e.g., "tests/test_new_requirement.py")
    - reason: string — brief reason why you added this file
    - content: string — full text content of the added file.

- decision_log: array of objects
  - Each object must have:
    - step: string — short identifier (e.g., "fix-format-assertion" or "add-new-flag-test")
    - decision: string — concise description of the decision you made for that step (1–2 sentences)
    - alternatives_considered: string — short list of alternatives you considered and why you did not choose them (1–2 short bullets or sentences).

- reproduce_instructions: string
  - Minimal exact commands and steps an evaluator can run in the original repository to reproduce your results and test outputs. Keep this short and precise (example: "1) pytest -q (shows failures); 2) edit files; 3) pytest -q (shows all tests pass)"). Prefer actual shell commands.

Content rules and tips (evaluate for objectivity):
- All modified_files and added_files content must be full file contents. The evaluator will not open the repository to read your working files; include everything in JSON.
- Keep changes scoped to tests/ files only unless you explicitly justify SUT edits in modified_files.reason (doing so may lower score).
- test_output_before must show failing tests; test_output_after must show passing tests.
- Keep explanations concise and factual. The decision_log should show you understood root causes and why your edits fix them.

If any part of your submission cannot be reproduced from the provided repository using only the included files and the commands you supply, it may be marked incorrect. Good luck.

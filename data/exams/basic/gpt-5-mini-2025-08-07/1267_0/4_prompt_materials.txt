You are an expert exam designer. Your task is to create synthetic but realistic digital materials for a **remote practical exam**.

Here is the exam overview for the evaluator:
<examoverview>
### Exam Purpose
Confirm that a candidate can take an existing, runnable program that produces incorrect or failing results, identify the root cause(s), apply appropriate code changes, re-run the program/tests, and deliver clear evidence that the fixes produce the desired results. This validates a core real-world skill: debugging, implementing minimal correct changes, and verifying outcomes — not just theoretical knowledge.

### Core Competencies
- Basic debugging workflow: reproduce failure, formulate hypothesis, make minimal change, re-run and verify.
- Reading and understanding unfamiliar code structure and test harnesses.
- Fixing common bug classes: syntax/typo, off-by-one, incorrect condition/logic, wrong data handling, incorrect use of API/standard library, resource/exception handling.
- Writing/adjusting small tests or using existing tests to verify fixes.
- Clear, concise reporting of changes and rationale.
- Use of local tooling only (editor + runtime) to iterate and validate fixes.

### Recommended Structure
Time limit: 90 minutes total. Basic exam should have 4 tasks of increasing complexity but all solvable by an entry-level candidate within the time.

High-level organization:
- Single project repository packaged for the candidate (no internet required).
- The repo includes: buggy source code, a README with test/run instructions, an automated test script (e.g., run_tests.sh or run_tests.py), and input/output sample files.
- Candidate completes all tasks in one repository, submits a single JSON file test_submission.json describing changes and test results, plus the modified source files.

Task breakdown (suggested):
1. Task 1 — Quick fix (15 minutes, 15 points)
   - Reproduce a trivial failing case: syntax/typo or incorrect constant causes program to crash or produce an obviously wrong result.
   - Deliverable: Fixed file(s); test runner shows pass for this case.
2. Task 2 — Logic bug (25 minutes, 30 points)
   - Off-by-one or wrong conditional that causes incorrect output on a provided test case.
   - Deliverable: Fixed code; tests show expected output for included inputs.
3. Task 3 — Data handling / edge case (30 minutes, 35 points)
   - Program fails for an edge case (e.g., empty input, null values, unexpected format), causing runtime exception or wrong behavior on larger sample.
   - Deliverable: Robust fix with minimal changes; tests pass including edge cases.
4. Task 4 — Small integration / regression check (20 minutes, 20 points)
   - After prior fixes, a regression or performance/formatting spec remains (e.g., output formatting or an additional test) that requires combining knowledge of previous fixes.
   - Deliverable: All tests pass; final run produces expected outputs/files.

Total points: 100. Passing threshold for basic exam: 80 points.

Expected deliverables from candidate:
- A single file named test_submission.json in repository root with prescribed fields (see "Submission format" below).
- All modified source files (committed or simply provided in repo — commit history optional depending on host).
- Optional short README note if needed to explain how to run tests (should be redundant with provided test runner).

### Practicality — how this is hands-on
- Candidates must run the provided test harness locally, see failing test output, edit code, re-run tests.
- No multiple-choice or paper answers — success is measured by tests/program output.
- All necessary data and tests are included so the candidate does not need external references.
- The tasks represent typical debugging jobs in production/maintenance code: small, localized fixes that must be validated.

### Strategic Elements to Include (distinguishing real performers)
- Multi-step dependency: later tasks assume earlier tasks are fixed (simulates an ongoing codebase). Candidate must recognize dependencies and run the whole test suite.
- Confusing, but deterministic failing output: failures may be caused by a cascade of small issues; candidate must find root cause, not just patch symptoms.
- Ambiguous requirement/edge-case: require candidate to make a decision (e.g., how to handle malformed input). Good candidates will choose a reasonable behavior and document it in JSON.
- Minimal-change expectation: evaluate whether the candidate made targeted fixes vs. large rewrites. Prefer minimal, well-justified changes.
- Include tests that require both correctness and simple formatting (e.g., exact whitespace, JSON structure), forcing the candidate to be precise.

### Practical Elements to Include (for exam creator)
- Language: choose one common language for which environment is easy to provide (recommend Python 3.9+ or Node.js). For a basic exam prefer Python.
- Provide an automated test runner script (single command) that returns non-zero exit code on failure and prints concise failure messages.
- Include clear README with:
  - exact command(s) to run tests,
  - brief description of tasks embedded in code comments (not detailed solutions),
  - time limit reminder and submission instructions (where to place test_submission.json).
- Provide small unit tests or assert-style checks for each task (e.g., pytest, unittest, or custom script). Tests should be deterministic, small, and quick to run.
- Include sample input/output and a “golden” reference output file. Test harness should compare actual vs expected output.
- Ensure no external dependencies required (avoid packages not in standard library) so candidate need not install add-ons.

### Submission format (test_submission.json)
Require the candidate to submit a single JSON file named test_submission.json with the following schema (all fields required unless noted optional):

- candidate_name (string)
- task_results (array of 4 objects, ordered tasks 1–4). Each object:
  - task_id (integer) — 1..4
  - files_changed (array of strings) — paths of files changed
  - change_summary (string) — up to ~200 words explaining the change
  - root_cause (string) — short explanation of what caused the failure
  - how_tested (string) — commands run and results (include exact test runner output lines that show pass/fail)
  - time_spent_minutes (integer)
  - confidence_level (string) — one of: "high", "medium", "low"
  - notes (string, optional) — any assumptions or trade-offs made
- final_test_output (string) — full output of the final run of the test runner (paste as-is)
- total_time_minutes (integer)
- checksum_of_modified_files (object) — mapping filename -> SHA256 hex digest (optional but recommended)
- final_score_self_assessment (integer 0..100) — candidate's self assessment of correctness

Example minimal test_submission.json (not code-block formatted here — to be created by candidate):
{
  "candidate_name": "Alice Example",
  "task_results": [
    {
      "task_id": 1,
      "files_changed": ["app/utils.py"],
      "change_summary": "Fixed typo: used 'len(items) > 0' instead of 'len(items) >= 0'.",
      "root_cause": "Incorrect conditional always true causing incorrect path.",
      "how_tested": "ran ./run_tests.py; Task1: PASS",
      "time_spent_minutes": 12,
      "confidence_level": "high",
      "notes": ""
    },
    ... tasks 2-4 ...
  ],
  "final_test_output": "All tests passed\n",
  "total_time_minutes": 78,
  "checksum_of_modified_files": {"app/utils.py": "abc123..."},
  "final_score_self_assessment": 92
}

Make it explicit in README that this file name and structure are required; evaluator can parse this file automatically.

### Evaluation Insights — what to look for
Primary observable outputs:
- Passing automated tests (all tasks): objective evidence the candidate produced the desired results.
- test_submission.json content: demonstrates candidate’s reasoning and reproducibility.
- Changes are minimal and well-targeted (diff review).

Scoring rubric (suggested):
- Task correctness (automated): 70 points total
  - Task 1: 15
  - Task 2: 20
  - Task 3: 20
  - Task 4: 15
  (Automated tests yield full points per task when passing.)
- Explanation & reproducibility: 20 points
  - Clear root cause & change_summary for each task (10 points)
  - test runner output included & steps to reproduce (10 points)
- Code hygiene & minimality: 10 points
  - No unnecessary changes, appropriate in-file comments, reasonable naming (10 points)

Partial-credit rules:
- If tests for a task still fail, award partial points for a correct root cause and a reasonable, partially-working change documented in change_summary (up to 50% of that task’s points).
- If candidate fixed code but introduced regressions (other tests fail), deduct points from code hygiene/minimality and task points of failing tests.
- If candidate’s fix is functionally correct but implemented as a large rewrite, award correctness points but deduct up to 50% of the code hygiene points.

Red flags (reduce score or require follow-up):
- test_submission.json missing or incomplete.
- No explanation of root cause or how tests were run.
- Massive unrelated changes (e.g., reformat whole repo without justification).
- Tests pass but change comments are incorrect / clearly copied (if evaluator suspects plagiarism).

Sample evaluator workflow:
1. Clone candidate repo (or unzip submission).
2. Run test runner exactly as README instructs.
3. Verify test_submission.json exists and parse it.
4. Cross-check tests claimed to be run vs actual test output.
5. Inspect diffs/modified files for correctness and minimal changes.
6. Apply scoring rubric and provide feedback.

### Time allocation guidance (for candidate)
- Read README + run tests initially: 5–10 minutes
- Task 1: 15 minutes
- Task 2: 25 minutes
- Task 3: 30 minutes
- Task 4 + final regression run + prepare submission JSON: 10–15 minutes
Total: 85–95 minutes (aim to keep under 90).

### Sample bug types to include (for exam creator)
- Wrong operator or off-by-one (easy to spot).
- Incorrect handling of empty input or missing file (exception).
- Logic error in loop or conditional causing incorrect aggregation.
- String formatting/serialization mismatch vs expected golden output.
- Minor performance pitfall (e.g., O(n^2) vs expected O(n)) — only if it affects test in time-limit.

### Final notes for exam creators and evaluators
- Keep tasks realistic but self-contained so they test debugging ability, not domain expertise.
- Make tests deterministic and fast.
- Ensure no external internet access is required.
- Use the test_submission.json as the primary artifact for automated and manual scoring.

This design will allow a remote, hands-on verification that a candidate can correct errors, make appropriate changes, and recheck the program to ensure the desired results are produced — the practical competence required for an entry-level Computer Programmer role.

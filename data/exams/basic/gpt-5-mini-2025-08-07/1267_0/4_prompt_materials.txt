You are an expert exam designer. Your task is to create synthetic but realistic digital materials for a **remote practical exam**.

Here is the exam overview for the evaluator:
<examoverview>
### Exam Purpose
Verify that a candidate can take a working codebase that produces incorrect or incomplete results, identify and correct defects in the code, re-run the program and tests, and demonstrate with clear evidence that the desired results are now produced. The exam confirms a real-world capability: fixing real bugs in a small codebase and validating fixes with automated or reproducible checks — the essential behaviour of a programmer responsible for maintaining and improving existing software.

### Core Competencies
- Debugging fundamentals: reproduce failures, read stack traces/logs, locate root cause.
- Corrective coding: make minimal, correct source changes (syntax, logic, boundary cases).
- Validation: re-run the program or test-suite, interpret results, and iterate until passing.
- Reasoning and justification: explain why the change fixes the problem and any trade-offs.
- Code hygiene and minimal invasiveness: prefer clear, maintainable fixes and avoid unnecessary changes.
- Use of available tools (editor, runtime, unit test runner, stdout/stderr) to perform the work under time constraints.

### Recommended Structure
Time limit: 90 minutes.

Number of tasks: 4 focused, progressive tasks (30–40 minute total for solving; remainder for write-up and final verification). Each task is small enough to complete within 15–30 minutes and covers different bug classes.

Sequence and rationale:
1. Task A — Quick compile/run failure (5–10 minutes)
   - Purpose: verify the candidate can reproduce an immediate failure (syntax, missing import).
   - Deliverable: modified source that runs; short explanation.

2. Task B — Single logical bug (15–20 minutes)
   - Purpose: fix an incorrect algorithm or wrong conditional causing incorrect result.
   - Deliverable: code change + demonstration (unit test passes or sample input/output matches) + brief explanation.

3. Task C — Edge-case / off-by-one / input validation (20–25 minutes)
   - Purpose: fix correctness for edge inputs and improve robustness (nulls, empty data, negative numbers).
   - Deliverable: code change + unit tests added or existing tests updated to cover edge cases (see constraints below) + explanation.

4. Task D — Small integration/behavior bug or regression (20–25 minutes)
   - Purpose: fix a bug that requires reasoning across two modules or a small refactor (e.g., API contract mismatch, wrong data format).
   - Deliverable: code change + passing integration test or sample script run + explanation of root cause and fix.

Mandatory rule for candidate: Do not change the provided test harness files (if any) unless explicitly permitted. Fix only source modules. The test harness is the oracle.

Expected deliverables:
- test_submission.json (exact JSON format described below)
- Modified source files (as provided in their workspace); candidate will include contents in the JSON.
- Terminal log(s) showing failing and passing runs (before/after).
- Short written explanations (per task) that justify each change.

Time allocation recommendation:
- Tasks A–D: ~60 minutes total
- Write-up, packaging, final verification: ~20–30 minutes

### Practicality — How this is hands-on (not a knowledge quiz)
- Candidate must run code, reproduce failures, open files, edit source, and re-run tests — actions, not theoretical answers.
- Tests and sample inputs are provided so the candidate can quickly observe failing behavior and confirm fixes.
- Candidate cannot access external web resources; they must use local debugging, reasoning, and language runtime knowledge.
- The exam includes multiple bug types mirroring real maintenance tasks: syntax, logic, boundary cases, and integration/regression.

### Strategic Elements that Differentiate Real Performers
Include these features in tasks to separate those who can do the job from those who only know theory:

- Multi-step debugging chains: a failing test may reveal a symptom, but the root cause lives in a different module. Fix requires tracing data flow (file A -> B -> C).
- Data dependencies: use small sample data files where a transformation is applied in stages; the bug could be a mismatch in expected format between stages.
- Decision points: provide one task where the candidate must choose whether to:
  - change the code to accept an ill-formed input, or
  - harden the input validation and return an error.
  The preferred solution (for this basic exam) should be to enforce correct behavior and document assumptions — but acceptance criteria are in the task description.
- Limited refactoring window: candidate should apply minimal, targeted changes rather than rewrite; this reveals pragmatic judgement.
- Tests as forensic tools: supply failing unit tests and a test runner; a competent candidate will use the tests to find and confirm fixes rather than guess.

Example defects to seed (basic level):
- Syntax/typo (easily reproducible quickly).
- Off-by-one in loops or slice boundaries.
- Incorrect boolean condition or order of operations.
- Incorrect handling of empty list/None/zero values.
- Wrong type conversion (string vs number).
- Misuse of API or incorrect assumptions about a helper function return value.
- Missing error handling causing crash on edge input.

### Practical Elements to Include (for exam creator)
- Small repository (2–6 source files) in a single language (recommend Python for speed or JavaScript/Node). Keep codebase small so edits are quick.
- A test harness with 6–10 unit tests:
  - 2 trivial tests (Task A)
  - 2–3 functional tests failing for Task B and C
  - 2 integration/regression tests failing for Task D

- A README that explains the constraints (no internet, do not modify tests, time limit, submission format).
- Seed a few clear comments in code like "# BUG: off-by-one" to reduce time-wasted guessing while still requiring actual fixes (this is optional — for basic exam you may include 1 comment hint).
- Provide sample inputs/outputs for the expected behavior so the candidate can confirm fixes manually if they prefer.

### Evaluation Insights — Observable outputs and criteria
Primary pass/fail evidence:
- Passing tests or program output: the strongest evidence is that the provided test harness or sample runs all succeed. For each task, tests that previously failed now pass.
- Reproducible command log: candidate supplies the exact commands and outputs that demonstrate failure before and success after fixes.

Qualitative signals (score these to complement test results):
- Explanation quality (20%): does the candidate clearly state root cause, why their change fixes it, and any assumptions or trade-offs? Look for concise reasoning — not just "I changed X to Y".
- Minimal and appropriate code change (15%): prefer limited, well-scoped changes. Penalize unnecessary widespread rewrites. Look for small diffs and clear intent.
- Correctness across edge-cases (15%): candidate should show they considered edge inputs (especially for the edge-case task). Passing additional tests for boundary conditions is a plus.
- Use of tests/logs to localize bugs (10%): candidate must show they used test output and stack traces to guide the fix (visible in commands_run and status_before).
- Clean submission (10%): JSON validity, inclusion of modified files, and reproducible commands.

Suggested numeric scoring (basic exam; target pass >= 80%):
- Functional correctness (tests passed): 60 points (all-or-most based on how many required tests pass)
- Explanation quality: 20 points
- Code hygiene/minimal changes: 10 points
- Completeness and reproducibility of submission (JSON correctness, logs): 10 points

Example pass threshold:
- Candidate who fixes all seeded failures and provides the required JSON with clear explanations should score > 80/100.
- A candidate who only fixes obvious syntax errors but fails logical and edge-case tasks typically scores < 50.

### Practical tips for the exam creator / evaluator
- Keep the repository and tests small and deterministic (no network, time-dependent behaviour, or randomness without seed).
- Make the failing behaviour unambiguous: tests should fail with clear messages. Avoid tests that can pass with multiple ambiguous fixes unless the task explicitly allows design choices.
- For fairness, clearly document what files the candidate may modify and the rule about not editing tests.
- Include at least one test that demonstrates an edge-case to force candidates to think about inputs/validation.
- Provide an example passing run in the evaluator docs (not visible to candidates) to validate the scoring script.

This design produces a compact, hands-on remote exam suited to assess an entry-level programmer’s ability to locate, fix, and validate code defects within 90 minutes, with a clear, machine-checkable submission format (test_submission.json) to simplify grading and reproducibility.

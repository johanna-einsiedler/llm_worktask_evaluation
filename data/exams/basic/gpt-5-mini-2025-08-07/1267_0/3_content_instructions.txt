### Exam Title
Practical Debugging & Fixing — Basic Level (90-minute remote practical)

### Instructions for Candidate

Overview
- You will be given a small, working repository containing source code, a test harness, and a run script. The codebase has 4 seeded problems of increasing difficulty (Tasks A–D). Your job is to reproduce failures, fix only the source modules (not the tests or harness), re-run the tests and any sample scripts, and produce a single structured JSON submission named test_submission.json that documents your work and includes the final source file contents.
- Time limit: 90 minutes. You must complete all four tasks within this time.

Rules (must be followed)
- Use only the tools available in the workspace: a code execution environment (runtime/test runner) and a text editor. No internet or external references.
- Do NOT modify any test files or the test harness (files in the tests/ directory, run_tests.sh, or equivalent) unless a task explicitly permits it. The test harness is the oracle of correctness.
- Make minimal, focused changes to source code. Avoid large rewrites or changing unrelated files.
- Your submission must be a single file named test_submission.json placed at the repository root. This file is the ONLY artifact evaluated.
- Include command output (failing and passing runs) in your JSON so an evaluator can reproduce your steps.

Step-by-step tasks (what you must do)
- Task A — Quick run/compile failure (5–10 min)
  1. Run the provided test harness (e.g., ./run_tests.sh or python -m pytest -q) to observe immediate failures.
  2. Identify the cause of the immediate failure (syntax, missing import, etc.), fix only the minimal source code required so the code runs.
  3. Re-run the harness to confirm the immediate failure is resolved.

- Task B — Single logical bug (15–20 min)
  1. Identify a failing unit/functional test that shows incorrect behaviour (wrong algorithm / wrong conditional).
  2. Make a minimal, correct change to the source to fix the logic.
  3. Re-run tests and confirm that the specific test(s) for this task now pass.

- Task C — Edge-case / input validation (20–25 min)
  1. Locate a failing test that demonstrates an edge-case problem (empty input, None/null, off-by-one, negative values).
  2. Fix the code to correctly handle the edge-case and, if necessary, add or update unit tests that are provided in the repo to prove the fix (see constraints below about not modifying tests — only modify tests if the repository explicitly includes a “permitted-to-edit” test file).
  3. Re-run the test harness and confirm the edge-case tests pass.

- Task D — Small integration/behavior bug (20–25 min)
  1. Find a test or sample script that fails due to a mismatch or regression across modules (data format mismatch, wrong interface usage, or incorrect data flow).
  2. Make a targeted fix (may touch 1–2 source modules). Keep changes minimal and well-justified.
  3. Re-run the full harness and any integration script(s) to confirm all relevant tests pass.

Notes on approach
- Use the failing test output and stack traces to locate the root cause before editing code.
- Prefer a minimal, readable fix rather than a large refactor.
- If you encounter ambiguous design choices (e.g., accept ill-formed input vs. validate and reject), follow the repository’s comments and test expectations. If still ambiguous, choose to validate inputs and return a clear error — but document your decision in the explanation.
- Keep a short command log of the exact commands you ran and the important outputs (failing messages, stack traces, final passing summary). Include these logs verbatim in your JSON.

Time allocation recommendation
- Tasks A–D: ~60 minutes total (5–10, 15–20, 20–25, 20–25)
- Packaging write-up and final verification: ~20–30 minutes

### Expected Outcome

By the end of the exam you must produce:
- A repository where the previously failing tests targeted by Tasks A–D are fixed.
- A single JSON file named test_submission.json at the repository root that documents your work and includes:
  - Per-task entries describing status before and after, the exact source files you modified (with full final contents), the commands you ran and key outputs, a 2–6 sentence explanation of the root cause and fix, and time spent per task.
  - A final_test_summary showing total tests, passed, failed, and the full final run_tests output.
  - A short signature line.

Scoring (what the evaluator will check)
- Tests you fixed must pass. Passing the provided test harness (all tests) is the strongest evidence of success.
- Explanations should clearly state the root cause and why your change fixes it.
- Changes should be minimal and restricted to source modules.
- JSON must follow the schema in the Submission Format below and be valid JSON.

### Provided Materials

You will be given a small repository containing:
- Source files (2–6 files) in a single language (Python recommended).
- A tests/ directory with unit tests (6–10 tests). Tests are seeded so:
  - 2 trivial tests for Task A
  - 2–3 functional tests for Tasks B and C
  - 2 integration/regression tests for Task D
- A test harness script (run_tests.sh or an equivalent) that runs the test suite and prints a machine-parseable summary to stdout. You may also run the test runner directly if you prefer (for example, pytest -q).
- A README with constraints and the rule about not modifying tests.
- (Optional, basic) sample input files used by the integration tests.

Important constraints about provided materials
- You may not add external libraries or change runtime dependencies.
- You may not modify test files or run script unless the repository explicitly marks a test file as editable for Task C (rare for this basic exam). If uncertain, assume tests and harness are off-limits.

### Submission Format

You must submit a single file named test_submission.json at the repository root. This JSON must be valid and follow this exact structure (field names and types must match):

- candidate_name: string
- time_taken_minutes: number
- tasks: array of task entries — one object per task in order A, B, C, D. Each task object must include:
  - id: string (e.g., "A")
  - status_before: string — short summary of the failing behaviour you observed before changes (include failing test names or error messages / stack traces snippets).
  - status_after: string — short summary after your fixes (include passing test names or final program output).
  - modified_files: array of objects { filename: string, content: string } — include the full final contents (UTF-8) of every source file you changed. If you changed no files for a task, provide an empty array.
  - commands_run: array of strings — list the exact commands you executed and the important outputs (copy/paste the failing output and the final passing output snippets). Include both the failing run(s) and the final passing run(s) relevant to the task.
  - explanation: string — 2–6 sentences explaining the root cause and the fix you applied (why this is correct and any assumptions).
  - time_spent_minutes: number — approximate minutes you spent on this task (should sum to <= time_taken_minutes).

- final_test_summary: object:
  - total_tests: number
  - passed: number
  - failed: number
  - runtime_output: string — the complete final stdout output of the run_tests.sh (or test runner) invocation after your fixes.

- signature: string — one-line signature (your name).

Additional requirements and tips for the JSON
- Include the complete final content of each modified file (not diffs).
- Commands_run should include exact commands such as:
  - ./run_tests.sh
  - python -m pytest -q
  - python scripts/sample_run.py input.txt
  - Any outputs pasted from terminal (failing trace, pytest summary).
- Keep explanations concise and factual — describe root cause, the precise code change, and why it solves the problem.
- Ensure the JSON is valid UTF-8. The evaluator will parse it automatically.

Example skeleton (you may use this as a template — replace values with your real outputs)
{
  "candidate_name": "Alice Example",
  "time_taken_minutes": 62,
  "tasks": [
    {
      "id": "A",
      "status_before": "SyntaxError at line 12: invalid syntax",
      "status_after": "Program runs; unit test 'test_init' passes",
      "modified_files": [
        {"filename":"app.py","content":"<full file contents here>"}
      ],
      "commands_run": ["./run_tests.sh\nOutput: ...", "python app.py\nOutput: ..."],
      "explanation": "Fixed a missing colon in function definition. This resolves the immediate SyntaxError and allows the test harness to run.",
      "time_spent_minutes": 8
    },
    ...
  ],
  "final_test_summary": {
    "total_tests": 8,
    "passed": 8,
    "failed": 0,
    "runtime_output": "Full run_tests.sh output here..."
  },
  "signature": "Alice Example"
}

What to include in modified_files
- For every source file you changed, include an object with filename and the full final source code content.
- Do NOT include binary files.
- If you add a small helper file as part of the fix (rare and allowed), include it in modified_files and ensure it is permitted by the repository instructions.

Final checks before submission
- Run the full test harness one final time and paste the full output into final_test_summary.runtime_output.
- Validate that test_submission.json is valid JSON (use python -c 'import json,sys; json.load(open("test_submission.json"))' or similar).
- Confirm total time_taken_minutes reflects the real time you spent and that task time_spent_minutes fields sum to a value ≤ time_taken_minutes.

Good luck. Work incrementally: reproduce a failure, locate the cause, make the minimal change, re-run tests, and document each step in test_submission.json.

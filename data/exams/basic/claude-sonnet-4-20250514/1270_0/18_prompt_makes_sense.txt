# Basic Computer Programming Practical Exam

## Exam Instructions

You are a junior programmer at TechCorp Industries. Your manager has assigned you to build an inventory management system that processes transactions and controls equipment. You have 90 minutes to complete this practical programming exam.

## Your Assignment

### Phase 1: Inventory Management System (60 minutes)

Build a program that processes inventory transactions and maintains accurate stock levels.

**Requirements:**
1. **Read and process transaction data** from the provided CSV file
2. **Update inventory levels** based on transactions (shipments add stock, sales subtract stock)
3. **Generate low stock alerts** for items with quantity below their reorder threshold
4. **Produce a daily summary report** with total transactions processed and current stock status
5. **Handle data validation** - reject invalid transactions and log errors

**Business Rules:**
- Shipment transactions (type "SHIP") add to inventory
- Sale transactions (type "SALE") subtract from inventory  
- Sales cannot reduce inventory below 0 (reject these transactions)
- Generate alerts when current stock < reorder_threshold
- All item codes must exist in the initial inventory file

### Phase 2: Equipment Control Integration (25 minutes)

Extend your system to control warehouse equipment based on inventory operations.

**Requirements:**
1. **Send equipment commands** when processing transactions:
   - SHIP transactions → send "SCAN_BARCODE" command to scanner
   - SALE transactions → send "PRINT_RECEIPT" command to printer
2. **Process equipment responses** and log successful/failed operations
3. **Handle equipment failures** - if equipment returns "ERROR", log the failure but continue processing
4. **Generate equipment status report** showing total commands sent and success/failure counts

### Phase 3: Final Testing (5 minutes)

Test your complete system and document any issues found.

## Materials Provided

You will receive these data files:

1. **initial_inventory.csv** - Starting inventory with columns:
   - item_code, item_name, current_quantity, reorder_threshold

2. **transactions.csv** - Daily transactions with columns:
   - transaction_id, item_code, transaction_type, quantity, timestamp

3. **equipment_responses.csv** - Simulated equipment responses with columns:
   - command_id, equipment_type, command, response_status

## Format Requirements

### String Values
- **item_code**: Use exact codes from CSV files (e.g., "A001", "B002")
- **item_name**: Use exact names from initial_inventory.csv
- **transaction_id**: Use exact IDs from transactions.csv (e.g., "T001", "T022")
- **equipment**: Must be exactly "scanner" or "printer" (lowercase)
- **command**: Must be exactly "SCAN_BARCODE" or "PRINT_RECEIPT" (uppercase)
- **status**: Must be exactly "SUCCESS" or "ERROR" (uppercase)

### Integer Values
- All quantity and count fields must be whole numbers (no decimals)
- Negative quantities are not allowed in final inventory
- All summary counts must equal the sum of their components

### Array Ordering
- **final_inventory**: Order by item_code alphabetically
- **low_stock_alerts**: Order by item_code alphabetically  
- **rejected_transactions**: Order by transaction_id
- **equipment_commands**: Order by the sequence transactions were processed

### Equipment Command Mapping Rules
- SHIP transactions → scanner equipment, SCAN_BARCODE command
- SALE transactions → printer equipment, PRINT_RECEIPT command
- Command status determined by matching with equipment_responses.csv in order

### Validation Rules
- All item_codes in transactions must exist in initial_inventory.csv or be rejected
- Sales cannot reduce inventory below 0 (reject transaction if insufficient stock)
- Equipment responses are consumed sequentially from equipment_responses.csv
- Low stock alerts only for items where current_quantity < reorder_threshold

### Source Code Format
- Include complete, executable program code as a single string
- Use proper escape characters for quotes and newlines within the JSON string
- Code should be readable and well-commented

# Basic Computer Programming Practical Exam Design

## Exam Overview and Purpose

This practical exam assesses a candidate's ability to **actually write, update, and maintain functional computer programs** that solve real-world business problems. Unlike theoretical assessments, this exam requires candidates to produce working code that handles data processing, business logic, and system integration tasks commonly found in entry-level programming positions.

## Strategic Exam Structure

### Core Assessment Philosophy
The exam simulates a **realistic workplace scenario** where a junior programmer receives a business requirement and must deliver a complete, working solution. This approach differentiates candidates who can actually program from those who only understand programming concepts.

### Key Strategic Elements

#### 1. **Multi-Step Problem Solving**
- **Data Input Processing**: Reading and validating data from multiple sources
- **Business Logic Implementation**: Applying rules and calculations
- **Output Generation**: Producing formatted results and reports
- **Error Handling**: Managing edge cases and invalid inputs

#### 2. **Data Relationship Management**
- Working with related datasets (customers, orders, inventory)
- Implementing data joins and lookups
- Maintaining data integrity across operations
- Handling missing or inconsistent data

#### 3. **Decision Points and Branching Logic**
- Conditional processing based on business rules
- Status updates and workflow management
- Alert generation for critical conditions
- Dynamic behavior based on data characteristics

#### 4. **Real-World Constraints**
- Time-based processing (dates, deadlines)
- Quantity and threshold management
- Data validation and sanitization
- Performance considerations for data processing

## Practical Assessment Components

### Primary Task: Inventory Management System
Candidates must build a complete inventory tracking system that:
- Processes incoming shipments and sales transactions
- Updates stock levels automatically
- Generates alerts for low inventory
- Produces management reports
- Handles data validation and error cases

### Secondary Integration: Equipment Control Simulation
Candidates extend their system to:
- Send commands to simulated equipment (printers, scanners)
- Process equipment status responses
- Log equipment interactions
- Handle equipment failure scenarios

## Evaluation Strategy

### Success Indicators
- **Functional Code**: Programs execute without errors
- **Correct Logic**: Business rules implemented accurately
- **Data Integrity**: Proper handling of data relationships
- **Error Management**: Graceful handling of edge cases
- **Code Organization**: Clear structure and maintainability

### Differentiation Factors
- **Problem Decomposition**: How candidates break down complex requirements
- **Data Flow Design**: Understanding of how data moves through the system
- **Integration Thinking**: Ability to connect multiple system components
- **Practical Decision Making**: Choosing appropriate solutions for real constraints

## Optimal Exam Structure

### Phase 1: Core Programming (45 minutes)
- Implement basic inventory tracking functionality

- Generate simple reports and alerts

- Add equipment control capabilities

## Materials Design and Expected Outcomes

### Data Structure Design
The test materials were carefully constructed to create predictable, verifiable outcomes while testing all required programming capabilities:

**Initial Inventory (10 items):**
- Items grouped by category (A=Widgets, B=Gadgets, C=Tools, D=Components, E=Supplies)
- Varying starting quantities (40-300) and reorder thresholds (20-75)
- Designed to trigger low stock alerts after transaction processing

**Transaction Processing (25 transactions):**
- Mix of SHIP (add inventory) and SALE (subtract inventory) transactions
- Includes deliberate test cases for error handling
- Sequential processing required to maintain data integrity

### Key Relationships and Expected Results

**Final Inventory Calculations:**
- A001: 100 + 50 - 80 + 60 = 130 (above threshold of 25)
- A002: 75 + 30 - 120 - 50 = -65 → Invalid sale T012 rejected, final = 55 (above threshold of 30)
- B001: 200 - 25 + 75 - 300 = -50 → Invalid sale T024 rejected, final = 250 (above threshold of 50)
- B002: 40 - 30 - 5 = 5 (LOW STOCK ALERT - below threshold of 25)
- C001: 150 - 60 - 45 - 20 = 25 (LOW STOCK ALERT - below threshold of 40)
- C002: 80 + 25 - 30 = 75 (above threshold of 35)
- D001: 300 + 100 - 150 = 250 (above threshold of 75)
- D002: 120 - 40 + 80 = 160 (above threshold of 60)
- E001: 90 - 15 + 40 = 115 (above threshold of 20)
- E002: 180 - 90 - 45 = 45 (above threshold of 45)

**Error Cases (3 total):**
1. T022: Invalid item code "X999" (doesn't exist in inventory)
2. T012: A002 sale of 120 would create negative inventory (75+30-120 = -15)
3. T024: B001 sale of 300 would create negative inventory (200-25+75-300 = -50)

**Equipment Commands:**
- SHIP transactions generate scanner commands (8 total)
- SALE transactions generate printer commands (14 valid sales)
- Equipment responses include 2 ERROR statuses (CMD007, CMD015)
- Commands are processed sequentially, matching transaction order

**Daily Summary:**
- Total transactions processed: 22 (25 minus 3 rejected)
- Total shipments: 8
- Total sales: 14
- Total rejected: 3

**Low Stock Alerts:**
- B002: quantity 5, threshold 25
- C001: quantity 25, threshold 40

### Tricky Elements and Common Pitfalls

1. **Sequential Processing Required**: Transactions must be processed in order since later transactions depend on updated inventory levels from earlier ones.

2. **Negative Inventory Prevention**: Candidates must check if a sale would create negative inventory BEFORE processing it.

3. **Invalid Item Codes**: Transaction T022 references non-existent item "X999" - must be rejected.

4. **Equipment Command Mapping**: 
   - SHIP → scanner/SCAN_BARCODE
   - SALE → printer/PRINT_RECEIPT
   - Only valid transactions should generate equipment commands

5. **Equipment Response Processing**: Equipment responses are provided in a separate file and must be matched to commands by sequential order (CMD001 corresponds to first equipment command sent, etc.).

6. **Threshold Comparison**: Low stock alerts trigger when current_quantity < reorder_threshold (strictly less than, not less than or equal).

### Hidden Information Requiring Careful Reading

- Equipment commands are only sent for VALID transactions (rejected transactions don't generate equipment commands)
- Equipment responses must be processed in the order commands were sent
- The reorder threshold comparison uses strict inequality (<)
- Transaction timestamps are provided but not required for processing logic
- Item codes follow a pattern but candidates shouldn't assume this pattern extends beyond provided data

This design ensures that candidates who correctly implement all business logic will produce identical, verifiable results, while those who miss edge cases or make logical errors will produce detectably different outputs.

- Missing critical JSON fields (final_inventory, rejected_transactions)
- Major calculation errors affecting majority of inventory items
- Complete absence of transaction validation
- Incorrect data types in JSON output
